# 优化规则

- [950(Ascend950) MXFP8 fused-MoE：进分组 matmul 前激活量化 scale 必须打包成 ［M, N//2, 2］ 并中心化收口](950_mxfp8_moe_activation_scale_packed_layout.md)：950(Ascend950) fused-MoE MXFP8(w8a8_mxfp8) 推理路径上，进下游分组 matmul(npu_grouped_matmul_swiglu_quant / gmm)前的激活量化 scale 必须做布局归一化：二维 [M,N] scale(dtype FLOAT8_E8M0FNU_DTYPE / E8M0)须 reshape 成打包三维 [M,N//2,2]，相邻两个 scale 打进最后一维。判据「scale 二维 + 最后一维 N 偶数 → 打包成 [M,N//2,2]；N 奇数直接 ValueError，不静默降级」。950 分组 matmul kernel 期望打包三维布局，而上游 npu_dynamic_mx_quant / npu_dynamic_quant 产出二维，须用中心化 DeviceAdaptor 方法(maybe_normalize_mxfp_scale_layout)统一收口：基类 no-op、950 override 才 reshape，避免各分支各写一遍漏做。三类接入点：动态量化产 scale 出口(注意 dynamic_scale is None 的提前 return 旁路易漏)、npu_grouped_matmul_swiglu_quant 的 gmm1 输出 scale、MoE MLP quant_apply_mlp 仅 use_mxfp_quant 时归一化。非 950 硬件与非 MXFP8 路径保持原样。衔接 MoE dispatch-combine v2 与分组 gmm 消费顺序。仓自报 Ascend950DT E2E serving 通过、无独立精度复测。
- [大 MoE 昇腾部署选型：并行形态/模型变体按集群规模选 + 非默认平台(310P/950)的算子与 HCCL 适配](ascend_deploy_parallel_variant_and_nondefault_platform.md)：大 MoE 昇腾部署选型：并行形态/模型变体按集群规模选 + 非默认平台(310P/950)的算子与 HCCL 适配。在昇腾上部署大 MoE 模型时，两类决策要先定：(1) 并行形态与模型变体按「时延 vs 吞吐 vs 集群规模/显存」选；(2) 若目标平台不是 recipe 官方目标（A3/950），要预判该平台的算子路径与 HCCL 适配点。310P 侧另含：多模态视觉 encoder 的非因果 attention 须避开 torch_npu._npu_flash_attention_unpad（该算子在 310P 有精度问题），改按 cu_seqlens 逐段调 npu_prompt_flash_attention(BSND)。
- [昇腾部署镜像的组件版本对齐（torch_npu / 驱动 HDK / CANN 包）与过渡态规避](ascend_deployment_image_version_alignment.md)：昇腾部署镜像的组件版本对齐（torch_npu / 驱动 HDK / CANN 包）与过渡态规避。cann-recipes-infer 的昇腾部署镜像把 torch_npu、驱动/HDK、CANN 包的版本成套 pin 死。不要把其中任一组件当作可自由升级的旋钮：单独换一个而与镜像不匹配，会在 bringup 期直接失败。做部署/调优时，先把组件版本对齐到目标 recipe/镜像 pin 的版本，再动优化。下面是三条已踩过的对齐关系与过渡态规避。

- [给 AscendC 自定义算子带外传入 torch 无法表示的 dtype（hifloat8/fp8 族）— int? dtype 参数 + TensorWrapper 包裹](ascendc_custom_op_out_of_band_dtype.md)：给一个走 torch_ops_extension 的 AscendC 自定义算子扩展输入 dtype，而这个 dtype 是 torch 的 scalar_type 无法表达的（典型是 hifloat8，其它 fp8/低比特族同理）。此时把裸 at::Tensor 直接交给 EXEC_NPU_CMD_V1，aclnn kernel 只能按张量自身的 torch dtype 推断 acl 类型，拿不到真实的 hifloat8——需要一条「把 torch 表示不了的 dtype 带外（out-of-band）传给 kernel」的通路。

- [块内双向注意力（掩码扩散 / DLLM 解码）走 FIA 非因果全注意力，勿套 causal FA 快路径](bidirectional_attention_fia_non_causal_full.md)：块内双向注意力（掩码扩散 / DLLM 解码）走 FIA 非因果全注意力，勿套 causal FA 快路径。在昇腾上适配一类块内注意力是双向的模型（Diffusion LLM / DLLM，掩码扩散式解码——一个块内并行逐步去掩码，块内所有位置互相可见），而不是自回归 causal 时。这类模型若沿用平台通用 causal FA 快路径，结果会错：causal 只算下三角、丢掉上三角，而块内是全连接语义。典型症状是解码输出异常但无报错（算子接受了非因果 shape、只是语义不对）。
- [因果稀疏注意力 CP prefill 的 zigzag 负载均衡：每 rank 两段两次调用 + 头尾因果前缀 actual_seq_lengths（qlen≠kvlen）](causal_cp_prefill_zigzag_actual_seqlens.md)：对因果掩码的注意力（含稀疏注意力：lightning-indexer 算 topk 索引 + sparse-flash-attention 下游）在 prefill 阶段开 context-parallel（query 沿序列维切到各 rank、KV 需完整）时，不要按「连续切分 + rank r 独占第 r 个 token」的朴素方式切——因果三角会让负载严重倾斜。正确做法是 zigzag 头尾配对切分，并且每 rank 对每个算子发两次调用、两次分别用「头段」「尾段」各自的因果前缀长度作 actual_seq_lengths_key。这是把 long-seq-prefill-context-parallel 的 CP 策略落到因果稀疏注意力时，决定正确性与均衡的一处关键实现细节。
- [CUDA 原生 DiT/视频生成模型移植昇腾：注意力后端改路由 NPU + 绕过 SP 库 CUDA 硬检查](cuda_native_dit_video_attention_sp_npu_adaptation.md)：注意力后端是 CUDA 专用的（flash_attn 或 xformers）——NPU 无这些包，import 即失败或运行即错。→ 把注意力改路由到 NPU 融合注意力（npu_fused_infer_attention_score 或 scaled_dot_product_attention）。 序列并行依赖库（xDiT/xfuser + yunchang）内置 CUDA 版本硬检查，初始化阶段强制校验 CUDA 环境，NPU 上直接判失败。→ 在检查点插入 try: import torch_npu 的 NPU 探测分支，跳过 CUDA 校验、保留 GPU 双路径。

- [消除 decode/生成热路径每步重复的 host 侧算子入参准备（scale / seq-length / 量化 scale：预算一次 + 透传/缓存复用）](decode_host_scalar_precompute_passthrough.md)：消除 decode/生成热路径每步重复的 host 侧算子入参准备（scale / seq-length / 量化 scale：预算一次 + 透传/缓存复用）。decode 逐 token / 生成多步推理时延偏高，profiling 看到频繁的下发中断（dispatch interruption）+ device 等待，或热路径里有 host 端标量运算 / .item() / 反复构造小张量 .npu()。 通用症结：每前向重复做、但在稳态内容不变的 host 侧算子入参准备（标量 scale、seq-length 小张量、量化 scale）是可去除的固定开销——它落在 host、每层/每步触发，造成下发中断与 H2D 强同步。
