# 优化技术

- [Attention-FFN Disaggregation (AFD)机制](afd.md)：AFD 将 Attention 与 FFN 放在独立节点，通过收发交换中间结果，使两侧计算资源可以分别配置。是否减少等待取决于计算、通信与汇合依赖；该机制本身不保证时延收益。
- [AICPU Scheduler（值依赖分核下沉 ARM 核）](aicpu_scheduler.md)：AICPU Scheduler 将稀疏注意力 SAS、LightningIndexer 等值依赖算子的分核策略从 Host 或主 AICore 下沉到芯片内 AICPU，生成可复用 metadata，避免 Host 往返或在主核内计算分核打断流水。流程拆成两段：Host 根据 shape 计算最大 workspace、tiling key、block dim 和静态 tiling data；AICPU 再结合 actualSeqLengths 等运行时值完成具体分核。DeepSeek-V4 通过三个 custom metadata 算子覆盖 SAS 非量化、SAS KV 伪量化和量化 LI，并可用独立 metadata stream 掩盖开销。它适合需要入图且分核依赖运行时值的场景；与 V3.2-Exp 将 LI 分核融入 AICore 主算子的机制不同，两者不存在已证实的取代关系。
- [CANN SHMEM 通信编程模型](cann_shmem.md)：CANN SHMEM 是面向昇腾多设备的共享地址空间通信模型，以 OpenSHMEM 风格 Host/Device 接口支持跨设备访存和通算融合。它提供 NPU HBM 与 CPU DDR 混合编址、对称内存及 put/get/signal/wait/barrier 等原语；通信域各卡共享虚拟地址，单 die 对称区总量不超过 1 GiB，状态区紧随数据区。基础层使用 MTE/xDMA 处理 D2D/D2H，HIXL 则通过 SDMA 访问远端 DRAM，二者不可混为同一路径。典型用途包括 KV Cache Offload、MoE Dispatch/Combine 和 HIXL 单边通信，可由原生 API、pyPTO 或 TileLang 接入。运行时实现位于外部 cann/shmem 仓，本卡 API 以固定 guide 为依据。
- [DiT Cache (FBCache / TeaCache / TaylorSeer)机制](dit_cache.md)：DiT 的 step-level 缓存通过复用或预测减少重复去噪计算；本卡解释判据、SP 一致性与 CFG 状态隔离，模型配置和来源性能分别引用规范入口。
- [MoE Double-Routing机制](double_routing.md)：DeepSeek-R1 / Kimi-K2 等大 EP MoE 模型在 Prefill 阶段使用的专家路由方案。每张卡完成 **两轮路由与两轮顺序恢复（末轮调用一次 npu_moe_finalize_routing）**：第一次做本卡内按专家排序 + 通过 AllToAll+ReduceSum 推导 `input_splits` / `output_splits`；token AllToAll 之后再做一次 re-routing 让本卡 token 按本地专家再次排序。相较 AllGather 全量方案，Double-Routing 在负载较均衡时**峰值显存更低**（无数据冗余）且**通信量更小**。
- [HIXL（Huawei Xfer Library 单边零拷贝通信库）](hixl.md)：HIXL 是基于 SHMEM 全局统一编址的昇腾单边通信库，主要解决超长序列推理将 KV Cache 卸载到 CPU DRAM 后的 Device→Remote Host PUT 与 Remote Host→Device GET。它通过 SDMA 直接访问对端 DRAM，无需对端进程参与或内核态中转，并屏蔽 HCCS、RoCE 等链路差异。vLLM 侧选择 Mooncake 后端且 protocol=ascend 时调用 HIXL；依赖 libcann_hixl.so、libllm_datadist.so，并需 Mooncake 以 USE_ASCEND_DIRECT 构建。HCCS IPC 缓冲区基址要求 2 MiB 对齐，RoCE 无此约束；默认 memfabric 后端不使用 HIXL。Mooncake 接入行为依据封装代码；HIXL 内部机制依据 guide 文档，未作源码级验证。
- [InferenceConfig（统一推理配置体系）](inference_config.md)：InferenceConfig 是 CANN Executor 新推理链路的 dataclass 配置入口，聚合 Data、Model、Parallel、Scheduler、Disagg 五类配置并自动校验。关键推导为 attn_dp_size=world_size/(attn_tp_size×cp_size)、batch_size_per_dp_rank=batch_size/attn_dp_size；max_prefill_tokens 为 0 时由 input_truncated_len×batch_size_per_dp_rank 生成。DisaggConfig 由服务端构造，支持 NONE/PREFILL/DECODE 及 memfabric、mooncake 后端。该体系仅适用于 executor/offline/infer.py；legacy model_runner.py 仍使用 runner_settings、input_max_len 和 kvp_size，旧模型 YAML 不能按新字段解释。文档曾漏掉 cp_size，以代码公式为准。
- [KVCache Offload机制](kvcache_offload.md)：容量型 Offload（DeepSeek-V3.2-Exp）：把 MLA Full KVCache 卸载到 Host 内存，Prefill 复用一层临时 Full KV 缓冲，Decode 另有逐层 selection KVCache，释放 HBM 以容纳更大的 batch 或更长的序列。Decode 阶段借助 Lightning Indexer TopK + GatherSelectionKvCache 算子，利用前后 Token 命中率复用设备端 cache，缓解 H2D 带宽压力。 时间型 Offload（HSTU）：不改变 KV 存放位置（目标仍是 Host/外存），而是把每层 KV offload 的触发时机从"HSTU dense 完成后统一执行"前移到"每层 Attention 结束立即触发"，并切到一条独立 NPU stream 异步执行，从而让 offload 通信与 HSTU dense/MLP 计算在时间轴上重叠，降低流水线空泡。
- [MoE Dispatch/Combine V2（一体化融合算子）](moe_dispatch_combine_v2.md)：torch_npu.npu_moe_distribute_dispatch_v2 / npu_moe_distribute_combine_v2（仓内文档亦称 MC2 路由）把 MoE 专家并行的 All-to-All dispatch / combine 路由通信收敛为两个一体化融合算子（专家 GroupedMatmul 仍位于两者之间独立执行）：dispatch_v2 按路由分发 token 到专家所在 rank 并按专家重排，combine_v2 按逆映射退还并加权融合。相比手写 init_routing_v2 重排 + all_to_all_single + finalize_routing（即 double-routing），把发送/状态同步/重排封装在单算子内，减少 host 下发与 kernel 启动，适合纯 EP Decode（moe_ep_size>1 且 moe_tp_size==1）小 batch 低时延场景。主要使用方（grep 实证、非穷举）：R1 / Kimi-K2 / Qwen3-MoE / Qwen3.5-MoE / DeepSeek-V3.2-Exp / LongCat-Flash(-Lite) / DeepSeek-V4 / Gemma-4 / Hy3-preview；A2 受 experts_per_rank≤24 限制、A3 无此限。配套 HCCL_BUFFSIZE / HCCL_OP_EXPANSION_MODE=AIV 调优。MC2 使用独立 HCCL 通信域 moe_ep_group_mc2（与 EP 的 moe_ep_group 解耦）+ 独立 buffer（calc_moe_hccl_buffer_size is_full_mesh_v2=True）+ fullmesh_v2 模式（dispatch_kwargs comm_alg=fullmesh_v2，见 R1/Kimi/V3.2/glm-5/qwen3_moe/V4）；fullmesh_v2 不支持零专家，故带 copy_expert_num 的 LongCat-Flash 仍切独立域但不置 comm_alg=fullmesh_v2。
- [MoE 多流（MoE Multi-Stream）：共享专家旁路与 ScMoE 分支](moe_multi_stream.md)：MoE Multi-Stream 将共享专家与路由专家或 ScMoE 双分支放到多条 NPU stream 并行；解释 Shared + Routed Overlap 与 ScMoE Stream Switch + Core Limit，按对应规则核对条件、同步和回退。
- [MTP Speculative Decoding](mtp_speculative_decoding.md)：解释 MTP 的 draft、主模型验证与接受前缀机制；接入接口、缓存策略和计时指标分别链接规范入口，模型与版本限制不相互外推。
- [NPU 多流机制：资源互补、Stream 与 Event](multi_stream.md)：解释 NPU 资源、流与事件的基本机制及三类并行形态；具体 API、实施步骤、控核和验收分别由规则与指南维护。
- [NPU 图模式（ge_graph / npugraph_ex）](npu_graph_mode.md)：解释 GE 编译与 npugraph_ex 捕获重放两条执行路径；阶段路由和配置限固定版本，选型、实施、排障及未核实观测分别链接对应入口。
- [权重在线切分（Online Split Weight）](online_weight_split.md)：权重在线切分指模型加载时由系统自动将对应权重分发到各个 Device，**无需预先离线处理**，从而避免额外磁盘存储开销、提升调试效率、降低磁盘占用。cann-recipes-infer 在 `module/Linear.py`、`module/fuse_moe_gmm.py` 提供了统一的在线切分 Linear / Embedding / MoE GMM 类，并在各模型的 `modeling_*.py` 中通过 `load_weights` 函数做 checkpoint 权重名 → 模型参数名的匹配与分发。 在线切分的核心机制：**每个相关模块在加载权重时获得当前 device 需要加载的权重切片位置**——根据 TP/EP 维度，从原始完整权重中 slice 出本卡分片，直接写入模块参数，跳过全局磁盘中转。
- [Prefill 微批次双流机制](prefill_micro_batch.md)：解释 Prefill 微批次的计算/通信流水与事件依赖；实现步骤和来源性能分别引用 Guide 与观测，不保证所有负载均能获益。
- [Ring Attention Overlap](ring_attention_overlap.md)：多卡 Ring Attention 的 P2P / AllGather 通信通常与 FA 计算串行，利用率低。Wan2.2-I2V 在此基础上做了**计算-通信掩盖**：异步启动 AllGather 收集远端 KV 的同时，立即用本地 KV 算第一次 FA；AllGather 完成后把远端多个 chunks 合并为一段长序列一次性算第二次 FA；最后用 LSE（Log-Sum-Exp）合并两次输出。实现代码见 `module/unified_sp/core.py`。
- [基于 SHMEM 重写的 MoE Dispatch&Combine](shmem_dispatch_combine.md)：MoE Dispatch 按路由将 token 发往专家所在 rank，Combine 再按逆映射返回并按权重聚合结果。本方案用 CANN SHMEM 对称 win 区和 put/signal/wait 语义，将两者显式编排为发送数据、发送状态、等待状态、本地拷贝四步；Dispatch 还记录来源 rank、token 和 top-k 序号供 Combine 原路返回。guide 给出原生 SHMEM、TileLang-shmem 与 pyPTO-shmem 三种实现，均依赖独立数据区和状态区。它适用于 MoE EP All-to-All 通算融合，但不同于 HCCL double-routing，也不同于将通信封装在 npu_moe_distribute_dispatch_v2/combine_v2 内的融合算子。当前 DeepSeek-V4 生产模型仍调用 torch_npu 融合算子，SHMEM 重写仅为文档级开发示例，未验证独立 cann/shmem 运行时的实际执行行为。
- [SuperKernel机制](superkernel.md)：TorchAir `ge_graph`（max-autotune）图模式下，**按用户声明的 scope 优化计算融合与任务调度** 的优化能力。目标是减少算子间任务调度的等待时间与下发开销，尤其针对 Decode 阶段大量细碎算子（MLA prolog、FA、MoE dispatch/combine、GroupedMatMul、finalize 等）叠加时的 host 下发与调度开销。 在 DeepSeek-R1 Decode W8A8C8 + MTP1 的 benchmark YAML (`decode_r1_rank_128_128ep_a8w8c8_mtp_benchmark.yaml`) 中默认 `enable_superkernel: True`。
- [weightNZ Format机制](weight_nz.md)：将 Matmul 类算子的权重 Tensor 转成昇腾 NPU 亲和的 **NZ 分形布局**（512 字节对齐），提升硬件访存带宽效率，加速 DeepSeek-R1 等模型的 Prefill / Decode Matmul 计算。由 YAML `enable_weight_nz: True` 使能，模型加载阶段由 各模块 `quant_method.process_weights_after_loading` 执行 NZ 转换；`convert_model.py` 负责权重量化转换。
- [Weight Prefetch (npu_prefetch)机制](weight_prefetch.md)：权重预取利用前序计算的带宽窗口提前搬运后续权重，解释缓存与依赖机制；调试规则、LongCat 参数和 AFD 故障入口分别引用规范卡。
