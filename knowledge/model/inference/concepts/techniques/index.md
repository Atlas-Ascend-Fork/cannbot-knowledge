# 优化技术

- [Attention-FFN Disaggregation (AFD)](afd.md)：Attention-FFN Disaggregation (AFD) 是 LongCat-Flash 模型在 Decode 阶段的**部署级解耦**优化：将 Attention 模块与 MoE (FFN) 模块**部署在不同的节点**上，中间通过 Send/Recv 算子进行节点间的数据交互。相比把 Attention 与 MoE 部署在同一张卡 + 多流 + 控核方案，AFD 解除了双流共享 Cube/Vector 核数的约束，Attention 侧算子不再控核后耗时大幅下降。 实测在 W8A8 + GBS=256 + Seq=4608 + 64 Chips + MTP2 + perfect eplb 场景下，AFD TPOT **9.5 ms**（相对同配置不分离 9.95 ms），且吞吐由 402.01 → 421.05 tokens/p/s，是 LongCat-Flash **TPOT 进入 10 ms 内**的关键优化。
- [AICPU Scheduler（值依赖分核下沉 ARM 核）](aicpu_scheduler.md)：AICPU Scheduler 将稀疏注意力 SAS、LightningIndexer 等值依赖算子的分核策略从 Host 或主 AICore 下沉到芯片内 AICPU，生成可复用 metadata，避免 Host 往返或在主核内计算分核打断流水。流程拆成两段：Host 根据 shape 计算最大 workspace、tiling key、block dim 和静态 tiling data；AICPU 再结合 actualSeqLengths 等运行时值完成具体分核。DeepSeek-V4 通过三个 custom metadata 算子覆盖 SAS 非量化、SAS KV 伪量化和量化 LI，并可用独立 metadata stream 掩盖开销。它适合需要入图且分核依赖运行时值的场景；与 V3.2-Exp 将 LI 分核融入 AICore 主算子的机制不同，两者不存在已证实的取代关系。
- [CANN SHMEM 通信编程模型](cann_shmem.md)：CANN SHMEM 是面向昇腾多设备的共享地址空间通信模型，以 OpenSHMEM 风格 Host/Device 接口支持跨设备访存和通算融合。它提供 NPU HBM 与 CPU DDR 混合编址、对称内存及 put/get/signal/wait/barrier 等原语；通信域各卡共享虚拟地址，单 die 对称区总量不超过 1 GiB，状态区紧随数据区。基础层使用 MTE/xDMA 处理 D2D/D2H，HIXL 则通过 SDMA 访问远端 DRAM，二者不可混为同一路径。典型用途包括 KV Cache Offload、MoE Dispatch/Combine 和 HIXL 单边通信，可由原生 API、pyPTO 或 TileLang 接入。运行时实现位于外部 cann/shmem 仓，本卡 API 以固定 guide 为依据。
- [DiT Cache (FBCache / TeaCache / TaylorSeer)](dit_cache.md)：DiT-Cache 是扩散生成模型推理加速的 Step-level 缓存框架：**利用相邻采样 step 间输出变化平滑的性质，复用或预测上一步的残差**，以跳过当前 step 的完整前向计算。本仓实现位于 `module/dit_cache/cache_method.py`（HunyuanVideo 使用）与 `module/dit_cache_step/cache_step.py`（Wan2.2-I2V 使用），支持三种范式：**FBCache**（First-Block L1 误差判据）、**TeaCache**（Timestep Embedding Modulated Noisy Input L1 距离 + 多项式 rescale 判据）、**TaylorSeer**（泰勒级数预测）。HunyuanVideo 上实测 FBCache 2.12×、TeaCache 2.06×、TaylorSeer 2.51× 端到端。
- [MoE Double-Routing](double_routing.md)：DeepSeek-R1 / Kimi-K2 等大 EP MoE 模型在 Prefill 阶段使用的专家路由方案。每张卡完成 **2 次 init-routing + 2 次 finalize-routing**：第一次做本卡内按专家排序 + 通过 AllToAll+ReduceSum 推导 `input_splits` / `output_splits`；token AllToAll 之后再做一次 re-routing 让本卡 token 按本地专家再次排序。相较 AllGather 全量方案，Double-Routing 在负载较均衡时**峰值显存更低**（无数据冗余）且**通信量更小**。
- [HIXL（Huawei Xfer Library 单边零拷贝通信库）](hixl.md)：HIXL 是基于 SHMEM 全局统一编址的昇腾单边通信库，主要解决超长序列推理将 KV Cache 卸载到 CPU DRAM 后的 Device→Remote Host PUT 与 Remote Host→Device GET。它通过 SDMA 直接访问对端 DRAM，无需对端进程参与或内核态中转，并屏蔽 HCCS、RoCE 等链路差异。vLLM 侧选择 Mooncake 后端且 protocol=ascend 时调用 HIXL；依赖 libcann_hixl.so、libllm_datadist.so，并需 Mooncake 以 USE_ASCEND_DIRECT 构建。HCCS IPC 缓冲区基址要求 2 MiB 对齐，RoCE 无此约束；默认 memfabric 后端不使用 HIXL。本卡只核对 Mooncake 接入封装，HIXL 库本体仍以外部仓为准。
- [InferenceConfig（统一推理配置体系）](inference_config.md)：InferenceConfig 是 CANN Executor 新推理链路的 dataclass 配置入口，聚合 Data、Model、Parallel、Scheduler、Disagg 五类配置并自动校验。关键推导为 attn_dp_size=world_size/(attn_tp_size×cp_size)、batch_size_per_dp_rank=batch_size/attn_dp_size；max_prefill_tokens 为 0 时由 input_truncated_len×batch_size_per_dp_rank 生成。DisaggConfig 由服务端构造，支持 NONE/PREFILL/DECODE 及 memfabric、mooncake 后端。该体系仅适用于 executor/offline/infer.py；legacy model_runner.py 仍使用 runner_settings、input_max_len 和 kvp_size，旧模型 YAML 不能按新字段解释。文档曾漏掉 cp_size，以代码公式为准。
- [KVCache Offload](kvcache_offload.md)：容量型 Offload（DeepSeek-V3.2-Exp）：把 MLA Full KVCache 卸载到 Host 内存，设备仅留一层 cache，释放 HBM 以容纳更大的 batch 或更长的序列。Decode 阶段借助 Lightning Indexer TopK + GatherSelectionKvCache 算子，利用前后 Token 命中率复用设备端 cache，缓解 H2D 带宽压力。 时间型 Offload（HSTU）：不改变 KV 存放位置（目标仍是 Host/外存），而是把每层 KV offload 的触发时机从"HSTU dense 完成后统一执行"前移到"每层 Attention 结束立即触发"，并切到一条独立 NPU stream 异步执行，从而让 offload 通信与 HSTU dense/MLP 计算在时间轴上重叠，降低流水线空泡。
- [MoE Dispatch/Combine V2（一体化融合算子）](moe_dispatch_combine_v2.md)：torch_npu.npu_moe_distribute_dispatch_v2 / npu_moe_distribute_combine_v2（仓内文档亦称 MC2 路由）把 MoE 专家并行的 All-to-All dispatch / combine 路由通信收敛为两个一体化融合算子（专家 GroupedMatmul 仍位于两者之间独立执行）：dispatch_v2 按路由分发 token 到专家所在 rank 并按专家重排，combine_v2 按逆映射退还并加权融合。相比手写 init_routing_v2 重排 + all_to_all_single + finalize_routing（即 double-routing），把发送/状态同步/重排封装在单算子内，减少 host 下发与 kernel 启动，适合纯 EP Decode（moe_ep_size>1 且 moe_tp_size==1）小 batch 低时延场景。主要使用方（grep 实证、非穷举）：R1 / Kimi-K2 / Qwen3-MoE / Qwen3.5-MoE / DeepSeek-V3.2-Exp / LongCat-Flash(-Lite) / DeepSeek-V4 / Gemma-4 / Hy3-preview；A2 受 experts_per_rank≤24 限制、A3 无此限。配套 HCCL_BUFFSIZE / HCCL_OP_EXPANSION_MODE=AIV 调优。MC2 使用独立 HCCL 通信域 moe_ep_group_mc2（与 EP 的 moe_ep_group 解耦）+ 独立 buffer（calc_moe_hccl_buffer_size is_full_mesh_v2=True）+ fullmesh_v2 模式（dispatch_kwargs comm_alg=fullmesh_v2，见 R1/Kimi/V3.2/glm-5/qwen3_moe/V4）；fullmesh_v2 不支持零专家，故带 copy_expert_num 的 LongCat-Flash 仍切独立域但不置 comm_alg=fullmesh_v2。
- [MoE Multi-Stream](moe_multi_stream.md)：Shared + Routed Overlap 变体（Qwen3-Next / Qwen2-MoE / DeepSeek-R1 Decode / DeepSeek-V3.2-Exp / Kimi-K2-Thinking / HunyuanImage-3.0）：shared-expert 的 gate_up_proj/act_fn/down_proj 放在独立 stream，与主 stream 上的 topk → dispatch → GroupedMatMul → combine 重叠。 ScMoE Stream Switch + Core Limit 变体（LongCat-Flash）：ScMoE 双段 "Attention → FFN → Attention → MoE" 结构里，把第二段 Attention 与 FFN 提前到与 MoE 并行，通过 npu_stream_switch("1") 与 limit_core_num 联合限定每条 stream 占用的 Cube/Vector Core（stream0 c16v32、stream1 c8v16），使双流计算时间接近，无明显拖尾。
- [MTP Speculative Decoding](mtp_speculative_decoding.md)：Multi-Token Prediction (MTP) 投机推理：主模型一次前向同时验证多个 draft token（MTP1 = 2 个 draft token），在相近的 HBM 搬运量下做更多算术运算，充分利用 Decode 阶段剩余的算力水位，降低等效 per-token 时延并提升吞吐。 cann-recipes-infer 中有两条落地路径： - **Qwen3-Next**：SGLang 的 `NEXTN` 投机算法 + AscendC `recurrent_gated_delta_rule` 融合算子的 `num_accepted_tokens` 接口（针对 GDN 线性注意力的 ssm_state 选择性回写）。 - **DeepSeek-R1**：自研 executor 的 MTP 实现，通过 `next_n` 参数使能；MLA 端通过 `npu_fused_infer_attention_score_v2` 的 `sparse_mode=3` 切换 MTP 因果 mask；KV 按 `speculative_num_draft_tokens` 连续布局；无 ssm_state 语义因而不需 num_accepted_tokens 回写。`DeepseekV3ModelMTP` / `DeepseekV3ModelMTPLayer` 承担 MTP layer。
- [NPU 多流优化(Multi-Stream)](multi_stream.md)：多流优化是把一个模块/算子序列里彼此无 data 依赖、可并行的子计算或通信段分配到多条 NPU stream 上重叠执行，用一条流的耗时去掩盖另一条流的耗时，从而在不增加算力的前提下缩短关键路径。它是 cann-recipes-infer 在 MoE / Attention 前处理 / KVCache 搬运 / Prefill micro-batch / 分离式通信等多个场景里反复使用的一类优化骨架。
- [NPU 图模式（ge_graph / npugraph_ex）](npu_graph_mode.md)：Pytorch 默认 `eager` 模式"边解释边执行"，逐算子下发 Device，推理场景容易暴露 Host 侧下发开销（**host bound**）。图模式通过 `torch.compile` 把前向逻辑捕获成图、交给 NPU 后端编译执行，**减少 Host 下发开销，允许后端在更大范围做融合、内存复用、调度优化**，显著降低 decode 时延。 NPU 图模式有两种实现路径：**GE 图模式**（FX → Ascend IR → GE 引擎编译）与 **npugraph_ex**（基于 npugraph capture & replay，强调下沉调度与低开销执行）。历史代码里的 `acl_graph` 命名对应当前 `npugraph_ex`，**将逐步废弃**。 cann-recipes-infer 通过 cann-executor 的 `model_config.exe_mode` 配置开关，图模式开关**仅对 decode 生效**，prefill 统一走 eager——prefill shape/控制流动态变化，容易断图或重编译，且单次算子执行更长、下发 bound 不突出。
- [权重在线切分（Online Split Weight）](online_weight_split.md)：权重在线切分指模型加载时由系统自动将对应权重分发到各个 Device，**无需预先离线处理**，从而避免额外磁盘存储开销、提升调试效率、降低磁盘占用。cann-recipes-infer 在 `module/Linear.py`、`module/fuse_moe_gmm.py` 提供了统一的在线切分 Linear / Embedding / MoE GMM 类，并在各模型的 `modeling_*.py` 中通过 `load_weights` 函数做 checkpoint 权重名 → 模型参数名的匹配与分发。 在线切分的核心机制：**每个相关模块在加载权重时获得当前 device 需要加载的权重切片位置**——根据 TP/EP 维度，从原始完整权重中 slice 出本卡分片，直接写入模块参数，跳过全局磁盘中转。
- [Prefill Micro-Batch (Dual-Stream Overlap)](prefill_micro_batch.md)：DeepSeek-R1 Prefill 阶段的计算/通信重叠技术。将输入拆成 2 个 micro-batch，在主计算流与副通信流之间构造双流水线，让 MoE 的 dispatch / combine AllToAll 被下一/上一 micro-batch 的计算完全掩盖。源文档 `docs/models/deepseek-r1/deepseek_r1_prefill_optimization.md` 在 Atlas A3 2 机环境下实测相对非 micro-batch 提升 **25%**（5237 → 6522 tokens/卡/s）。
- [Ring Attention Overlap](ring_attention_overlap.md)：多卡 Ring Attention 的 P2P / AllGather 通信通常与 FA 计算串行，利用率低。Wan2.2-I2V 在此基础上做了**计算-通信掩盖**：异步启动 AllGather 收集远端 KV 的同时，立即用本地 KV 算第一次 FA；AllGather 完成后把远端多个 chunks 合并为一段长序列一次性算第二次 FA；最后用 LSE（Log-Sum-Exp）合并两次输出。实现代码见 `module/unified_sp/core.py`。
- [基于 SHMEM 重写的 MoE Dispatch&Combine](shmem_dispatch_combine.md)：MoE Dispatch 按路由将 token 发往专家所在 rank，Combine 再按逆映射返回并按权重聚合结果。本方案用 CANN SHMEM 对称 win 区和 put/signal/wait 语义，将两者显式编排为发送数据、发送状态、等待状态、本地拷贝四步；Dispatch 还记录来源 rank、token 和 top-k 序号供 Combine 原路返回。guide 给出原生 SHMEM、TileLang-shmem 与 pyPTO-shmem 三种实现，均依赖独立数据区和状态区。它适用于 MoE EP All-to-All 通算融合，但不同于 HCCL double-routing，也不同于将通信封装在 npu_moe_distribute_dispatch_v2/combine_v2 内的融合算子。当前 DeepSeek-V4 生产模型仍调用 torch_npu 融合算子，SHMEM 重写仅为文档级开发示例，外部 cann/shmem 运行时未在本仓核验。
- [SuperKernel](superkernel.md)：TorchAir `ge_graph`（max-autotune）图模式下，**按用户声明的 scope 将计算子图整体融合为单个大 kernel** 的优化能力。目标是减少算子间任务调度的等待时间与下发开销，尤其针对 Decode 阶段大量细碎算子（MLA prolog、FA、MoE dispatch/combine、GroupedMatMul、finalize 等）叠加时的 host 下发与调度开销。 在 DeepSeek-R1 Decode W8A8C8 + MTP1 的 benchmark YAML (`decode_r1_rank_128_128ep_a8w8c8_mtp_benchmark.yaml`) 中默认 `enable_superkernel: True`。
- [weightNZ Format](weight_nz.md)：将 Matmul 类算子的权重 Tensor 转成昇腾 NPU 亲和的 **NZ 分形布局**（512 字节对齐），提升硬件访存带宽效率，加速 DeepSeek-R1 等模型的 Prefill / Decode Matmul 计算。由 YAML `enable_weight_nz: True` 使能，模型加载阶段由 `convert_model.py` 对权重做一次性离线/在线转换。
- [Weight Prefetch (npu_prefetch)](weight_prefetch.md)：该优化提供网络 weight 预取功能，在算子计算的同时，**利用空闲的带宽，提前将一些访存 bound 算子的权重从 HBM 搬运到 L2 Cache 中**，提升算子性能。`npu_prefetch` 技术的详细介绍，请参考 官方文档。LongCat-Flash 通过 `enable_prefetch` 开关使能该优化。
