# GMM1 双累加器预算反例：512 列 fp32 在 256KiB L0C 下已满

## 适用场景

针对报告中两个部分和同时驻留的 GMM1 设计前提做预算核算；256KiB、512 列等均为待在目标实现确认的参数，不是本卡测得的设备容量。

## 触发与观测

设计报告使用了不同的列宽预算前提；在讨论双通道前先明确同时存活的张量形状。

## 探针与操作

先按 dtype、行列形状和深度计算基线，再计算所有同时存活通道的总量；不要只计算新增通道。

固定前提下的完整预算计算：

```text
L0C budget = 262144 B
baseline = 128 * 512 * 4 = 262144 B
extra = 16 * 512 * 4 = 32768 B
total = 294912 B > 262144 B
```

## 机制与判别

在这里的预算前提下，128×512×4=262144B，额外 16×512×4=32768B，总量 294912B 超过 256KiB。改变为每半 256 列需要重审循环嵌套、数据搬运与 FIFO，不是只修改声明。

## 验证信号

本次 CPU 算术检查得到基线 262144B、新增 32768B、合计 294912B。原轨迹中的回滚与 L0/L1 通过仅出自子 Agent 报告，没有绑定直接测试返回，本卡不采用这些验收声明。

## 适用与失效边界

只否定当前同时驻留的双通道形态。若平台预算、dtype 或循环重排改变，需重新计算；本卡不把单个平台预算扩展到所有芯片。
