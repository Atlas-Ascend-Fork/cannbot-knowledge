# 标量写 UB 后 MTE3 回写旧值的缓存可见性排查

## 适用场景

标量写入 UB 后，后续 MTE3 搬运是否能看到新值，需要结合标量访问模式、缓存状态和流水依赖判断。仅增加计算流水屏障，不能据此证明缓存副本已经写回。

## 症状与记录

CANN 9.3、dav-3510 的整数 TopK 实现中，曾出现索引正确而 int8、int32、uint8 输出值错误。把选择过程改为 GM→UB 后错误减少；在标量写 UB 与 DMA 回写之间加入 `asc_ub_dcci_single` 相关缓存维护后，记录的两组公开用例各为 20/20 通过。这是诊断线索，不代表所有标量 UB 写都需要同一套指令。

## 定位与处理

1. 将排序选择与回写拆开：标量生成已知序列到 UB，单独用原 MTE3 路径写回，同时检查值和索引。
2. 固定地址、长度和搬运参数，只改变缓存维护步骤，对比错误是否消失。
3. 查明当前标量访问是否使用 DCache，再按目标版本确认 DCCI 的作用、覆盖单位和完成等待方式，建立 Scalar→MTE3 的依赖。
4. 若使用单行维护接口，计算整个写入范围覆盖的缓存行；不能把对首地址的一次调用视为整段刷新。失效操作之前也必须确认脏数据的处理语义。

`asc_mem_bar(VST_VLD)` 处理的依赖与标量缓存维护不同。把 VF 内存屏障搬到任意标量位置，不能替代上述诊断。

## 验证边界

使用跨缓存行、非整块尾部、多次复用 UB 的用例；比较无维护、维护且等待完成两条路径。分别记录编译、精度和性能，不以增加屏障后的偶然通过归因。草稿：上述观测尚待目标环境独立复核，未声明性能收益。
