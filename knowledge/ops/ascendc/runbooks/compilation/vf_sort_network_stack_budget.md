# VF 排序网络栈超限时缩小同时存活的寄存器集合

## 适用场景

小规模排序网络也可能在 VF 内产生过大的同时存活集合。源码中的键数、临时数组大小与最终栈消耗不是同一个量，应以目标编译器的栈对象诊断为准。

## 症状与记录

CANN 9.3、dav-3510 的整寄存器排序网络候选出现 `total stack object size 23392` 超过 `vf stack 6144` 的编译错误。另一组 32-key 原型请求 10816 字节；改为只保持 8 个活跃键并在 UB 中分阶段处理后，记录中编译成功且完成 706 项检查。这些数字属于具体候选，不是“最多允许 8 个键”的硬件规则。

## 定位与处理

1. 记录失败 VF 的栈需求和当前编译选项，排除把整个 kernel 的 UB 预算当作 VF 栈预算。
2. 缩减一阶段内同时存活的键、索引和比较交换临时量；分阶段载入、处理、写回 UB。
3. 逐个增加网络宽度和展开阶段，观察栈需求的变化；只缩短变量声明的代码距离不保证编译器缩短其存活期。
4. 对新增 UB 交接显式核对地址、尾掩码与生产消费顺序。

## 验证边界

分阶段方案须重新检查稳定的值索引配对、相同值处理、全范围整数键及尾块。栈需求下降不证明性能改善；额外 UB 搬运需单独测量。不把释放 VF 栈预留的编译开关当作超限修复。草稿：尚待当前工具链复核。
