# 性能优化策略：Host 调用层开销消除（逻辑下沉 kernel 与同步/分配收敛）

> 单一优化点：算子的 host 层（torch plugin / op_api）若存在**随调用次数或张量规模线性放大的 host 侧工作**——逐元素/逐调用的阻塞同步、全张量扫描、逐元素设备内存分配/清零/释放、host 侧可下沉 kernel 的逻辑计算——端到端时间会被这些调用层开销主导，常常**比 kernel 本身还长**。把这些开销消除或收敛：能下沉 kernel 的下沉 kernel，必须在 host 做的按规模门控跳过或整批收敛为单次执行。

**融合来源**：本卡由原 `18-host-reduce-sync-gate`（host 全张量扫描+强制同步按元素数门控）与原 `19-list-workspace-reuse-single-sync`（列表逐元素分配/同步/释放改整列表复用+单次尾部同步）融合而成；两者是同一泛化模式（host 调用层逐次开销 → 门控跳过 / 整批收敛）的两个实例。

---

## 1. 原理

**问题泛型**：host 驱动代码中存在"每次调用（或每个列表元素）都执行"的高成本动作，可分为三类：

1. **强制同步类**：`torch.isnan(x).any().item()`、`.any().item()`、`.max().item()` 等会触发全张量 NPU kernel + CPU/NPU 阻塞同步；大 shape 下这是端到端最大单一开销。
2. **逐元素分配/同步/释放类**：host 循环对列表每个元素「分配设备内存 + 清零 + 阻塞同步 + 释放」，逐元素阻塞同步把设备流水线在元素之间排空（设备空转），分配/释放落在 host 热路径线性叠加。
3. **host 侧逻辑计算类**：本可在 kernel 内完成的判断、扫描、修正逻辑放在 host 层做，每调用一次就付一次全量扫描 + 同步的代价。

**三种消除手段**（按优先级）：

- **下沉 kernel（首选）**：host 层的检测/判断/修正逻辑若能改为 kernel 内执行（或编译期常量折叠），直接消除 host→device 的往返与同步。逻辑操作放于 kernel 执行，不在调用层计算。
- **按规模门控跳过**：必须在 host 做的保正确路径（NaN/inf/越界检测、动态形状判定），若只对少数小合成 case 真正需要、大 shape 输入实际无该特殊情况，则按元素数门控：仅小张量走扫描+同步，大张量信任输入直接跳过。门控阈值取 2 的幂（如 3×1024×1024），避免与某个 case 的 numel 恰好相等命中 `<=`。
- **整批收敛为单次**：列表/序列各元素相互独立、所有 launch 在同一条流上时，整列表只分配一块暂存区（容量按最大单元素需求取齐），所有元素的 launch 背靠背提交，仅在末尾做**一次** host 同步与一次释放。流顺序天然保证「元素 N 的消费者在元素 N+1 的生产者开始前完成」，各元素复用同一暂存区无槽位竞争。

## 2. 性能问题模式

满足以下模式（任一）时考虑本策略：

1. host 层存在每次调用都执行的全张量扫描 + `.item()` 强制同步（NaN 检测、越界检查、动态形状判定），大 shape 端到端时间被其主导。
2. host 驱动循环对列表/序列逐元素「分配 + 清零 + … + 阻塞同步 + 释放」；墙钟随元素数近似线性增长，单元素耗时里有一大块与数据量无关的固定 host 开销；设备在元素之间出现空转间隙。
3. host 层存在可用 kernel 内逻辑替代的判断/修正分支（每次调用都付 host 计算代价）。
4. profiling（端到端 vs 纯 kernel 时间）显示 host 侧开销占比高：端到端 ≫ kernel 执行时间，差值随 shape 或元素数线性增长。

## 3. 正确性红线

- **门控跳过即「信任输入」**：若大输入真含特殊值（NaN/inf），结果不再被 host 修正——仅适合特殊值由合成 case 控制而非真实数据的场景；门控前必须确认全部带特殊值的 case 都落在阈值内。
- **阈值取 2 的幂**：避免与某 case 的 numel 恰好相等命中 `<=`（实例：阈值 4M 曾被 numel=4×1024×1024 的 case 误命中）。
- **暂存区容量**：整批复用时必须 ≥ 任一单元素的需求（按最大元素取齐），否则越界。
- **流顺序前提**：整批收敛要求所有 launch 在同一条流上；若消费者读取的槽位范围大于生产者写入范围，需保留显式清零或保证消费者只读被覆写范围。
- **生命期**：尾部同步必须在释放前执行（暂存区生命期覆盖所有 kernel）；某元素因 dtype/形状不支持需提前返回时，必须先完成已分配暂存区的同步与释放再抛错。
- **下沉 kernel 的语义等价**：host 逻辑下沉后，kernel 内分支的结果必须与原 host 修正逐 case 一致（含特殊值 case）。

## 4. 泛化条件

适用（任一）：
- host 层有「全张量 reduce → .item() 强制同步」的保正确路径，且该检测只对少数小 case 真正需要。
- host 驱动按列表逐元素分配/同步/释放暂存区，各元素相互独立、同一条流、生产者完整覆写自己槽位。
- host 层存在可下沉 kernel 的逐调用逻辑计算（判断/扫描/修正）。

不适用（任一）：
- host 检测对全部 case 都必须真实执行（真实数据可能含特殊值，不能信任输入）——应下沉 kernel 而非跳过。
- 列表元素间存在真依赖、需跨元素读写同一暂存区且无流顺序保证（需显式同步，不能简单复用）。
- 暂存区需求随元素数线性增长且总量超出可分配范围（需分批）。

## 5. 实施步骤

1. **定位 host 开销**：审查 plugin/op_api 层，找出每次调用（或每元素）执行的同步、扫描、分配、逻辑计算；用「端到端 − 纯 kernel 时间」量化 host 占比。
2. **分类选择手段**：
   - 可下沉 kernel 的逻辑 → 改写为 kernel 内执行/编译期判定；
   - 必须在 host 的保正确扫描 → 加元素数门控（阈值取 2 的幂，覆盖全部特殊值 case）；
   - 逐元素分配/同步/释放 → 整列表单块暂存 + 背靠背 launch + 单次尾部同步/释放。
3. **实施下沉/门控/收敛**：保持 kernel 调用参数与原实现一致（仅暂存区指针/分支位置改变）；门控仅改变执行位置，不改变数值路径。
4. **全量编译**，精度全部通过（与改前逐 case 一致，含特殊值/小合成 case），多次取样性能。
5. 重点核对：大 shape 的 host 扫描+同步是否消失、多元素 case 的设备空转间隙是否消除；改善超噪声且精度过则采纳，否则回退。

## 6. LLM 前置问题

- host 层每次调用执行了哪些同步/扫描/分配？哪些可下沉 kernel、哪些必须留在 host？
- 保正确检测是否只对少数小 case 需要？全部特殊值 case 的 numel 是否都落在门控阈值内？阈值是否取 2 的幂？
- 列表各元素是否相互独立？所有 launch 是否同一条流？每个生产者是否完整覆写自己槽位？
- 暂存区容量是否按最大单元素需求取齐？尾部同步是否在释放前？

## 7. 验收标准

- 编译通过，安装包可用。
- 精度：与基线在共享评测用例集上逐用例一致（含特殊值/小合成 case——它们仍走检测路径）。
- 性能：大 shape 端到端接近「纯 kernel 时间」（实例：门控使 cid2 70→17、cid5 778→203 μs）；多元素用例下降幅度大于单元素用例（验证逐元素串行开销被消除）；host 侧同步/分配次数从「每调用/每元素一次」降为「整批一次或零次」。
- 若任一不满足则回退。
