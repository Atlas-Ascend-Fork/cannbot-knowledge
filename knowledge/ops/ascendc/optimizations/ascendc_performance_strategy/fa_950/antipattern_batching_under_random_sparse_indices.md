# 反模式策略：随机稀疏索引下的"合批"（M 维合并 / 多头合并）

> **单一反模式：** 在稀疏 attention 类算子中，观察到两个诱人的事实：
> ① 同一份 KV 被大量 query 位置**重复 gather**（索引重叠率可达 75%）；
> ② Cube 的 M 维利用率极低（如 G=4 补齐到 16，仅 25%）。
>
> 于是自然想到"**把多个 query 位置合批**"——既能共享 gather 结果省搬运量，又能把 M 维填满。
>
> **结论：❌ 在索引随机的前提下不成立。** 根因是一个**内在矛盾**：
> **M 维合并的前提是共享索引集，而共享索引集的代价（并集膨胀）增长快于 M 维利用率的收益。**
>
> 本策略记录完整证伪链，避免重复立项。

---

## 1. 反模式的两种形态（本质是同一件事）

立项时容易把方案拆成两个"可独立取舍"的选项：

| 方案 | 描述 | 表面优点 |
|---|---|---|
| A | **仅**合并 M 维（不共享 gather） | workspace 不变、无缓存风险，可以先做 |
| B | 合批 + 共享 gather 去重 | 省 75% 搬运量 |

**这个拆分是错的。方案 A 不存在。**

矩阵乘 `S[m,n] = Σ_k Q[m,k] × K_sel[n,k]` 中，单次 `Mmad` 的 **B 矩阵（K_sel）由全体 M 行共用**。而稀疏索引是 per-query-position 的（`si[b, n, s, :]`），不同 query 位置的索引集完全不同：

- 行 m 属于位置 a ⇒ 需要 `K_sel_a[n, :]`
- 行 m 属于位置 b ⇒ 需要 `K_sel_b[n, :]`
- ⇒ **同一次 Mmad 的不同 M 行需要不同的 B 矩阵——硬件不支持**

**所以"合并 M 维"的前提就是"共享 K_sel"，A 就是 B。**

> **对照：为什么 GQA 的 group 维可以合并？**
> 因为同一 KV 头下的 G 个 query 头**共享同一个 n**，因而共享同一份 K_sel——这是**语义允许**的合并，通常实现中已经做了（`M = G`）。
> 换言之，"M 维利用率只有 25%" 往往不是实现缺陷，而是 `G=4` 这个 shape 的**固有属性**。

---

## 2. 共享索引集的代价：并集膨胀

要共享就得取并集。实测（topK=1024, S2=8192, 随机索引）：

| 合批数 | 索引并集 | 每位置有效列占比 | **矩阵乘算力浪费** | 中间矩阵单槽 |
|---|---|---|---|---|
| 1（不合批） | 1024 | 100% | 0% | 32KB |
| 2 | 1918 | 53% | **47%** | 60KB |
| 4 | 3389 | 30% | **70%** | 212KB |
| 8 | 5377 | 19% | **81%** | 672KB |

M 维利用率确实能从 25% 提到 100%（4x），但同时：

- **矩阵乘的 N 维膨胀到并集大小**——每个位置只用得上并集的一小部分列，算力浪费 47%~81%；
- 中间矩阵（scores/attn）同步放大 1.9~5.3x。

**两者相乘，净收益为负。**

---

## 3. workspace 的硬约束

若做全并集共享，中转 workspace 会膨胀：

| 合批数 | 单核占用 | 总量（32 核） |
|---|---|---|
| 1（当前） | 128KB/槽 ×3 | **12 MB** |
| 8 | 1344KB/槽 ×3 | **126 MB** |
| 32 | 2021KB/槽 ×3 | **190 MB** |

而同一算子上另有实测（策略 04 §6）：workspace 仅涨到约 **30MB** 就因工作集跨出缓存产生 **30% 双峰分布**。126~190MB 会严重重蹈覆辙。

---

## 4. 即便合批可行，收益也被另一侧瓶颈挡住

退一步假设合批无副作用，收益上限也有限。实测各管线占比：

| 管线 | ratio | 合批后 |
|---|---|---|
| **向量侧 mte2（gather 搬运）** | **0.817** | **不变**（gather 量不变——若只合并 M 不共享 gather） |
| 向量侧 scalar | 0.810 | 部分 ÷合批数 |
| Cube 侧 scalar | 0.728 | ÷合批数 |
| Cube 侧 mac | 0.186 | 不变 |

向量侧各管线 ratio 之和 = 1.915（远大于 1）说明管线间已大量重叠，瓶颈是 `max = 0.817`。

**即使 Cube 侧开销完全归零，下界也是 `0.817 × 总时长`，仅 1.22x** ——
而代价是 host tiling + 多个 kernel 文件的全链路改动，且会使小 shape 的每核任务数跌破流水稳态（策略 04 的判据）。

---

## 5. 另一变体：多 KV 头合并（同样不成立）

在 BSND 布局下，`K[b, idx, :, :]` 的 N2 个 KV 头**内存连续**（如 8×128×2 = 2048B）。既然"每次发射多搬几乎免费"（策略 09），一次搬 8 个头似乎可行。

但索引仍是 per-head 的，8 个头需要的 idx 集合不同，仍需取并集：

| 项 | 值 |
|---|---|
| 同一 (b, s) 下 8 个头的索引并集 | 5377 / 8192（重复率 34.4%） |
| 发射次数 | 8192 → 5377（**降到 66%**） |
| 搬运量 | 2.0MB → 10.5MB（**放大 5.25x**） |

**搬运量放大 5.25x 只换来发射降 34%，兑换比不划算**；且中转区需存 N2 份，容量 ×8。

> 注意与 §1 的区别：多头合并**不会**让矩阵乘的 N 维膨胀（各头是独立 task，各算各的矩阵乘），
> 所以不存在算力浪费问题。它否掉的原因纯粹是**搬运量/发射数的兑换比**。

## 6. 判别问题（动手前必答）

| 问题 | 若答案是… |
|---|---|
| 要合并的多个单元是否**共享同一索引集**？ | 否 ⇒ 必须取并集，进入下一问 |
| 并集相对单个的膨胀率是多少？ | 实测统计，不要估算 |
| 合并后矩阵乘的 N 维是否随并集膨胀？ | 是 ⇒ 算力浪费 = 1 − 单个/并集，通常直接判负 |
| 中转 workspace 膨胀后是否仍在**缓存**内？ | 否 ⇒ 双峰风险（策略 04 §6） |
| 另一侧管线是否已饱和？ | 是 ⇒ 合并收益被其挡住，先算上限 |
| 合并后每核任务数是否仍留稳态余量？ | 否 ⇒ 流水失稳（策略 04 判据） |

**任一问答案为负 ⇒ 不要做。**

---

## 7. 什么情况下合批是对的

本策略否定的是"**索引随机时的合批**"，不是否定合批本身：

| 情形 | 说明 |
|---|---|
| 多个单元**天然共享**索引集 | 如 GQA 的 group 维（共享同一 KV 头）——已在实现中做了 |
| 索引**有序且高度重叠** | 并集膨胀率低（如滑动窗口注意力，相邻位置窗口大幅重叠） |
| 合并不引起矩阵乘 N 维膨胀 | 如纯搬运侧合并，且兑换比划算 |
| 稠密场景 | 无稀疏索引，不存在并集问题 |

判别式：

```text
收益 ≈ M维利用率提升倍数
代价 ≈ 并集膨胀率（算力浪费）× 中间矩阵放大率 × 缓存风险
仅当 并集膨胀率 ≈ 1（高度重叠）时，合批才划算
```

## 8. 方法论教训

> **立项时我把「M 维合并」和「共享 gather」当成两个可独立取舍的选项，
> 并据此认为"方案 A 无缓存风险，可以先做"。这个拆分从一开始就不成立。**
>
> **动手前应先验证方案的数学前提**（单次 Mmad 的 B 矩阵是全 M 行共用的），
> 而不是先算容量和收益。
>
> 这与另外几个已记录的同类错误同源（策略 06 的"没算 kTiles"、策略 07 的"把气泡拍成 200ns"）：
> **先验证前提是否成立，再谈收益大小。**

## 9. 验收标准（若要复核本结论）

本策略**不涉及代码改动**。复核方式是数据核算：

```python
# 1. 统计目标 shape 上的索引并集膨胀率
import torch
g = torch.Generator().manual_seed(0)
perm = torch.rand(num_groups, S2, generator=g).argsort(dim=1)
sel  = perm[:, :topK]
for SB in [2, 4, 8, 16, 32]:
    u = set()
    for i in range(SB): u |= set(sel[i].tolist())
    print(SB, len(u), f"每单元有效占比 {topK/len(u)*100:.0f}%")

# 2. 核算 workspace 膨胀后总量，与已知的缓存双峰阈值对比
# 3. 用 profiling 的 max(ratio) 算另一侧瓶颈给出的收益上限
```

判据：

- 并集膨胀率显著 >1 ⇒ 算力浪费不可接受 ⇒ 不做；
- workspace 膨胀后超过已知双峰阈值 ⇒ 不做；
- 另一侧管线 ratio 已 >0.8 ⇒ 收益上限 = 1/ratio，据此评估是否值得全链路改动。

结论须写清：

```text
本条为已证伪的反模式：随机稀疏索引下的合批。
内在矛盾：M 维合并要求共享索引集，而共享的代价（并集膨胀 ⇒ 算力浪费 + workspace 膨胀）
增长快于 M 维利用率的收益。
"M 维利用率低"往往是 shape 的固有属性，不是实现缺陷。
仅当多单元天然共享索引集、或索引高度重叠（并集膨胀率≈1）时，合批才成立。
```

## 检索卡（短卡）

动作：反模式：随机稀疏索引下把多个 query 位置合批共享 gather 填满 M 维（G=4 补 16 仅 25%），并集膨胀算力浪费 47%~81% 净负。
适用：仅当多单元天然共享索引集、索引有序高度重叠（并集膨胀率≈1）或合并不引起 Mmad N 维膨胀时合批才成立。
限制：单次 Mmad 的 B 矩阵由全 M 行共用，不同位置索引集不同⇒合并 M 维前提就是共享 K_sel，「仅合并不共享 gather」不存在。
范围：稀疏 attention 类算子的 gather 与 M 维合并决策。
检索词：稀疏索引、并集膨胀、M 维利用率、gather、topK、GQA、workspace、双峰分布。
机会：同一份 KV 被重复 gather（重叠率 75%）且 Cube M 维利用率仅 25%，想合批共享搬运。
代价：并集下矩阵乘 N 维膨胀、中间矩阵放大 1.9~5.3x、8 合批 workspace 达 126MB。
