# 正确性策略：并发阶段共用片上 buffer 的隐蔽竞争（识别、诊断与修复）

> **单一问题点：** 在软流水（ring pipeline）算子中，若两个**并发执行的阶段**（如 `Gather(cur)` 与 `Vec1(prev1)`）共用同一块片上 `TBuf`，就存在写读竞争。这类 bug 的特点是**长期潜伏**——当消费方是"读得快且紧跟同步"的标量循环时，竞争窗口极窄，可能几十轮迭代都不暴露；一旦把消费方改成向量批量读取（时序变化），窗口立刻显形。
>
> **本策略不是性能优化，是正确性防护。** 但它必须与性能策略一起记录，因为**它总是在做性能优化时才被触发**——性能改动改变了时序，把潜伏的竞争暴露出来，此时极易误判为"我的性能改动引入了数值错误"，从而回退掉本来正确的优化。
>
> **已验证锚点：** A5(Ascend950DT) SparseFlashAttention。`siIdxBuf_` 被 `Gather`（处理 `cur` 任务）与 `ApplyCausalMask`（处理 `prev1` 任务）共用，而 ring 流水中二者**并发**。原标量逐元素消费未暴露；改为向量化消费（策略 03）后立刻显形：**精度随机漂移、失败用例集合每次都变、同一用例 mismatch 在 0.02%~6.9% 间跳**。分配专用 buffer 后恢复 37/37。
>
> **关键诊断签名：** 数值逻辑错 ⇒ **稳定**失败在**固定**用例；竞争/未初始化 ⇒ 失败集合**每次都变**、误差量级**跳变**。

---

## 1. 问题原理

### 1.1 软流水中"并发"的含义

ring pipeline 的典型调度：

```cpp
void ExecuteTask(loop, runInfo[]) {
    cur   = runInfo[loop % RING_SLOTS];
    prev1 = runInfo[(loop + RING_SLOTS - 1) % RING_SLOTS];
    prev2 = runInfo[(loop + RING_SLOTS - 2) % RING_SLOTS];

    if (cur.valid)   { StageA(cur);   }    // ← 处理任务 N
    if (prev1.valid) { StageB(prev1); }    // ← 处理任务 N-1
    if (prev2.valid) { StageC(prev2); }    // ← 处理任务 N-2
}
```

`StageA` 与 `StageB` 在**同一次调用内顺序书写**，但它们处理的是**不同任务**，且各自的搬运/计算指令在不同管线上**重叠执行**。因此：

> **同一 AIV 上、同一次 `ExecuteTask` 内的不同阶段，其指令是并发的**——不能假设 `StageA` 的全部副作用在 `StageB` 开始前已完成，除非有显式同步。

若 `StageA` 写某 `TBuf`、`StageB` 读同一 `TBuf`，且二者之间**没有**跨阶段同步，就是竞争。

### 1.2 为什么会长期潜伏

竞争是否显形，取决于**消费方的读取时序**：

| 消费方式 | 竞争窗口 | 表现 |
|---|---|---|
| 标量逐元素 `GetValue`（紧跟 `MTE2_S` 同步） | 极窄，读得快 | 可能长期不暴露 |
| 向量批量读取（一次算整段） | 变宽，活跃期长 | 立刻显形 |

因此典型的触发路径是：

```text
性能优化（把标量循环向量化）→ 时序变化 → 潜伏的竞争显形 → 精度失败
                                                    ↓
                              ❌ 误判"是我的优化引入了数值错误" → 回退掉正确的优化
                              ✅ 正解：识别为竞争，分配专用 buffer，优化保留
```

### 1.3 与"同一阶段内的 buffer 复用"的区别

同一阶段内先后使用同一 buffer（用完即弃）是**安全**的（有管线内序或显式事件保证）。
本策略针对的是**跨并发阶段**的共用。

## 2. 识别条件

出现以下**任一**组合即应怀疑：

| 线索 | 说明 |
|---|---|
| **失败集合漂移** | 多次运行，失败的用例列表**每次不同** |
| **误差量级跳变** | 同一用例 `mismatch` 在 0.02% ~ 6.9% 之间跳 |
| 与改动无关的用例也失败 | 失败范围超出本次改动的语义影响范围 |
| 改动本身可证等价 | 改动是逐位等价变换，理论上不该有任何精度变化 |
| 时序敏感 | 加大/减小某处并发度会改变失败率 |

**对照签名**（用于排除竞争）：

| 现象 | 结论 |
|---|---|
| 每次失败**同一批**用例、误差量级**稳定** | 数值逻辑错，不是竞争 |
| 只有开启某特性的用例失败 | 该特性路径的逻辑错，不是竞争 |

---

## 3. 排查步骤

### 3.1 列出所有共用 buffer

```bash
grep -n "<bufName>_" <kernel>.h        # 找出全部使用点
grep -n "InitBuffer" <kernel>.h        # 确认分配处
```

对每个 buffer 记录：**在哪些阶段被写、被读**。

### 3.2 判定阶段是否并发

对照 ring 调度函数，确认这些阶段是否在同一次调用内被分派给**不同任务**（`cur`/`prev1`/`prev2`）。若是 ⇒ 并发 ⇒ 存在竞争。

### 3.3 确认无跨阶段同步

检查两个阶段之间是否有覆盖该 buffer 的显式事件。ring 流水里的 `CrossCoreSetFlag/WaitFlag` 通常只覆盖 **workspace(GM)** 的可见性，**不覆盖片上 TBuf**。

### 3.4 隔离验证

把可疑 buffer 拆成两块专用 buffer，其余不动，重测：
- 精度恢复 ⇒ 确认是竞争；
- 仍失败 ⇒ 另有原因，恢复原状继续查。

---

## 4. 修复方式

### 4.1 首选：分配专用 buffer

```cpp
// 修复前：两个并发阶段共用
pipe->InitBuffer(sharedBuf_, size);

// 修复后：各自专用
pipe->InitBuffer(stageABuf_, size);    // StageA 专用
pipe->InitBuffer(stageBBuf_, size);    // StageB 专用（注释写明为何不可复用）
```

代价是片上容量。若容量紧张，先用策略"片上 buffer 容量回收"腾出预算。

**必须在注释里写明"为何不可复用"**，否则后人会以"这里有两块一样的 buffer，合并省容量"为由改回去。

### 4.2 次选：加跨阶段同步

若容量确实不够，可在两阶段间加显式事件。但要注意：
- 这会**串行化**两个本可并发的阶段，损失流水并行度；
- 同步开销可能抵消性能收益。

一般**优先选 4.1**。

### 4.3 检查同类隐患

修完一处后，把 §3.1 的清单过一遍——同一算子里常有**多处**同类共用。

## 5. 已知陷阱

### AP-001：误判为"我的性能改动引入了数值错误"

问题：性能优化后精度失败，直接回退优化。
症状：丢掉了本来正确、且有显著收益的优化（实例中该优化值 2.8x）。
修复：先用 §2 的签名判定是否为竞争。**失败集合漂移 ⇒ 是竞争，不是你的公式错。**

### AP-002：把公共临时区当自由空间用

问题：向量化时随手用了公共 `tmpBuf_`（常被 softmax 等高阶 API 当工作区）。
症状：数值随机漂移。
修复：高阶 API 的工作区**整块**属于它，不要在其中另辟偏移。分配专用 buffer。

### AP-003：只改一处使用点

问题：把某 buffer 的**生产方**改了（如改成从别处读索引），但**消费方**（另一阶段）仍读原 buffer。
症状：消费方读到未填充数据，大面积失败。
修复：`grep` 全部使用点，同步修改。

### AP-004：依赖"调用顺序"这种隐式契约

问题：认为"反正 StageB 在 StageA 之后写的代码，顺序有保证"。
澄清：源码顺序 ≠ 执行顺序。不同管线的指令重叠执行，只有显式事件才有保证。

### AP-005：删除"看起来没用"的 buffer

问题：发现某 `TQue` 已无 `AllocTensor`/`DeQue` 消费点，判定为死代码删除。
症状：**其它 buffer** 的同步闭环被破坏（TQue 的数量会影响隐式分配的事件 ID 编号），出现小幅稳定精度偏差。
修复：这类 kernel 里 **TQue 数量本身是同步契约的一部分**。删 buffer 属**行为变更**而非清理；要动必须同时把手工 `SetWaitFlag` 改成显式 `FetchEventID` 分配的事件。

## 6. LLM 实施前必须回答的问题

| 问题 | 必填内容 |
|---|---|
| 失败签名 | 失败集合是否漂移？误差量级是否跳变？（据此判定竞争 vs 逻辑错） |
| buffer 清单 | 可疑 buffer 的全部读写点及所属阶段 |
| 并发判定 | 这些阶段在 ring 调度中是否处理不同任务 |
| 现有同步 | 两阶段间是否有覆盖该 buffer 的显式事件 |
| 容量 | 拆成专用 buffer 需要多少额外片上空间；当前余量 |
| 同类隐患 | 是否还有其它跨并发阶段共用的 buffer |
| 隔离验证 | 拆分后精度是否恢复 |

任一项无法回答，不下"是竞争"的结论。

---

## 7. 禁止事项

禁止：

- 在未做签名判定前，因精度失败就回退性能优化（AP-001）。
- 在高阶 API 的工作区内另辟偏移（AP-002）。
- 只改生产方或只改消费方（AP-003）。
- 依赖源码顺序当同步（AP-004）。
- 把"无消费点的 TQue"当死代码直接删（AP-005）。
- 合并两块注释写明"不可复用"的 buffer。

## 8. 验收标准

```bash
# 精度必须【多次】运行，观察失败集合是否稳定
for i in 1 2 3; do pytest <op>/test/test_<op>.py -q; done
```

判定：

- 修复后 **3 次全通过** ⇒ 竞争已消除；
- 若仍有失败但**集合稳定** ⇒ 另有逻辑错，与竞争无关；
- 若失败集合**仍漂移** ⇒ 还有未找到的共用 buffer，回 §3.1。

性能：分配专用 buffer 本身**不应带来性能变化**（实例实测：仅修竞争而不做向量化时，性能与基线一致，摆幅内）。

> **归因纪律**：若一次改动同时包含"性能优化"与"竞争修复"，**必须做 A/B 分离**——
> 分别测"只修竞争"与"修竞争+优化"，否则会把收益记错。
> 实例中分离验证表明：**仅修竞争 0 收益，全部收益来自向量化**。
> 不做分离就会得出"修竞争带来 2.8x"的错误结论。
