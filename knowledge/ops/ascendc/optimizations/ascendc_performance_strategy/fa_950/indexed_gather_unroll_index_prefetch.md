# 性能优化策略：索引驱动散读的 N 路展开 + 索引预取（打散"标量装载→搬运发射"依赖链）

> **单一优化点：** 当一个按运行时索引散读的循环写成 `for i: idx=load(i); DataCopy(dst_i, src[f(idx)], len)` 时，每条搬运指令的**源地址必须等这一行的索引标量装载回来才能算出**，形成逐行的 `装载→发射` 串行依赖链，搬运管线被标量装载延迟一行一行地卡住。改为 **N 路展开 + 索引预取**：先**连续**读 N 个索引，再**连续**发 N 条搬运指令。N 次标量装载彼此重叠、并与前一组的搬运发射重叠，依赖链由 `装载→发射` × M 摊薄成 M/N 段。
>
> **与策略 01 的区别（关键）：** 01 削减的是**标量算术量**（每行少几次乘法），实测 −1.2%；本策略削减的是**依赖链深度**（装载与发射的串行关系），实测 **−20%**。两者作用于同一段代码但削减不同的东西，**正交可叠加**。若只做 01 而不做本策略，会把"标量占比高"误归因为"算术太多"。
>
> **已验证锚点：** A5(Ascend950DT) SparseFlashAttention `Gather`，每行搬 256B（Dk=128, fp16）。4 路展开：三个 Dk=128 用例齐降 **−20%**（`s256 1715.7→1358.6µs`、`s1024 15315.4→12481.1µs`、`mtp 115.1→92.0µs`）。后续把展开度扫全 4~7，最优在 **6**：`s256 →453.6µs`、`s1024 →~3954µs`，相对 4 路再 **−5.5%**，精度 37/37。
>
> **展开度必须实测扫全，不能只测两点** —— 见 §3.2 与 AP-004（实测 5 路反而比 4 路差，非单调）。

本策略只改"内层展开度与索引预取顺序"。不改变搬运指令总数、不改变搬运字节数、不改变数据值/布局、不改 tiling、不动同步结构。

## 1. 优化原理

### 1.1 性能问题模式（通用）

索引驱动散读的朴素写法：

```cpp
for (uint32_t i = 0; i < rows; ++i) {
    int32_t idx = idxUb.GetValue(i);          // (a) 标量装载（S 管线，有延迟）
    uint64_t off = base + idx * stride;       // (b) 地址计算
    DataCopy(dstUb[i * dstStride],            // (c) 搬运发射（MTE2）
             srcGm[off], len);
}
```

依赖关系是 `(a) → (b) → (c)`，且**下一轮的 (a) 排在本轮 (c) 之后**。于是时间线为：

```text
load(0) ──▶ issue(0)
              load(1) ──▶ issue(1)
                            load(2) ──▶ issue(2)   ← 每条发射都在等一次装载
```

搬运单元在等标量装载，标量单元在等上一条发射腾出发射窗口。**当单行搬运字节数很小时（如 256B），单行成本由"发射侧"而非"带宽侧"决定**，这条链就是天花板。

判据：`aiv_scalar_ratio` 与 `aiv_mte2_ratio` **同时很高且数值接近**（实例中分别为 0.810 / 0.817）——这不是两个独立瓶颈，而是同一条串行链的两个侧面。

### 1.2 本策略利用的机制

同一管线内**连续发射的多条指令天然按序**，无需逐条同步。因此可以把 N 轮的 (a) 与 (c) 分别聚拢：

```cpp
for (i = 0; i + N <= rows; i += N) {
    int32_t d0 = idxUb.GetValue(i);           // N 次装载连续发出，
    int32_t d1 = idxUb.GetValue(i + 1);       // 彼此可重叠（无相互依赖），
    ...                                        // 且与上一组的搬运发射重叠
    int32_t dN_1 = idxUb.GetValue(i + N - 1);

    DataCopy(dstUb[...], srcGm[base + d0*stride], len);   // N 条发射连续
    DataCopy(dstUb[...], srcGm[base + d1*stride], len);
    ...
}
for (; i < rows; ++i) { /* 尾行：原逐行路径 */ }
```

时间线变为：

```text
load(0..N-1) ──────▶ issue(0..N-1)
                       load(N..2N-1) ──────▶ issue(N..2N-1)
```

依赖链的**段数**从 M 降到 M/N。注意：**指令总数没变**，变的只是它们之间的依赖结构。

## 2. 适用条件与泛化边界

必须**同时**满足：

| 条件 | 要求 |
|---|---|
| 循环形态 | 内层 `装载索引 → 算地址 → 发搬运`，且下一轮装载依赖上一轮发射完成 |
| 索引来源 | 索引已在片上（UB）；若每轮都要从 GM 读索引，先解决索引落片（见 AP-006） |
| 发射受限 | 单次搬运字节数小，行成本由发射决定而非带宽（**用策略 09 的探针实测确认**） |
| 管线内有序 | 同一管线连续发射的多条指令按序完成，批内无需逐行同步 |
| 无跨行依赖 | 第 i 行的搬运不依赖第 i-1 行的结果 |
| 寄存器余量 | N 个索引同时活跃需 N 个标量寄存器，N 过大会溢出（见 §3.2） |
| 基线稳定 | 修改前 build/精度/性能可重复 |

优先适用：

- profiling 显示 `scalar_ratio` 与 `mte2_ratio` **同时高且接近**（同一串行链的两面）。
- 稀疏 gather / embedding lookup / 按 index 取行的任意场景。
- 单行 128B~512B 量级（太大则转为带宽受限，本策略收益衰减）。

不适用：

- 单行搬运很大（已带宽受限）——先用策略 09 判定；带宽受限时本策略无效。
- 索引间存在依赖（如链式索引 `idx[i+1] = f(data[idx[i]])`）——无法预取。
- 循环体内有跨行同步（如逐行 `SetFlag/WaitFlag`）——需先合批消除（属"批量 gather"策略）。

## 3. 实施步骤

### 3.1 改写内层

1. 保留原批处理/同步结构（WAR/RAW 事件位置不动）。
2. 内层拆为「主循环（步长 N）+ 尾循环（逐行）」两段。
3. 主循环内：**先全部 `GetValue`，再全部 `DataCopy`**——顺序不能交错，交错就退化回原依赖链。
4. 尾循环保持原逐行写法，处理 `rows % N` 部分。

### 3.2 展开度 N 的选取：**必须实测扫全**

这是本策略最容易做错的一步。

**不要**只测两个点就下结论。实测（A5 SFA，256B/行）：

| 展开度 N | s256 (µs) | s1024 (µs) | 相对 4 路 |
|---|---|---|---|
| 1（原始） | — | — | 基线 |
| 4 | 479.7 | ~4200 | 0 |
| 5 | 492.2 | ~4313 | **+2.6%（比 4 还差）** |
| **6** | **453.6** | **~3954** | **−5.5%（最优）** |
| 7 | 471.1 | ~4124 | −1.8% |
| 8 | 劣化 | 劣化 | +3%（寄存器压力溢出） |

**曲线非单调**：5 路比 4 路差，6 路又是极小值。因此"测了 4 和 8，发现 8 更差，所以 4 是拐点"的推断**是错的**——中间的 6 才是最优，漏测导致少拿 5.5%。

推荐流程：

1. 先取 4 作为起点（多数场景的合理值）。
2. **逐点扫 3~8**，每点至少测 3 次（间隔足够，避免冷启动尖峰）。
3. 取极小值；若曲线在端点仍下降，继续外扩直到出现劣化。
4. 把整条曲线写进代码注释——后人才不会重复"只测两点"的错误。

非单调的可能成因（机制层，供参考）：寄存器分配与指令调度的对齐效应、展开后循环体大小与取指缓冲的匹配。**不必先解释清楚才敢用实测值**，但要在注释里说明"非单调，故扫全"。

### 3.3 与批处理结构的关系

若循环外层已有"攒批 + 批量写出"结构（常见于 gather），本策略作用在**批内**：

```cpp
for (base = 0; base < dealRows; base += batchRows) {   // 批循环：WAR/RAW 同步在此
    // ... WAR ...
    uint32_t i = 0;
    for (; i + N <= batchRows; i += N) { /* N 路展开 */ }   // ← 本策略
    for (; i < batchRows; ++i)         { /* 尾行 */ }
    // ... RAW，批量写出 ...
}
```

批循环的同步结构**不动**。

## 4. 正确性红线

### 4.1 顺序不可交错

- 主循环内必须**先全部装载、再全部发射**。若写成 `load(0); copy(0); load(1); copy(1); ...` 则完全退化，无收益。

### 4.2 尾行必须保留

- `rows % N != 0` 时尾行须由独立循环处理；漏掉尾行 ⇒ 少搬数据 ⇒ 结果错。
- 尾循环的 `i` 必须**承接**主循环结束时的值（用同一个 `i`，不要重新初始化）。

### 4.3 目的偏移不能算错

- 展开后每条 `DataCopy` 的目的偏移是 `(i + j) * dstStride`（`j` 为组内序号），容易写错成 `i * dstStride`。
- 建议逐条显式写出 `i`、`i+1`、…、`i+N-1`，不要用可能出错的游标自增。

### 4.4 索引类型转换

- N 条展开的类型转换链必须与原逐行写法**逐字符一致**（见策略 01 §4.1）。

### 4.5 不改变搬运语义

- 搬运长度、目的行距、源地址公式均不变。本策略**只改指令排列顺序**。

## 5. 已知陷阱

### AP-001：装载与发射交错

问题：展开后写成 `load;copy;load;copy;...`。
症状：无收益（依赖链未打散）。
修复：§4.1，先全部装载再全部发射。

### AP-002：尾行漏处理或 `i` 重置

问题：主循环用局部 `i`，尾循环从 0 开始；或忘记尾循环。
症状：数据少搬/重复搬，结果错。
修复：§4.2，共用同一个 `i`。

### AP-003：目的偏移写错

问题：组内第 j 条仍用 `i * dstStride`。
症状：同一位置被覆盖 N-1 次，结果错。
修复：§4.3，逐条显式写 `(i + j)`。

### AP-004：只测两点就宣布拐点

问题：测了 4 和 8，见 8 更差便断定 4 最优。
症状：漏掉真实最优（实测在 6），少拿 5.5%。
修复：§3.2，逐点扫全；曲线可能**非单调**。

### AP-005：在带宽受限场景上做

问题：未判定瓶颈性质就展开。
症状：无收益。
修复：先用**策略 09 的探针**判定是发射受限还是带宽受限；带宽受限时本策略无效。

### AP-006：索引仍在 GM，每轮现读

问题：`GetValue` 作用在 `GlobalTensor` 上（直接读 GM）。
症状：展开收益被 GM 读延迟吃掉；实测大 topK 场景反而 **+19%**。
修复：索引须先批量搬到 UB（一次 `DataCopyPad`），再在 UB 上 `GetValue`。

### AP-007：把本策略与策略 01 混为一谈

问题：认为"外提地址计算"和"展开预取"是同一件事。
澄清：01 削算术量（−1.2%），本策略削依赖链深度（−20%）。**正交，应叠加**。

| 基线 | 修改前 build/精度/性能基线值，及重复次数 |

任一项无法回答，不实施本策略。

## 7. 禁止事项与回退条件

禁止：

- 装载与发射交错（AP-001）。
- 省略尾行处理（AP-002）。
- 只测两个展开度就固化（AP-004）。
- 未判定瓶颈性质就实施（AP-005）。
- 在索引仍需从 GM 现读时实施（AP-006）。
- 改变搬运长度/目的行距/源地址公式。
- 为了展开而修改同步结构（同步属其它策略）。

回退或缩小策略的条件：

- 精度不一致 → 首查目的偏移（AP-003）与尾行（AP-002）。
- 实测无收益 → 检查是否交错（AP-001）；再用策略 09 确认瓶颈性质（AP-005）。
- 所有展开度都不优于原始 → 该循环非发射受限，放弃。
- 展开后寄存器溢出（编译告警或性能骤降）→ 减小 N。

## 8. 验收标准

最小验证：

```bash
bash <build> --soc=<soc> --op=<op> --wheel 2>&1 | grep -cE "error:"   # 须为 0
source <set_env> && pytest <op>/test/test_<op>.py -q                   # 精度须与基线一致
# 展开度扫描：对每个 N，重复 ≥3 次，取样间隔足够长
```

精度：**必须逐位一致**（本策略是纯指令重排）。

性能（profiling 归因）：

- 端到端时间下降（实测量级 **−20%**，发射受限场景）；
- `scalar_time` 与 `mte2_time` **同时**下降（因为削的是二者共同构成的串行链）；
- 搬运指令数、搬运字节数**不变**（若变了说明改动越界）。

边界：不同 `rows % N`（尾行长度）各测一次；小 shape 应无劣化。

性能结论须写清：

```text
本策略削减的是"标量装载→搬运发射"的依赖链深度，不减少指令数与字节数。
仅在发射受限场景有效（须先用策略 09 判定）。
展开度必须逐点扫全——实测曲线非单调（5 路比 4 路差，6 路最优）。
与策略 01（削算术量）正交，应叠加。
```

## 检索卡（短卡）

动作：将索引散读循环N路展开：主循环先批量预取索引，再连续发射搬运；尾部逐行处理。
适用：内层按“装载索引→算地址→发搬运”执行，下一轮装载依赖上一轮发射。
限制：主循环先全部装载索引、再全部发射搬运，不得交错；原批处理和WAR/RAW事件位置保持不动。
范围：按运行时索引执行DataCopy的内层散读循环。
检索词：索引驱动散读、N路展开、索引预取、DataCopy、WAR/RAW事件。
机会：运行时索引散读循环逐轮执行索引装载、地址计算和搬运。
代价：不足N路的尾部仍需逐行处理。
