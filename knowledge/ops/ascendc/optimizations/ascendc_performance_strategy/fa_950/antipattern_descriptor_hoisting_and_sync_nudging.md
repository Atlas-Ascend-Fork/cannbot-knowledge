# 反模式策略：搬运描述符外提与同步位置微调（两类"看似免费"的微优化）

> **单一反模式：** 当 profiling 显示某核**标量占比高**时，很容易想到两类"零风险"的微优化：
> **(A) 把 `DataCopy` 的参数结构体提到循环外构造一次**；
> **(B) 把某个 `WaitFlag` 往后挪，让不相关的标量计算填进 `SetFlag`/`WaitFlag` 之间的气泡**。
>
> **实测两类都失败**：(A) **+21.2%** 严重劣化；(B) 最好值持平但**引入了 +67% 的异常抖动**。
>
> **共同根因：用未经验证的假设做定量推断。** (A) 假设"结构体重载比标量重载更省"；(B) 把气泡大小拍成 200ns 才算出 4.9% 的诱人收益——两个假设都从未被测量过，且都是错的。

---

## 1. 反模式 A：把 `DataCopy` 描述符提到循环外

### 1.1 想法

```cpp
// 原实现：每次调用都传 calCount，看起来"每次都要现算 blockLen 并构造 DataCopyParams"
for (i...) {
    DataCopy(dstUb[...], srcGm[...], dk_);          // ← calCount 重载
}

// "优化"：结构体只构造一次
DataCopyParams params;
params.blockCount = 1;
params.blockLen   = dk_ * sizeof(T) / 32;
params.srcStride  = 0;
params.dstStride  = 0;
for (i...) {
    DataCopy(dstUb[...], srcGm[...], params);       // ← 结构体重载，复用
}
```

推理：`calCount` 重载内部要从 `calCount` 现算 `blockLen` 并现场构造 `DataCopyParams`，外提后省掉这份重复构造。在标量已是瓶颈的核上，这看起来是纯赚。

### 1.2 实测：严重劣化

| 用例 | 逐行 `calCount` 重载 | 外提 `DataCopyParams` | Δ |
|---|---|---|---|
| prefill_bnsd_gqa_b2_s1024 | 11210.3 | 13585.7 | **+21.2%** |
| prefill_bsnd_gqa_b2_s256 | 1358.1 | 1386.8 | +2.1% |

### 1.3 根因

**`calCount` 重载并不是"先构造结构体再走通用路径"。** 它是一条更精简的路径——直接由标量立即数生成搬运指令；而结构体重载需要**从内存读结构体字段**，反而更重。

即：原本以为"外提省掉构造"，实际是"把立即数路径换成了访存路径"。

### 1.4 推广结论

> **在这类搬运密集路径上，不要用结构体重载替换标量（`calCount`）重载。**
> 若确需结构体重载（如需要 `blockCount>1` / `srcStride`），那是**功能需求**，其收益应来自"一条指令搬多块"，而非"少构造一次结构体"。

## 2. 反模式 B：挪动同步位置以"填气泡"

### 2.1 想法

gather 中读索引与散读之间有一个硬同步：

```cpp
DataCopyPad(siUb, siGm[...], ...);            // MTE2 读索引到 UB
event_t e = FetchEventID<HardEvent::MTE2_S>();
SetFlag<HardEvent::MTE2_S>(e);
WaitFlag<HardEvent::MTE2_S>(e);               // ← 立刻等：索引必须全部落地
                                              //   每 task 一次全管线气泡
uint64_t base, stride;                        // ← 这段【不依赖 si】
{ ...算地址不变量... }                          //   正好可以塞进气泡
```

于是把 `WaitFlag` 推迟到地址计算之后：

```cpp
SetFlag<HardEvent::MTE2_S>(e);
{ ...算地址不变量（不依赖 si）... }             // 与 MTE2 传输重叠
WaitFlag<HardEvent::MTE2_S>(e);               // 到真正要用 si 之前才等
```

按"每核 1024 个 task、气泡 200ns"估算，值约 205µs（总时长的 4.9%）。

### 2.2 实测：无收益且引入抖动

| 用例 | 基线 | 挪动同步后 | 说明 |
|---|---|---|---|
| prefill_bsnd_gqa_b2_s256 | 478.6 / 478.4 / 478.9 | 511.7 / **475.7** / **799.3** | 最好值持平，但出现 +67% 异常值 |
| prefill_bnsd_gqa_b2_s1024 | 4162 / 4196 / 4236 | 4154 / **5794** / 4215 | 同上 |

回退后复测：s256 = 479.78 / 479.62 / 479.69（摆幅 **0.03%**），稳定性完全恢复——反证抖动确由该改动引入。

### 2.3 根因

**其一：气泡本来就很小。** 最好值持平（475.7 vs 478.4）说明气泡接近 0——si 只有 2KB，且 MTE2 与后续散读同属一条管线，硬件本就有重叠能力。"200ns" 这个数字是**拍出来的，从未验证**。

**其二：同步位置影响调度稳定性。** 推迟 `Wait` 使 Scalar 与 MTE2 的相对时序变松，可能与 ring 流水中其它阶段的争用形成**新的耦合**，导致偶发的长尾。

### 2.4 推广结论

> **同步位置的调整不是"省几纳秒"那么简单，它会改变整个调度的耦合关系。**
> 在软流水算子中，一个稳定的同步结构本身有价值；为了填一个未经测量的小气泡去动它，风险大于收益。

## 3. 两条反模式的共同教训

| 反模式 | 未经验证的假设 | 实际 |
|---|---|---|
| A | "结构体重载 = 先构造结构体再走通用路径，所以外提更省" | `calCount` 重载是更精简的立即数路径 |
| B | "气泡有 200ns 量级" | 接近 0 |

> **定量推断前必须验证其前提。** 这与另外两个已记录的同类错误同源：
> - 「没算 `kTiles` 实际取值就动手」（策略 06）；
> - 「用『搬运量 ÷ 时间 = 所需带宽』反推架构，却没验证『时间正比于搬运量』」（策略 09）。
>
> 三者都是**拍脑袋的量级假设 = 没有量级依据**。

## 4. 什么情况下这两类改动才值得做

### 4.1 描述符外提

仅当**同时**满足：

| 条件 | 说明 |
|---|---|
| 确需结构体形态 | 需要 `blockCount>1` / `srcStride` / `dstStride` 等 `calCount` 重载表达不了的语义 |
| 收益来自功能 | 收益是"一条指令搬多块"，而非"少构造结构体" |
| 已实测对比 | 两种重载各测 ≥3 次 |

### 4.2 同步位置调整

仅当**同时**满足：

| 条件 | 说明 |
|---|---|
| 气泡已被**测量** | 不是估算——用探针（如把被等待的搬运量改大/改小）实测气泡量级 |
| 填充物足够大 | 待填入的工作量与气泡量级相当 |
| 稳定性有验证 | 改后重复 ≥3 次，确认**没有引入长尾** |
| 不破坏流水结构 | 不改变跨阶段的同步拓扑 |

## 5. 已知陷阱

### AP-001：只看最好值，不看分布

问题：挪同步后最好值 475.7 优于基线 478.4，据此判定"有收益"。
症状：忽略了 799.3 这个 +67% 的异常值，实际均值劣化。
修复：**看分布，不看单点**；重复 ≥3 次，异常值必须解释。

### AP-002：把估算值当实测值

问题：气泡拍成 200ns 就算出 4.9%，据此认为"值得一试"。
澄清：估算可以用来**排序候选**，但不能用来**下结论**。前提本身要先验证。

### AP-003：认为"零风险"

问题：认为挪同步/外提结构体不改变语义，所以是零风险微优化。
澄清：不改变**数值**语义 ≠ 不改变**调度**行为。实例中稳定性从 0.1% 摆幅劣化到出现 +67% 异常值。

## 6. 验收标准（若要复核本结论）

```bash
bash <build> --soc=<soc> --op=<op> --wheel 2>&1 | grep -cE "error:"
source <set_env> && pytest <op>/test/test_<op>.py -q      # 精度应不变（两类改动都不改数值）
for i in 1 2 3; do <run perf>; done                        # 关键：看分布
```

判据：

- **精度不变但性能劣化** ⇒ 反模式 A 成立，回退；
- **最好值持平但出现长尾** ⇒ 反模式 B 成立，回退；
- 回退后应观察到稳定性恢复（摆幅回到基线水平）——这是反证改动确为抖动来源的关键一步。

结论须写清：

```text
本条为已证伪的两类反模式：
A) 搬运描述符外提：+21.2%。calCount 重载比结构体重载更精简，不要替换。
B) 同步位置微调填气泡：最好值持平但引入 +67% 长尾。气泡实测接近 0。
共同根因：用未经验证的量级假设做定量推断。
判定纪律：看分布不看单点；回退后须复测确认稳定性恢复。
```

## 检索卡（短卡）

动作：反模式：DataCopy 参数结构体外提循环外复用（+21.2%）、WaitFlag 后挪填气泡（+67% 长尾），两类微优化均证伪。
适用：仅当确需结构体语义（blockCount>1/srcStride）或气泡已被实测（非估算）且改后重复≥3 次无长尾时才值得做。
限制：calCount 重载是由标量立即数生成搬运指令的精简路径，结构体重载须从内存读字段更重；同步位置改变调度耦合，稳定同步结构本身有价值。
范围：标量占比高的搬运密集 kernel 微优化。
检索词：DataCopyParams、calCount 重载、SetFlag、WaitFlag、FetchEventID、气泡、长尾、调度耦合。
机会：profiling 某核标量占比高时想找零风险微优化；把气泡拍成 200ns 就算出 4.9% 诱人收益。
代价：估算可以排序候选但不能下结论；只看最好值不看分布会漏 +67% 异常值。
