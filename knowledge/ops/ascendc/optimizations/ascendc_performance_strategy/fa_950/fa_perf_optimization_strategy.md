# FA 类算子性能优化通用策略

> 适用范围：昇腾平台上 Attention 族融合算子（含标准/因果/稀疏/分页/变长等变体）的 kernel 与 tiling 优化。
> 证据基础：两个独立 FA 类算子的实测 profiling + 快慢实现代码对照。凡标注「双算子验证」的结论在两者上同时成立。

---

## 0. 一条总纲：FA 算子几乎从不是 MAC-bound

两个算子、四类场景的实测 `aic_mac_ratio`：

| 场景画像 | mac_ratio | 真实瓶颈 |
|---|---|---|
| 长序列 prefill | 0.63 | AIV 向量计算效率 |
| 短序列 decode（多 batch） | 0.16 | 无效 cube 计算（M 维空转） |
| 短序列 decode（单 batch） | 0.15 | 并行度塌陷（1 核 / 32 核） |
| 稀疏 decode | **0.07** | 离散搬运 + 标量开销 |

**健康的快实现 mac_ratio 可达 0.98。** 慢实现的共性是：cube 各 pipe（mac/mte1/fixpipe）全面不饱和，唯独某一条 pipe 打满 —— 那条打满的 pipe 就是所有其他单元在等的对象。

> ⚠️ **诊断陷阱（双算子验证）**：`aic_scalar_ratio` 打到 0.98~0.999 时，**不要**直接判定"标量受限"。MIX 模板下 AIC 等待跨核 flag 的时间会被计入 scalar pipe。受控实验证据：某算子把 AIC scalar 实际耗时降了 280us，Task Duration **纹丝不动**。判据是看 mac/mte1/fixpipe 是否同时低 —— 若是，则 scalar 高是"在等"的表象，真实瓶颈在对侧核。

**方法论**：先用 pipe ratio 定位瓶颈单元 → 再看该单元内部构成（vec / scalar / mte2 / mte3）→ 只优化占比最大的那一项。跳过这一步的优化极易做在非关键路径上。

## 1. 数据流架构层（收益最高、改动最大）

### S1.1 中间结果不落 GM

**问题**：Cube 与 Vector 之间的中间量（scores / P / partial-O）若经 GM workspace 中转，每个流水阶段边界都是一次完整 GM 往返 + 跨核同步。

**度量**：统计单 tile 的 GM 流量，与"理论最小流量（仅读输入 + 写输出）"求比值。**放大 2 倍以上即为重症**。某稀疏算子实测放大 **2.65×**，总带宽已逼近单核上限，彻底 memory-bound。

**做法**：
- 主路径用 `Fixpipe` 直接 L0C→UB，Cube 结果不落 GM
- P 矩阵经 shared L1 交换而非 GM
- 仅在容量确实放不下时（如 D 超阈值、或开启 KV 轴分核）才退回 workspace

**红线**：这是架构级决策。若原设计有"禁用 CV 直连"之类的强制约束，需先确认该约束是否仍然成立 —— 它可能是当初为规避某类风险而设，而非性能考量。

### S1.2 消除源数据的多次中转

**问题**：从 GM 读入的数据被"搬进 UB → 写回 GM 暂存区 → 再读进 L1"，而源本来就在 GM。

**判别**：凡是「UB 只作透传、不做任何计算」的搬运链路，都是纯冗余。常见成因是误读了"dst=L1 的 ND2NZ 源必须为 GM"这类约束 —— 该约束禁止的是 UB→L1，**不禁止 GM→L1 直读**。

**做法**：把这类搬运下沉到 Cube 侧，直接 GM→L1 多次 ND2NZ，同时释放 Vector 的 MTE2/MTE3 带宽。某算子据此可消除 57% 的 GM 流量。

## 2. 访存与搬运层（稀疏/离散场景的首要瓶颈）

### S2.1 离散 gather 的搬运聚合 【双算子验证】

**问题**：按索引逐 token 发一条搬运指令。单次搬运量远低于 DMA 效率拐点（实测单行 1152B 时有效带宽仅 **7.4 GB/s**），指令数正比于选中 token 数。

**做法（按收益递减）**：
1. **相邻索引配对合并**：检测索引间距，把 2 个（或 N 个）token 合成一条 `DataCopyPad`，用 `blockCount` + 计算出的 `srcStride` 跨越间隔。指令数降至 1/N。
2. **多分量交织落位**：若一个 token 含多个分量（如 nope + rope 两段），用两条带 `dstStride` 的搬运直接交织进同一行宽 UB，避免后续再做拼接。
3. **连续 run 合并**：索引升序时相邻概率大增 —— 排序是启用合并的前提，且对"按值 gather"的语义中性。
4. **多小拷贝合并**：多个小 `DataCopy` 用 `blockCount`/`blockLen`/`dstStride` 收成一条 strided 拷贝。

**验证要点**：务必设计 `sorted` vs `unsorted` 的对照用例来量化相邻性收益 —— 否则这条优化的实际价值无从判断。

### S2.2 UB/GM stride 不匹配导致的逐行搬运

**问题**：UB 内行距因对齐要求被撑大（如为满足 softmax 基本块的最小列宽约束），与 GM 紧凑行距不等，于是退化成 `for r in rows { DataCopy }`。

**做法**：用 `DataCopyPad` 的 `srcStride`/`dstStride` 参数一条指令完成，而非逐行循环。

### S2.3 冗余搬运的识别

**注意**：代码上"重复搬运 N 倍"不等于"性能损失 N 倍" —— L2 cache 可能已将其掩盖。某算子代码层面有 64 倍 KV 重复读，但 `aic_mte2_time` 仅 1.11×，据此**排除**了该优化项。**先看 pipe 数据，再决定是否动手。**

## 3. 同步与流水层

### S3.1 热路径禁用全局 barrier 【双算子验证】

**问题**：`PipeBarrier<PIPE_ALL>` 阻塞全部流水（MTE1/2/3/V/M/FIX），使 TQue 的多缓冲**完全失效**。某稀疏算子在 gather 内层循环每 token 用了 2 个 `PIPE_ALL`，topK=512 时即 **1024 次全流水停顿**。

**做法**：换成精确的 pipe 对事件（如 `MTE2→MTE3`），VF 内部用 `LocalMemBar` 而非 barrier。跨核同步按 buffer + pipe 精确配对，`SyncAll` 只允许出现在主循环外。

> ⚠️ **已证伪的做法**：单独删除某个热路径 barrier 而不配套改同步语义 → **不稳定，会回退**。barrier 消除必须整套一起做（补齐精确事件 + 核对生产消费距离）。

### S3.2 软件流水的有效性前提 【关键，易被忽略】

**问题**：`RING_SLOTS=3` / `PRELOAD=2` 的软件流水，需要**每核至少 3 个任务**才能填满。而 decode 场景任务数常常塌缩到每核 1 个 —— 此时流水完全退化为串行，每次跨核 flag 往返裸露在关键路径上。

**判别**：算 `每核任务数 = totalWork / usedCoreNum`。**< RING_SLOTS 即流水失效**。

**典型塌缩成因**：任务分解式中某个因子退化为 1（如 `topK ≤ 阈值` 时分块数为 1、`Sq=1` 时 query 块数为 1）。

**做法**：见 S4.2（增大 totalWork 是同一个问题的解）。

### S3.3 流水槽深度必须一致

各级 buffer 的槽数要与流水深度匹配。若 state 槽为 3 而 UB ping-pong 仅 2 槽，会强制 AIC/AIV 更紧地交替，削弱预取重叠效果。

**配套契约**：改任何 buffer 槽数，必须同步改流水**预热与排空**两处的信号个数 —— 反向信号（消费者→生产者）在首轮无前驱须预置，退出前须对称消费掉，否则残留 flag 污染后续阶段。

## 4. 并行度与 Tiling 层

### S4.1 GQA group 折叠进 M 轴 【双算子验证，收益最高的通用项】

**问题**：把 GQA 的 group 维当作**分核维度**（外层循环），导致：
- 同一 KV head 被组内每个 query head 各搬一次 → G 倍冗余 GM 往返
- M 维只剩单 head 的少量行，cube M 方向严重不饱满

**度量**：`M 有效利用率 = 实际有效行数 / M 基本块尺寸`。实测某算子 G=1 时 Mmad 的 M=16 里 15 行是 padding → 有效利用率 **0.8%**；G=8 时 6.25%。历史实测佐证：G=128 达 30 TFLOPS，G=64 掉到 19.6 TFLOPS —— **M 维半空吞吐即腰斩**。

**做法**：把 group 维折叠进 BMM1 的 M 轴，G×query 行拼成统一 M 索引，每个 KV 块只搬一次供组内全部 head 复用。

**红线**：
- M 行到 (group, query_pos) 的映射须与 Fixpipe 行主序回写 stride 一致
- softmax 的 max/sum 必须**按 head 独立归约**
- M 尾块按真实有效行数计，不按满块
- **必须配套并行度兜底**：折叠后工作项数除以 G，会加剧 S4.2 的塌陷。`totalWork < coreNum` 时须回退到 group 级调度
- 已知副作用：大 Q 场景可能微退（实测 ~4.5%），建议按 M 块数判断只在小 Q 启用

### S4.2 KV 轴归约分核（stream-K / FlashDecode）

**问题**：分核只按外层维度（batch × kv_head × query块）线性均分。当外层任务数 < 核数时大量核空转，长 KV 的归约压在少数核上串行。实测极端情形：某算子 `Block Num=1` 而快参考 `=32`，**31/32 核完全闲置**。

**做法**：外层填不满时沿 KV 序列方向额外切分，各核算局部（加权输出 + LSE 状态）写中转区，再做轻量二次归约合并。

**红线**：
- 在线合并必须数值稳定重标定：先取全局 max，再按 `exp(局部max − 全局max)` 缩放
- 缩放因子只作用于历史累积项
- 分片数退化为 1 时须与原路径**完全等价**
- 局部状态三元组（O / max / sum）须同坐标存放
- 尾分片单独处理

**门控**：长序列 prefill 场景应自动关闭，无回退损失。

### S4.3 尾块负载均衡

**问题**：纯线性均分（`end = totalWork*(core+1)/coreNum`）把尾块与满块同等计价。

**做法**：
1. 代价表区分尾块（M-normal/tail × KV-normal/tail 的 2×2 表），尾块按真实代价计入
2. 分配容差：允许超出代价上限半个块，避免"差一点就换核"导致核数虚高、尾巴更碎
3. 归约阶段把空闲核借给大归约任务，二次向上取整重算核数
4. 归约阶段可再做行粒度细分

**适用性判断**：序列长度全是基本块整数倍时**收益为零**。评估前先确认用例含非对齐 shape，否则数据上体现不出来。

### S4.4 并行度诊断清单

优化 tiling 前先算这几个数：

| 指标 | 计算式 | 健康阈值 |
|---|---|---|
| 核占用 | `usedCoreNum / 物理核数` | 接近 1 |
| 每核任务数 | `totalWork / usedCoreNum` | ≥ RING_SLOTS |
| M 有效利用率 | `有效行 / M 基本块` | > 50% |
| GM 流量放大 | `实际流量 / 理论最小` | < 1.5 |

## 5. 向量微观层（prefill 场景的富矿）

长序列场景下 AIV 向量计算常是真实瓶颈（实测 1.52×）。以下按"是否已被榨干"分两类。

### S5.1 高价值微观优化

| 技术 | 做法 | 收益来源 |
|---|---|---|
| **输出别名 in-place** | 输出 `SetAddr` 别名到输入缓冲，去掉额外分配 | 零额外 UB + 少一次搬运 |
| **统计量寄存器化** | M 基本块 ≤ 单寄存器容量时，行统计量整寄存器操作，消除逐行更新循环 | 消除循环开销 |
| **除法全融合** | 除法只做一次，融进末轮累加的同一内循环（`Mul`→`Add`→`Div`） | 减少一趟 UB 往返 |
| **列数模板特化** | 关键 VF 改 `template<uint16_t COL_COUNT>` 显式实例化常见列数 | 零精度风险，代价是代码膨胀 |

### S5.2 应已具备的基础项（若缺失则优先补齐）

- `ExpSub` 单条融合指令算 `exp(x−max)`
- 行归约 = 寄存器间 `Max`/`Add` + 寄存器内 `Reduce`，仅 2 条指令
- `[m,1]` 统计量用 load 的广播分发模式完成，不额外调用广播算子
- fp32→fp16 用两个 `RegLayout` + `Or` 三指令合并两个半字槽
- cast 与 ND2NZ 融进 store，靠 block-copy 模式 + blockStride 直出 NZ
- 尾块用谓词 `UpdateMask` 而非 padding
- mask 直接进谓词寄存器 + `Select`，**从不 cast 成浮点**
- 单元素写回用非对齐攒批，Post 操作移出循环
- 用 65/33 之类的奇数 DataBlock stride 解 UB bank 冲突

### S5.3 标量退化实现（隐蔽但代价极高）

**问题**：为绕开某些 API 的布局约束（如 Compare 输出 bit-wise 而 Select 需要 byte-wise），把向量操作退化成逐元素 `GetValue`/`SetValue` 循环。某算子的 causal mask 因此产生 **1024 次标量往返**，而本应是 2 条向量指令。

**识别**：`aiv_scalar_ratio` 显著高于 `aiv_vec_ratio` 即是信号 —— 实测某算子标量是真实向量计算的 **4.4 倍**。

**做法**：修正 mask 布局（谓词化）后改回 `Compare` + `Select`。

### S5.4 标量提壳层

- 标量地址/常量全部提到 `__aicore__` 壳层，VF 签名只收指针 + 标量
- 循环内指针用 post-update 自增，不重算地址
- 循环不变量按"外层是否变化"守卫缓存
- 调度骨架避免每任务重复的非常量除法/取模，改用增量游标与手动环形计数器

> **优先级提示**：AIC 调度骨架标量优化的收益容易**被 AIV 侧瓶颈吞掉**（实测降 280us 而 Task 不变）。应在 AIV 优化完成之后再测。

## 6. 编译期裁剪

- 未使用的可选特性（dropout / PSE / 量化 / sink 等）在特定分支中**编译期钉死为 false**，相关代码完全不生成
- tilingkey 实例数收敛到实际需要的组合，缩短编译时间也减少指令 cache 压力
- mask 全通/全屏时用纯标量前置判断跳过整块搬运

## 7. 实施纪律

### 优先级排序方法

按「可解释 gap 比例」排序，而非直觉：

1. 用**主导路径反推法**：把目标 pipe 降到参考实现水平后，取新的路径上限，算 `(原耗时 − 新上限) / (原耗时 − 参考耗时)`
2. 数据粗糙时退回代码证据强度
3. 明确区分「已具备 / 部分具备 / 缺失」，已具备项要带证据排除

### 分档实施

| 档位 | 特征 | 例 |
|---|---|---|
| 打底项 | 改动局部、风险低，用于验证 build/精度/perf 全流程 | 累加器多缓冲深度自适应、输出别名 |
| 主收益项 | 收益最高、全场景受益 | group 折叠 M 轴 |
| 结构项 | 需同时改 host + kernel，**每轮限 1 个** | KV 轴分核、CV 直连改造 |

**每次只改一项，测量，验证，再决定采纳或回退。**

### 通用红线

- **数值稳定性**：任何涉及 online softmax 合并的改动，必须先全局 max 再 exp 缩放
- **退化等价**：分片数/组数退化为 1 时必须与原路径完全等价
- **尾块真实性**：所有维度的尾块按真实有效长度计，不按满块
- **早退补信号**：分到 0 行的核在早退路径**必须**补齐跨核信号，否则死锁
- **flag id 预算**：手工分配的 event id 与框架自动分配（如 `MAKE_ID % 11`）可能撞号；AIC 与 AIV 侧 buffer 构造顺序必须完全一致
- **隐式耦合**：多缓冲池的 ping/pong 游标可能依赖特定的调度交替序列，改流水深度会**静默算错** —— 建议加 `static_assert` 固化前提

### 容易做错的判断

| 误判 | 实情 |
|---|---|
| `aic_scalar_ratio` 高 → 标量受限 | 多为跨核等待被计入 scalar pipe；看 mac/mte1/fixpipe 是否同时低 |
| 代码有 N 倍重复搬运 → 有 N 倍收益 | 可能已被 L2 掩盖；先看 `mte2_time` 比值 |
| 硬编码硬件参数 → 性能缺陷 | 快实现 kernel 侧往往同样硬编码；这是**可移植性**议题，非性能项。但要留意核数被常量截断导致换 SKU 浪费核 |
| 换用主线 matmul 框架会更快 | 已证伪：±0.15% 噪声，整体回退 |

## 8. 快速诊断流程

```
1. 采 profiling（Level2 + PipeUtilization），确认 shape/dtype 公平对比
      ↓
2. 看 aic_mac_ratio
   ├─ ≈0.9+  → 已健康，只剩微观优化（§5）
   └─ 低     → 继续
      ↓
3. 看哪条 pipe 打满
   ├─ aic_scalar 打满而 mac/mte1/fixpipe 全低 → 是"在等"，瓶颈在对侧核
   ├─ aiv_vec 高      → 向量计算效率（§5）
   ├─ aiv_mte2/mte3 高 → 搬运（§2），检查是否离散 gather
   └─ aiv_scalar 高    → 标量退化实现（§5.3）
      ↓
4. 算并行度四件套（§4.4）
   ├─ 核占用低      → KV 轴分核（§4.2）
   ├─ 每核任务 < RING → 流水失效（§3.2），增大 totalWork
   ├─ M 利用率低    → group 折叠 M 轴（§4.1）
   └─ GM 放大 > 2   → 数据流架构（§1）
      ↓
5. 按 gap 可解释比例排序，分档实施，每次一项
```
