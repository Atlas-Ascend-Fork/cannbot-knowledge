# 方法论策略：发射受限 vs 带宽受限的判定探针（改搬运量、不改发射数）

> **单一方法点：** 当 profiling 显示某个搬运管线 ratio 很高（如 `mte2_ratio = 0.82`）时，**不能**据此断定"带宽已饱和"。该数值只说明"这条管线忙"，不说明**忙在什么上**。用一个 10 分钟的探针即可判定：
>
> **人为改变每次搬运的字节数（×2 或 ÷2），保持发射指令数完全不变**，然后看耗时如何变化：
> - 耗时**近似正比**于字节数 ⇒ **带宽受限**：减少发射次数无用，只能减少数据量；
> - 耗时**几乎不变** ⇒ **发射受限**：带宽有余量，**减少发射次数 / 摊薄发射依赖链才是杠杆**。
>
> 探针会算出错误结果（故意的），只用于测时间，测完立即回退。
>
> **已验证锚点：** A5(Ascend950DT) SparseFlashAttention，实测**搬运量翻倍耗时仅 +2%、减半反而慢 6%** ⇒ 发射受限、带宽有 1 倍以上余量。该结论**推翻了此前"已到物理下界"的判断**，并直接导出了后续 −5.5% 的优化（策略 02 的展开度再调优）。

---

## 1. 为什么需要这个探针

### 1.1 profiling 的 ratio 是有歧义的

`mte2_ratio = 0.82` 可能意味着两件完全不同的事：

| 解释 | 含义 | 应对手段 |
|---|---|---|
| 带宽受限 | 数据传输本身占满了带宽 | 减少数据量（压缩、复用、去重）；减少发射次数**无效** |
| 发射受限 | 指令发射/延迟占满了时间，数据量远未跑满带宽 | 减少发射次数、摊薄依赖链、加深展开；减少数据量**无效甚至有害** |

**两种解释导向完全相反的优化方向。** 不判定就动手，有 50% 概率做无用功。

### 1.2 常见的错误推断

一个典型的错误链：

```text
观察：case 要 gather 4.3GB，而 baseline 只用 795µs
推断：795µs 搬完 4.3GB 需要 5.4TB/s，物理上不可能
结论：baseline 一定不是逐行 gather 架构；我们已到物理下界
```

**这条推断的隐含前提是"时间正比于搬运字节数"（即带宽受限），而该前提从未被验证。**
实测证明前提为假 ⇒ 整条推断作废。

> **教训：任何"字节数 ÷ 时间 = 所需带宽"的反推，都必须先验证"时间正比于字节数"。**

---

## 2. 探针设计

### 2.1 核心要求

| 要求 | 说明 |
|---|---|
| **只改字节数，不改发射数** | 循环结构、迭代次数、指令条数完全不变，只改每条指令搬多少 |
| 不改地址计算 | 源/目的地址公式不变，避免引入其它变量 |
| 不改同步 | 同步结构完全不动 |
| 允许结果错误 | 探针**故意**算错，只测时间；测完立即回退 |

### 2.2 实现

```cpp
// 基线
for (i...) {
    DataCopy(dstUb[i * dstStride], srcGm[addr(i)], len);
}

// 探针 A：搬运量减半（发射数不变）
const uint32_t probeLen = len / 2;          // ← 只改这里
for (i...) {
    DataCopy(dstUb[i * dstStride], srcGm[addr(i)], probeLen);
}

// 探针 B：搬运量翻倍（发射数不变）
const uint32_t probeLen = len * 2;          // ← 只改这里
for (i...) {
    DataCopy(dstUb[i * dstStride], srcGm[addr(i)], probeLen);
}
```

> **翻倍探针的越界风险**：`len*2` 可能读出源数据范围。若目的 buffer 行距足够（如 `dstStride ≥ 2*len`）且源侧有后续数据可读，通常不会触发非法访问；否则改用"减半"探针 + 一个更小的第三点（如 `len/4`）来定趋势。**探针不进入正式代码，但仍不应制造非法访问。**

### 2.3 测量纪律

- 每个探针点**重复 ≥3 次**，取样间隔足够长（避免冷启动尖峰）；
- 三个点（`len/2`、`len`、`len*2`）都测，看**趋势**而非单点；
- 精度必然失败（探针故意算错），**不看精度**，只看性能数字；
- 测完**立即回退**到基线，确认回退后性能恢复。

## 3. 判读

### 3.1 判读表

设基线耗时为 `T`：

| `len/2` 的耗时 | `len*2` 的耗时 | 结论 |
|---|---|---|
| ≈ `0.5T` | ≈ `2T` | **带宽受限**（纯粹） |
| ≈ `0.8T` | ≈ `1.3T` | 混合，偏带宽 |
| ≈ `T` | ≈ `T` | **发射受限**（纯粹） |
| **> `T`** | ≈ `T` | **发射受限**，且当前 `len` 已在效率拐点上 |

### 3.2 实测实例

| 每行搬运量 | s256 (µs) | s1024 (µs) | 相对基线 |
|---|---|---|---|
| 128B（减半） | 513.2 / 520.8 | 4433 / 4437 | **+7% / +6%** |
| **256B（基线）** | **479.7** | **~4200** | — |
| 512B（翻倍） | 510.9 / 511.1 | 4278 / 4335 | +6% / **+2%** |

判读：

1. **翻倍只涨 2%** ⇒ 数据量翻倍几乎不要钱 ⇒ **发射受限，带宽有 1 倍以上余量**；
2. **减半反而慢 6~7%** ⇒ 当前 256B 已在效率拐点上，更小的传输无法摊薄固定开销。

### 3.3 从判读到行动

| 判读 | 应做 | 不应做 |
|---|---|---|
| 带宽受限 | 减少数据量：去重、复用、压缩、降精度 | 加深展开、合并发射（无效） |
| 发射受限 | 摊薄发射依赖链（策略 02）、减少发射次数、每次多搬 | 减少数据量（无效）；也不要盲目减小传输粒度 |

## 4. 发射受限确认后的连锁推论

一旦确认是发射受限，以下推论随之成立，可直接用于筛选后续候选：

| 推论 | 用途 |
|---|---|
| "每次发射多搬点几乎免费" | 可重新评估此前因"搬运量放大"而否掉的方案 |
| "减少发射次数是唯一有效杠杆" | 聚焦发射数，不再优化字节数 |
| "此前基于带宽的推算全部作废" | 重审所有"×带宽"的定量结论 |
| "同一循环的 scalar 与 mte2 高 ratio 是同一条链的两面" | 不要当作两个独立瓶颈分别优化 |

⚠️ 但注意：**"多搬几乎免费"不等于"合批一定划算"**。若多搬需要取索引并集，并集膨胀会同时放大算力与容量代价（见策略 08）。推论只解除"搬运量"这一个约束，其它约束仍需各自核算。

## 5. 已知陷阱

### AP-001：用 ratio 直接下"饱和"结论

问题：见 `mte2_ratio = 0.82` 即断言带宽饱和。
症状：后续所有优化方向被错误锁定。
修复：本策略的探针，10 分钟即可判定。

### AP-002：探针同时改了发射数

问题：为了改搬运量，顺手把循环步长/迭代次数也改了。
症状：两个变量同时变，无法归因。
修复：**只改 `len` 一个量**，循环结构逐字不动。

### AP-003：只测一个方向

问题：只测翻倍，不测减半。
症状：漏掉"减半反而更慢"这一信息（即当前粒度是否已在拐点）。
修复：三点都测。

### AP-004：探针代码流入正式提交

问题：探针会算错结果，若误提交则引入静默错误。
修复：探针前先备份基线文件；测完立即 `cp` 回；提交前 `diff` 确认。

### AP-005：把探针的精度失败当成 bug 去查

问题：探针必然精度失败（故意的），却花时间去 debug。
澄清：探针**只看性能数字**，精度失败是预期行为。

## 6. 实施前必须回答的问题

| 问题 | 必填内容 |
|---|---|
| 目标循环 | 哪个搬运循环；当前每次搬多少字节；发射多少次 |
| 探针点 | 计划测哪几个 `len`（至少 3 点） |
| 越界检查 | 翻倍探针是否会越界；目的行距是否足够 |
| 备份 | 基线文件备份路径 |
| 测量 | 每点重复次数；取样间隔 |
| 回退验证 | 回退后是否复测确认性能恢复 |

## 7. 验收标准

```bash
cp <kernel>.h /tmp/baseline.h                  # 1. 备份
# 2. 注入探针（只改 len）
bash <build> ... --wheel 2>&1 | grep -cE "error:"
for i in 1 2 3; do <run perf>; done            # 3. 每点重复 ≥3 次（不看精度）
cp /tmp/baseline.h <kernel>.h                  # 4. 立即回退
bash <build> ... --wheel && pytest ... -q      # 5. 确认精度与性能恢复
diff <kernel>.h <archived>.h                   # 6. 确认无探针残留
```

产出：一张 `搬运量 → 耗时` 表 + 明确的判读结论（发射受限 / 带宽受限 / 混合）。

结论须写清：

```text
判定方法：改每次搬运字节数、保持发射次数不变，看耗时是否正比于字节数。
实例结论：翻倍 +2%、减半 +6% ⇒ 发射受限，带宽有 1 倍以上余量，256B 已在拐点。
该结论推翻了此前基于 "字节数 ÷ 时间 = 所需带宽" 的全部推算——
那条推算的隐含前提（时间正比于字节数）从未被验证，且为假。
后续方向应聚焦发射次数与依赖链，而非数据量。
```
