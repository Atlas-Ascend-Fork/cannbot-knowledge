# 性能优化策略：结构化掩码下的归约块裁剪

> 单一优化点：在任务生成阶段，根据结构化单调掩码为每个查询块推导保守的联合可见终点，并跳过完全不可见的归约块；边界块仍保留原有精确掩码。

## 1. 原理

当掩码具有可由序列位置推导的单调可见区域时，查询块不必执行完全不可见的归约块。对查询块内所有行求一个保守的联合可见终点，再只生成终点之前的归约块；终点所在的边界块仍按原有逐元素掩码处理。

通用语义伪代码：

```text
对每个查询块：
  可见终点 = 保守计算该块所有行的联合可见范围
  可见终点 = 限制到有效键序列范围
  归约任务数 = 向上取整除(可见终点, 归约块宽度)
  仅调度这些归约任务
```

若实现含独立的 group-major 查询轴，必须先对**每个 group** 的查询长度分块，再乘 group 数：

```text
每组查询块数 = ceilDiv(queryLength, queryTileRows)
group-major 查询块总数 = groupCount * ceilDiv(queryLength, queryTileRows)
```

禁止先合并 group 与 query 轴再向上取整。host 线性化、kernel 解码、prefix 边界恢复和任务描述符
构造必须从同一个“每组查询块数”定义派生，不能各自复制近似公式。

## 2. 性能问题模式

- 归约轴很长，但结构化掩码使后半段整块对当前查询块完全不可见。
- 任务生成仍按完整归约长度计数，导致矩阵、向量、搬运和流水槽处理无效块。
- 已有精确掩码只能保证结果正确，不能避免整块无效任务的调度与执行成本。

本策略只减少可证明无效的任务数量；不改变块大小、矩阵公式、在线归约公式或边界块的元素级掩码。

## 3. 正确性红线

- 可见终点必须是查询块内全部行可见范围的保守并集；不能只按块首行推导而漏掉后续行。
- 必须纳入矩形查询与键序列的相对偏移，不能假定两条序列从同一逻辑位置开始。
- 终点必须限制在有效键长度内，并正确处理尾块和每批不同的有效长度。
- 任务数必须使用向上取整除，使含有任一可见元素的边界归约块保留下来。
- 保留的边界块仍必须执行原有精确掩码；本策略不以块级裁剪替代元素级掩码。
- 推导后无归约工作的查询块必须有合法的空工作路径，不得访问未初始化状态或产生悬空任务。
- 在线归约的首块、末块标志以及状态初始化和最终写回，必须以裁剪后的任务数为准。
- 环形流水、跨核任务数、槽位释放和信号收发必须随裁剪后的任务数一致更新，不能遗留等待或提前复用。
- 环形槽位数必须与 host 分配的每个按槽索引的 GM workspace 槽位数相等；不能仅因缓冲被称作
  ping-pong 就按双缓冲容量分配多级流水。
- 多 group 的短查询用例若仅一个 group 正常而其余 group 整体失败，失败比例接近
  `(groupCount - 1) / groupCount`，应先检查 group-major 任务轴覆盖，不能直接归因于掩码数学。
- 非结构化掩码、不能证明单调可见区域的掩码，以及非因果路径不得应用此裁剪。

## 4. 泛化条件

### 适用前置条件

- 掩码语义能证明某个查询块在归约轴上存在连续的可见前缀，或等价的可安全上界。
- 归约块按逻辑键位置顺序处理，且同一查询块的在线状态在保留任务间连续。
- 调度层可在执行前改变该查询块的归约任务数量，并能同步更新相关任务元数据。
- 若存在 group-major 查询轴，group 数、单 group 查询长度和查询块高必须可独立取得；任务总数采用
  `groupCount * ceilDiv(queryLength, queryTileRows)`。
- host 与 kernel 必须共享同一任务轴语义；prefix 边界能够无损恢复 group 与 query-block 坐标。
- host 能按实际环形流水深度为所有按槽索引的 GM workspace 分区分配容量。

不适用于任意稀疏、数据相关或可见位置不连续的掩码；也不适用于裁剪会改变既有跨核归约语义的实现。

## 5. 实施步骤

1. 确认掩码属于可从查询位置、键位置和序列偏移推导的结构化单调形式。
2. 在任务生成前，对每个查询块计算覆盖全部行的保守联合可见终点，并限制到该样本的有效键长度。
3. 以向上取整的块数替换完整归约轴的任务数，只生成完全可能可见的任务。
4. 用新的任务数重建首末标志、空工作处理、流水槽计数及跨核同步计数。
5. 保留边界块内的原始精确掩码和原始尾块处理。
6. 对非结构化或非因果分支保持原任务数和原调度路径。

### 实施检查清单

- [ ] group-major 总任务轴使用 `groupCount * ceilDiv(queryLength, queryTileRows)`；禁止先合并
  group 与 query 轴再向上取整。
- [ ] host 任务总数、kernel 解码、prefix 编码/恢复和任务描述符构造使用同一个 query-block 定义。
- [ ] 覆盖 `groupCount > 1` 且 `queryLength < queryTileRows` 的最小用例，确认每个 group 至少有一个任务。
- [ ] 多 group 用例按 group 统计失败；出现 `(groupCount - 1) / groupCount` 指纹时先审计任务覆盖。
- [ ] 对每个按槽索引的分区验证“环形槽位数 == GM workspace 槽位数”，并覆盖最大合法槽位。
- [ ] 首末标志、空工作路径、跨核 prefix、slot release 和信号基数均以裁剪后的连续任务列表为准。

## 6. LLM 前置问题

1. 掩码是否能证明为每个查询块提供连续可见区域的保守上界？
2. 查询和键长度是否可能不同，是否存在相对序列偏移或每批可变长度？
3. 在线归约状态、首末标志、环形槽位和跨核信号分别由哪里按任务数驱动？
4. 边界归约块是否仍会走精确元素级掩码？
5. 哪些掩码类型或执行分支必须明确回退到未裁剪路径？
6. group-major 任务总数是否按单 group 先分块，且 host/kernel/prefix/任务构造是否同源？
7. kernel 环形流水深度与 host 的所有 GM workspace 槽位乘数是否完全一致？

## 7. 验收标准

- 构建通过，且结构化掩码、矩形序列、尾块、可变长度和空工作测试与基线结果一致。
- 非因果和非结构化掩码路径结果及性能不回退。
- 任务记录证明完全不可见的归约块不再进入执行流水，同时边界块仍接受精确掩码。
- 多 group 短查询用例覆盖全部 group，不出现接近 `(groupCount - 1) / groupCount` 的整组缺失。
- 环形流水的最大合法槽位访问落在所属 GM workspace 分区内，且不与相邻分区别名。
- 长归约轴且存在大段完全不可见后缀的场景获得可重复的端到端性能改善。
