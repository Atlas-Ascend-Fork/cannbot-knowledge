# 性能优化策略：增大归约维计算块以缩短串行依赖链

> 单一优化点：当矩阵乘沿归约维执行大量细粒度的“搬运右操作数、格式变换、矩阵计算”串行链，且更大计算块能够在目标硬件片上容量内驻留时，合并相邻归约块，减少循环次数和每块固定调度开销。

---

## 1. 原理

定义两个术语：

- **归约维计算块**：一次搬入片上并参与矩阵乘累加的连续归约维区间。
- **依赖链固定开销**：每个计算块都要重复支付、但不随块内有效计算量等比例增长的搬运发射、格式变换、同步和矩阵指令调度开销。

若归约总长度不变，把相邻的两个小计算块合成一个大计算块，循环次数近似减半。有效乘加总量基本不变，但每块固定开销和串行依赖节点数减少。该策略的收益来自“减少固定开销”，不是减少数学计算量。

块大小不是越大越好。更大计算块会同时提高片上存储占用、单次搬运长度和尾块浪费；当容量接近上限时，还可能迫使其他缓冲退化或失去流水空间。因此必须把容量判定作为启用条件，而不是把某个已验证块大小写成通用常量。

## 2. 性能问题模式

适用时通常同时出现以下指纹：

- 归约维较长，内层循环次数多。
- 每轮都按相同顺序执行右操作数搬运、布局变换和矩阵计算，前后轮存在严格依赖。
- 剖析中搬运或标量调度占比明显，矩阵计算单元没有被单次大块计算充分摊薄。
- 估算显示增大计算块后乘加总量不变，而循环次数和搬运发射次数显著下降。
- 目标硬件片上缓存能够容纳放大后的操作数块及所有并存缓冲。

低效形态可抽象为：

```python
for small_reduce_tile in reduce_tiles:
    right_onchip = load_and_transform(small_reduce_tile)
    accumulator = matmul_accumulate(accumulator, right_onchip)
```

调整后：

```python
for merged_reduce_tile in merged_reduce_tiles:
    right_onchip = load_and_transform(merged_reduce_tile)
    accumulator = matmul_accumulate(accumulator, right_onchip)
```

## 3. 正确性红线

### 3.1 容量必须按目标硬件查询

计算放大后所有同时存活的 L1、L0 和队列缓冲峰值，并与目标硬件真实容量比较。不得沿用其他芯片或历史任务中的容量常量。若恰好顶满容量，必须视为零余量方案：编译器临时缓冲、对齐膨胀或后续改动都可能使其失效。

### 3.2 尾块必须保持原有有效范围

归约长度不能整除新块大小时，最后一块的有效元素范围、补零范围和全局内存访问边界必须重新计算。不得用放大后的满块长度读取越界数据，也不得把无效尾部参与累加。

### 3.3 累加语义不能被附带改变

本策略只改变计算块粒度，不改变输出分块、原子累加范围、数据类型、舍入模式或跨核归约顺序。若底层接口因块大小变化而改变浮点累加顺序，必须执行全量精度验证，不能只验证单个代表形状。

### 3.4 不得挤占必要流水槽位

若放大单块需要减少队列深度、取消双缓冲或复用仍被异步指令占用的槽位，应把这些变化拆成独立候选评估。不能把多个机制混入同一次修改后把收益都归因于计算块放大。

### 3.5 先决反指纹（2026-09-22 新增）

任一命中则本策略收益≈0，**选路阶段即排除**（不必进入实现）：

- **K-loop 固定开销已被既有软件流水/双缓冲隐藏**：搬运与矩阵乘已重叠时，循环次数下降不改变墙钟（收益份额≈0）。
- **L0 容量已零余量**：块大小无放大空间，放大即越界。
- **瓶颈在输出向量后处理 / 跨核负载不均 / 主机开销**，与归约循环无关。

成功轮证明：K 链开销真实存在时可拿到 1.14-1.32×（linalg_matmul 1.3244、mkldnn_linear 1.2194、linear_selu_sigmoid 1.1366）；未命中反指纹且归约维足够长时才应选。

## 4. 泛化条件

满足以下条件时可以进入候选：

- 目标是沿归约维分块的矩阵乘或同构 cube 计算。
- 当前块大小导致较多串行循环，固定开销可见。
- 放大后的片上峰值容量可证明不超限。
- 新块大小满足底层矩阵指令、搬运和布局变换的对齐要求。
- 代表性形状包含足够长的归约维，能够观察循环次数下降后的收益。

以下情况不适用：

- 归约维很短，原本只有一到两轮。
- 当前瓶颈在输出向量后处理、跨核负载不均或主机开销，与归约循环无关。
- 放大后必须牺牲关键双缓冲，且净收益没有独立证据。
- 尾块占比很高，放大主要增加无效计算。
- 片上容量只能依赖未验证的假设才能成立。

## 5. 实施步骤

1. 记录基线归约块大小、循环次数、每轮搬运字节数和并存缓冲峰值。
2. 查询目标硬件各级片上容量，按对齐后的实际字节数计算候选块大小。
3. 只修改归约维块大小及其直接派生的循环次数、搬运长度和尾块范围。
4. 保持输出分块、同步协议、队列深度和累加类型不变，避免混入其他优化。
5. 编译并先跑容量边界、非整除尾块和最小归约维用例。
6. 通过精度后，对长归约维主场景做交错 A/B/A 测量，并核对循环次数或指令发射次数确实下降。
7. 若收益只在单一形状出现，为块大小增加形状门控并保留原路径回退。

## 6. LLM 前置问题

以下问题任一无法回答时，不实施：

1. 当前内层循环的串行依赖链由哪些阶段组成，固定开销证据是什么？
2. 候选块大小使循环次数、搬运发射次数分别下降多少？
3. 放大后每一级片上存储的峰值占用是多少，目标硬件容量从何处查询？
4. 尾块、对齐和补零逻辑需要怎样调整？
5. 是否无意改变了队列深度、同步协议、输出分块或累加顺序？
6. 哪些形状预计无收益，回退条件是什么？

## 7. 验收标准

- **构建**：目标硬件编译通过，无片上容量、队列或矩阵指令参数错误。
- **精度**：覆盖整除、非整除、短归约维、长归约维和容量边界形状；全部满足算子既有误差标准。
- **性能**：以稳定 kernel 时间为主指标，交错 A/B/A 测量后候选仍优于基线；同时确认循环或依赖链节点数按预期下降。
- **归因**：矩阵乘总计算量和输出语义不变，收益可归因于固定开销减少，而不是短路计算、跳过尾块或改变精度。
- **回退**：不满足容量、对齐或收益条件的形状继续走原块大小路径。
