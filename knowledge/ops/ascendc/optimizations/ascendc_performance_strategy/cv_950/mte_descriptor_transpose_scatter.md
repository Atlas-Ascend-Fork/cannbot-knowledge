# 性能优化策略：转置折入搬运描述符（列组跨距装载 + 逐行跨距源散写）

> 库内状态：`active`。已进入可选择策略库并纳入自动路由。来源为另一批同域任务的独立探索轨迹脱敏归档（与「显式向量索引转置」卡面向同一瓶颈的替代机制）：单一 Campaign 内完成构建（1 修复）、全量精度（22/22，2 修复后逐字节等价）与正式稳定配对验证（2 对平衡交替、全部用例在每对两 run 中均更快），全集相对加速 2.6197。修复轮约束已并入 §3 红线；验证记录见 §7。

> 单一优化点：转置阶段由向量管承担（微码原语或向量指令流）成为吞吐墙时，把转置整体移入搬运引擎的二维描述符：装载侧按列组发跨距搬运（块数 = 行数、块长 = 组宽字节、源步距 = 行距−组宽、目的步距 = 0），宽元素类型用原地低位掩码把目标字节折到元素偏移 0，写出侧每输出行一笔跨距源散写（块长为单字节粒度、源步距按源俯仰量化单位换算）；窄元素类型路径全程零向量指令。

---

## 1. 原理

- **引擎分工重排**：转置的「跨距」语义改由搬运描述符表达——装载侧每列组一笔二维跨距搬运把一列组按行拼入片上（片上行俯仰按对齐粒度取整），写出侧每输出行一笔「跨距源、连续目的」散写。向量管只剩宽类型的低位折叠（一次原地掩码 + 一次栅障），窄类型完全无向量工作。
- **两侧步距语义不对称**：全局内存侧步距为字节粒度；片上侧步距按固定粒度量化并向上取整。同一行距在两侧的编码值不同，必须分别从架构契约推导，不得互套。
- **跨管依赖显式化**：装载 → 写出的先后序不能由深度为 0 的队列或裸缓冲建立，需要显式跨管事件对（装载完成事件 → 标量等待 → 写出发射；写出完成事件 → 槽复用守门），尾部逐槽排空保证全局写可见与配对平衡。
- **补零契约**：行数不足整块的尾部补零由零缓冲逐行散写维持原口径。

**定性归因**：向量管转置指令全部消失，kernel 时间移向搬运发射与数据速率；全部用例一致改善。这是判断本策略是否对症的主判据。

## 2. 性能问题模式

低效形态：

```python
# 前：转置在向量管（微码原语 / 指令流），向量管吞吐墙
for tile in tiles:
    load_rows(tile)                    # 连续装载
    transpose_on_vector(tmp, rows)     # ← 向量管每元素成本主导
    store_rows(tmp)

# 后：转置折入搬运描述符，窄类型零向量指令
for tile in tiles:
    for g in column_groups:            # 每列组一笔二维跨距装载
        gather_load_2d(ub[g], gm, blocks=rows, blocklen=grp_w, srcstride=pitch-grp_w, dststride=0)
    widen_fold_low_byte_if_needed()    # 仅宽类型：一次原地掩码折叠
    for j in out_rows:                 # 每输出行一笔跨距源散写
        scatter_store_2d(gm_row(j), ub_col(j), srcstride=pitch_q - 1)
```

指纹：

- 转置段随元素量近线性主导（与「显式向量索引转置」卡共享该指纹）。
- 已知收集微码吞吐或向量管速率存在墙，而搬运引擎利用率低、发射速率有富余。
- 搬运接口支持两侧所需的二维跨距形态（源步距字节粒度 + 目的侧量化俯仰）。

## 3. 正确性红线

### 3.1 搬运源地址最小对齐（最易翻车）

写出侧的片上源地址必须满足最小对齐粒度；「块内字节偏移源」形态可触发设备错误。列组装载产出的片上行俯仰必须恰好满足该对齐（取整公式闭环）。

### 3.2 尾组俯仰公式同时匹配两引擎

组宽非整组（尾组）时，片上俯仰取整公式必须同时匹配装载侧与写出侧的量化语义；不匹配即行错位（首行正确、后续行脏读是该类错误签名，参见「行块级带源步距批量写」卡的单位契约纪律）。

### 3.3 跨管事件配平

装载/写出跨管依赖用显式事件对逐槽建立；Set/Wait 必须配对，尾部排空补齐未配平槽，防止过期置位与写可见性问题。

### 3.4 宽类型低位折叠的小端前提

「目标字节折到元素偏移 0」依赖小端序前提；大端或非零偏移布局需要重新推导折叠位置。折叠掩码是原地操作，其后的一次栅障不可省（掩码写 → 散写读的管间序）。

### 3.5 数值等价

数据内容只被重排与按位掩码折叠：输出与基线逐字节等价；任何字节差异优先排查 3.2/3.4。

### 3.6 补零写契约

尾部补零逐行散写的目标区与字节数必须与原口径一致，不得因通路重构吞掉补零差异。

## 4. 泛化条件

必须同时满足：

- 转置在向量管且为吞吐墙；搬运引擎发射/带宽有富余。
- 搬运接口支持「全局侧字节粒度源步距」与「片上侧量化俯仰」的二维形态。
- 跨管事件对可用且预算充足（逐槽）。
- 片上源/目的地址最小对齐可满足。

禁止条件（任一即不实施）：

- 步距单位与量化契约无法从目标架构确认（3.2 前置失败）。
- 对齐不满足且无重排方案。
- 搬运引擎已是瓶颈（把转置移入反而加重）。
- 逐行散写发射速率在极宽输出形态下将成为新墙且无合并方案（可叠加整面板写卡）。

## 5. 实施步骤

1. 确认转置向量管墙与搬运引擎富余（占比 + 引擎利用率证据）。
2. 从架构头文件/接口契约确认读写两侧步距单位、量化取整与最小对齐。
3. 推导列组装载（块数/块长/源步距/目的俯仰）与逐行散写（源步距换算）参数，做「编码—反算」闭合自检。
4. 宽类型插入原地低位折叠 + 栅障；窄类型直接散写。
5. 以显式跨管事件对组织装载→散写序，尾部逐槽排空。
6. 保持 host tiling/分配、全局内存读/写各一次契约、补零口径零改动。
7. 覆盖尾组、尾行、非整块、多 dtype 的精度（预期逐字节等价）与平衡交替配对性能验证。

## 6. LLM 前置问题

1. 转置段的向量管占比与搬运引擎利用率各是多少？移入搬运后的发射数预算是多少？
2. 所用搬运接口读写两侧的步距单位与量化取整规则是什么（从契约确认）？反算是否闭合？
3. 片上俯仰是否恰好满足写出发侧的最小对齐？尾组俯仰公式如何同时匹配两引擎？
4. 跨管事件预算够逐槽配对吗？尾部排空在哪里补齐？
5. 宽类型的字节折叠位置依赖什么端序前提？补零写口径是否保持？
