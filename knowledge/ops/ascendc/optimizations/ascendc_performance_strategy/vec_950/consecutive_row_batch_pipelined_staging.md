# 性能优化策略：连续多行批处理 + 预发射软件流水

> 单一优化点：当每个工作项只处理"一行"且行字节不大时，每个工作项都要付"一条搬运描述符 +
> 一次向量调用 + 一次 V↔S 同步 + 一次队列往返 + 一次标量收尾"的固定成本。把 **K 个连续行
> 合成一个 staging 块**（一条描述符 + 一次向量调用内循环 K 行 + 一次同步 + 一次批量写出），
> 并**在取走当前块之前先预发射下一块的搬运**，让搬运与向量计算重叠。

---

## 1. 原理

每项固定成本的来源（行字节只有几百 B~几 KB 时占比极高）：

| 成本 | 说明 |
|---|---|
| 描述符 | 每项至少一条 `DataCopyPad`（即便行字节很小） |
| 向量调用 | 每次 `asc_vf_call` 有固定的启停/参数装载成本 |
| 同步 | 向量结果给标量读之前必须 V→S；每项一次就是每项一段空转 |
| 队列往返 | `AllocTensor / EnQue / DeQue / FreeTensor` 每项一轮 |
| 收尾 | 每项一次标量读结果 + 一次输出入队 |

把 K 行合并后，以上 5 项全部变成"每 K 项一次"，而向量侧只是把原来的行循环搬进一次调用内
（逐行重置寄存器状态），计算量不变。

**行基址的 32B 对齐（关键）**：搬运的 Normal 模式会把每个 UB 块按 `ceil32(blockLen)` 推进。
因此**用 `blockCount=K` + 每行一个块**（块内连续时 `srcStride=0`），UB 里每行的起点天然是
32B 对齐，向量 `LoadAlign` 才能直接用；若图省事用"一整段连续拷贝"（`blockCount=1`），
行基址 = 行字节 × r，非 32B 对齐 → **向量核异常**（该异常不报错在代码层，极难定位）。

**批大小的上界**：K 由"整块能放进一个 staging 容量"决定，并**留出一个向量长度的尾部余量**
（向量按 256B 载入，最后一段会读到行尾之后最多 255B；这段越界读必须仍落在缓冲区内）。
再叠加约束：K ≤ 每核剩余项数、K ≤ 输出批量上限。

**预发射流水（第二半收益）**：深度 2 的队列天然只能容纳 2 块，因此顺序必须是
**先 `DeQue` 当前块、再 `Alloc` + 发下一块**（反过来会要求第 3 个槽位，直接卡死/异常）；
并且**空闲核必须跳过前导发射**（否则会构造 0 或负长度的描述符）。

瓶颈类型：固定开销（描述符/同步/队列往返）/ 访存-计算未重叠（ripe for overlap）。

## 2. 性能问题模式

- 工作项数远大于并发度，但每项数据很小（每项几百 B~几 KB）；
- profile 显示标量/同步占比高、DMA 有效带宽很低、向量利用率不高；
- 代码形态：`for (item) { DataCopyPad(...); asc_vf_call(...); SetFlag/WaitFlag(V_S); scalar get; push }`；
- 单行数据完全放得进一个 staging 容量（否则本策略退化）。

## 3. 正确性红线

1. **行基址必须是 32B 对齐**：用"每行一个块"的搬运形态（`blockCount=K`），依赖 Normal 模式
   的 `ceil32(blockLen)` 推进；不要用整段连续拷贝代替（除非行字节恰为 32 的倍数且确认过）。
2. **尾部向量读要留余量**：缓冲容量至少 行数 × 行距 + 一个向量长度；否则越界读。
3. **排队顺序**：`DeQue` 必须先于下一块的 `Alloc`（深度 2 时），否则无槽可用。
4. **空闲核跳过前导**：核的工作区间可能为空（工作项数少于核数×每核项数），前导发射必须
   先判空，否则会发出长度非法/为负的描述符。
5. **唯一写者**：批内每行只由一个核写；批边界不得与别的核重叠。
6. **整行放得进一个 staging 容量**才可批处理；否则必须保留"跨块状态 + 合并"的旧路径
   （不能假设单块即完整行）。
7. **状态逐行重置**：向量调用内循环多行时，运行态（值/位置/NaN 位置）必须在每行入口重新初始化；
   只有设计上要求"跨行延续"时才保留。
8. **向量结果给标量读之前**：一次 V→S 同步覆盖整批；但批内多条 VF 调用之间不要再插不必要的同步。

## 4. 泛化条件

- **适用**：行结构明显（行数 ≫ 并发）、行字节较小、整行可入 staging；逐行独立、无跨行依赖；
  每行需要"载入→计算→写回"的完整流水。
- **不适用 / 收益低**：
  - 行字节已经很大（单行就能打满搬运带宽）：合并只增加缓冲压力，没有多少固定开销可摊；
  - 行数很少（≤ 并发度）：批处理没有可合并的邻居，应改为"一项多核"或增大并行粒度；
  - 归约轴本身就跨行（转置型归约）：这里的"行"不是独立工作项，需要另一套切分。
- **可叠加**：更深的输入流水（需要同步重算缓冲预算）、行内循环展开（提高访存并行）、
  批量写回（一次写出整批结果）。

## 5. 实施步骤

1. 量化固定开销：按"每项一次"的成本列清单（描述符/向量调用/同步/队列/收尾），确认它在总时长里
   占主导；否则先做别的。
2. 定批大小 K：由 staging 容量、行距、尾部余量、每核剩余项数共同决定；输出批量上限也要考虑。
3. 行距与对齐：行距 = `ceil32(行字节) / 元素字节`；搬运用 `blockCount=K, blockLen=行字节,
   srcStride=0(块内连续), dstStride=0`。
4. 向量调用内循环 K 行：每行重置运行态，复用同一套索引/常量寄存器；结果按行写到 32B 对齐的
   槽位（每行 2~3 个槽：值 / 位置 / 附加标记）。
5. 收尾：整批只做一次 V→S；标量侧按行读需要的槽位并入队；批量写回。
6. 预发射：前导发第 0 批 → 循环「DeQue 当前批 → 发下一批 → 计算当前批 → Free 当前批」→ 收尾。
   空闲核直接返回（但仍要 flush 自己的输出队列，如果接口要求）。
7. 回退路径：整行放不进一个容量时，保留原逐块路径；两条路径用同一个"行是否可入块"判据分派。

## 6. LLM 前置问题

- 每个工作项的数据量有多大？每项的固定成本（描述符/调用/同步/队列）是否已经是主导？
- 行数是否远大于并发度？有没有足够的连续行可以合并？
- 整行是否放得进一个 staging 容量？行字节能被 32 整除吗（决定是否需要"每行一块"的对齐技巧）？
- 现在的搬运是"每行一条"还是"每个工作项一条"？是否已经在用深度 2 的队列？
- 队列深度是多少？是否按"先取后发"的顺序使用？空闲核的分支是否已经处理？
- 逐行计算是否有跨行依赖（有则不能合并）？

### 与相邻策略的关系

- 本策略解决**固定开销与重叠**；"带位置输出的极值归约单趟化"解决**每 tile 内的指令数**。
  小项场景两者必须一起用，否则批处理之后仍然被每行的同步/指令数拖住。
- 若新增通路显著改变了 kernel 的代码体积，注意"把新通路放到独立 kernel 承载"以避免短 kernel
  的取指/启动开销反噬（新增通路与旧通路共用同一个 kernel 体时常见）。

## 检索卡（短卡）

动作：把每行一条描述符、一次向量调用、一次 V 到 S 同步改为多行合成一块批处理，并在取走当前块前预发射下一块搬运。
适用：行数远大于并发度、行字节小、整行可入一个 staging 容量，且逐行独立无跨行依赖。
限制：行基址须 32B 对齐（用每行一块的搬运形态）；缓冲留一个向量长度尾余量；队列深度 2 时先 DeQue 再 Alloc；空闲核跳过前导。
范围：行结构明显的小行逐行流水环节（搬入、计算、写回均可批处理）。
检索词：blockCount、Normal 模式、ceil32、行距、预发射、TQue、DeQue、V_S、多行批。
机会：每项固定成本（描述符、调用、同步、队列往返）在小行场景占主导，DMA 有效带宽低。
代价：缓冲占用按行数成倍增加，行距非 32B 倍数时需额外对齐槽位。
