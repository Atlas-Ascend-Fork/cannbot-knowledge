# 性能优化策略：宽整数拆 32-bit 平面做字典序比较

> 单一优化点：在 64-bit 元素的比较/选择明显慢于 32-bit 的实现上，把 64-bit 数组**解交织成
> (hi, lo) 两个 32-bit 平面**，用 32-bit 指令做字典序比较，从而让一次向量操作覆盖的元素数
> 翻倍、且每条指令都是便宜的 32-bit 操作。适用于"比较类"归约（极值/带位置极值/计数）等
> 不需要 64-bit 位精确选择的场景。

---

## 1. 原理

很多实现里 64-bit lane 的算术/比较/选择是用两次 32-bit 操作模拟的，吞吐约为 32-bit 的 1/2~1/4，
而一个 256B 向量在 64-bit 域只有 32 lane、在 32-bit 域有 64 lane。两边叠加，64-bit 比较类
归约的有效吞吐只有 32-bit 的 1/4~1/8。

**做法**：把连续的 64-bit 元素读成字序列 `[lo0, hi0, lo1, hi1, ...]`，用两次 256B 载入
（两块共 128 个 32-bit 字 = 64 个 64-bit 元素）+ 一次**解交织**得到 `lo[]` 与 `hi[]`
两个 64-lane 平面。之后：

```
hi 有符号比较（int32 的有符号序 == int64 高字的有符号序）
lo 转无符号序：loU = lo ^ 0x80000000，再按有符号比较（等价于无符号）
字典序取用： take = (hi > hiRun) | (hi == hiRun & loU >= loURun)
```

**跨 lane 定案也必须按同一字典序**，不能分别取 `MAX(hi)` 与 `MAX(lo)`（lo 的最大值可能来自
hi 较小的 lane）：

```
hiMax = MAX(hiRun)
keep  = EQ(hiRun, 广播(hiMax))       // 只保留高字并列的 lane
loMax = MAX(Select(loURun, 域最小值, keep))
eq    = keep & EQ(loURun, 广播(loMax))
位置  = MIN(Select(位置, BIG, eq))
```

瓶颈类型：vec/issue（64-bit 指令吞吐低、lane 数减半）。

## 2. 性能问题模式

- 比较/归约类 kernel 在 64-bit 整型 dtype 上的耗时明显差于 32-bit dtype（远超过数据量的比例）；
- profile 显示向量发射已饱和，但单位时间处理的元素数远低于 32-bit 场景；
- 代码里 64-bit 的 `Compare / Select / Reduce` 是热点，且没有位精确的 64-bit 选择需求；
- 归约轴足够长（每段指令的固定成本可被摊薄）。

## 3. 正确性红线

1. **字典序的两半必须成对比较**：高字用有符号比较；低字先异或 `0x80000000` 再按有符号比较，
   才等价于无符号比较。写错会让负数区间的顺序整体翻转。
2. **定案不能分别取两个平面的极值**：必须先锁高字并列的 lane，再在这些 lane 内取低字极值，
   否则会选到"高字较小但低字较大"的伪赢家（症状：位置看似合理但值是错的，或定案 mask 为空）。
3. **解交织后的 lane 语义翻倍**：mask、位置向量、常量（BIG 哨兵）都要按 32-bit 宽度重新构造；
   **不能直接复用"按 64-bit lane 摆放"的常量缓冲**（把 64-bit 的 `INT64_MAX` 当 32-bit 读会得到
   `(0xFFFFFFFF, 0x7FFFFFFF)`，其中 `0xFFFFFFFF` 是 `-1`，会污染 MIN 归约）。
4. **尾巴补读但不参与比较**：最后一段不足"两个 256B 载入"覆盖的元素数时，必须用 mask 把
   无效 lane 排除；比较建议用全 mask 计算后**显式 `And` 上尾 mask**，不要依赖比较指令的 mask
   参数去屏蔽（不同实现对 mask 参数的语义不一致，尾部会读到下一行数据并污染定案）。
5. **位置仍用 int32**：轴长通常远小于 2^31；若位置以位模式跨域存放，只有非负值可用数值 MIN。
6. **不要用它实现位精确的 64-bit 选择**（如按位掩码选择、符号位处理）：本策略只保证"比较语义"
   等价，不做整字搬移。

## 4. 泛化条件

- **适用**：64-bit 整型（有符号/无符号）的比较类归约；64-bit lane 明显慢于 32-bit 的实现；
  归约轴长 ≫ 一个向量；不需要 64-bit 位精确选择。
- **不适用 / 收益低**：
  - 32-bit 与 64-bit lane 吞吐相同的实现（此时只是白忙）；
  - 需要按位操作 64-bit 值、或输出完整 64-bit 值参与后续 64-bit 运算（拆平面会增加重组成本）；
  - 归约轴很短（一次定案的固定开销占比过高），应先做多行批处理。
- **可叠加**：与"多行批处理""单趟 lane 扫描"叠加；位置/值仍按原来的 32B 槽位发布。

## 5. 实施步骤

1. 先量一下：64-bit 与 32-bit 在同一形态下的耗时比，确认差距远大于数据量比例（否则不值得）。
2. 载入：每段按两个 256B 载入（共 128 个 32-bit 字 = 64 个 64-bit 元素），解交织成 (hi, lo)。
3. 低字转换：`loU = lo ^ 0x80000000`；准备 32-bit 的 BIG 哨兵与位置向量（本地构造，不复用按
   64-bit 摆放的常量槽）。
4. 扫描：`take = (hi > hiRun) | (hi == hiRun & loU >= loURun)`；反向扫描取首现；按 take 更新
   hiRun/loURun/位置；尾部用全 mask 计算后 `And` 上尾 mask。
5. 定案：按"先高字并列、再低字极值"的两级归约；位置用 MIN 归约。
6. 发布：只发布 32-bit 的位置（必要时发布值），写到 32B 对齐的槽位；上层按 32-bit 视图读取。
7. 保留 32-bit dtype 的原有路径不变（两条路径用元素宽度分派）。

## 6. LLM 前置问题

- 目标实现上 64-bit lane 的比较/选择/归约是否明显慢于 32-bit？差距有多大？
- dtype 是有符号还是无符号？低字是否需要异或符号位？
- 是否需要 64-bit 位精确选择（有则需要另寻方案）？
- 常量/哨兵/位置向量是否都按 32-bit 宽度重新构造（是否误用了 64-bit 布局的常量槽）？
- 尾部怎么处理？比较是否用全 mask + 显式 And 收口？
- 归约轴是否足够长以覆盖两级定案的固定开销？是否应先叠加多行批处理？

### 与相邻策略的关系

- "单趟 lane 扫描"定义比较与取用谓词的形式；本策略只是把该谓词换成 32-bit 平面的字典序，
  两者天然叠加。
- "多行批处理"负责摊薄每项固定成本；本策略负责降低每元素的指令代价。三者共同作用时，
  64-bit 归约的吞吐可以接近 32-bit 场景。

## 检索卡（短卡）

动作：把 64-bit 元素的比较与选择解交织成 hi、lo 两个 32-bit 平面，按字典序比较，使一次向量操作覆盖的元素数翻倍。
适用：64-bit 整型比较类归约，且实现的 64-bit lane 吞吐明显低于 32-bit，归约轴远长于向量宽度。
限制：低字须异或符号位再比；定案先锁高字并列再取低字极值；64-bit lane 布局的常量槽不可当 32-bit 读；尾部补读后 And 尾 mask。
范围：宽整型比较类归约（最值、带位置最值、计数）。
检索词：解交织、DeInterleave、hi lo 平面、字典序比较、异或符号位、跨 lane 归约、lane 宽度。
机会：64-bit 比较按两次 32-bit 模拟且 lane 数减半，向量发射饱和而元素吞吐只有 32-bit 的零头。
代价：值与位置需在两个平面间维护，尾部与常量构造更繁琐。
