# 性能优化策略：原语可用性探针 + 零置换代数恒等式 + 反 flop 折半（FFT/复杂数学类算子的工程收敛）

> **来源：多任务内核评审与同构实现对照沉淀（2026-11-11）**
> 证据形态：本策略一半是性能策略、一半是**流程策略**——同类复杂数学任务中，「设计期决策正确」的实现以数倍少的代码量全量过评并进入性能迭代，「设计期设错禁令 + 多路径膨胀」的实现常见结局是超时未交付或精度带伤；差距主体来自设计期决策而非指令级优化
> 验证状态：探针/恒等式/反折半三机制在同类交付中有全量过评背书；「超时归因到未回归分支」属流程证据推断，具体缺陷点需盲调

## 原理

1. **自设伪约束是最贵的弯路**：设计文档/头注释自设「禁 Sin/Cos/Exp/Log」类禁令且无实测依据，会把 twiddle 因子逼成 float-float 军备竞赛——Dekker TwoProduct + 复乘残差补偿 + 根常数表二进制分解 + 两级查表纯标量 SetValue 构建 + 每级重建 base ramp；而目标硬件一条 `SinCos` 向量指令即可一次性生成全级 twiddle 表（每 kernel 仅一次，跨 b 块复用）。典型指令画像反差：SetValue/Gather 高密度 vs SinCos 为零。**硬件原语可用性必须实测裁定，不能凭架构信仰设禁令**（探针实测 + 全量精度过评可直接证伪禁令）。
2. **零置换代数恒等式消位逆序**：常见保守形态是固定宽度窗口 + Gather/Scatter 索引机 + 首级位逆序两遍法（依赖图含环，被迫 Gather 全平面→scratch→Scatter 回）。推荐形态：用恒等式 `Inverse(Forward(x)⊙Forward(k)) = n·cyclic_conv(x,k)`——Forward 用 DIF、Inverse 用其镜像共轭 DIT，两者互为精确逆且**全链无位反序置换**；逐点乘与排列无关 → 转置态直接跨 Forward/Inverse 消费（整行只需一次转置），各级全是整条数组连续块 Add/Sub/MulAddDst，小级用 DeInterleave/Interleave 转置。这是该类引擎代码规模数倍差距的最大单一来源。
3. **反 flop 折半**：为省一半蝶形做 r2c/c2r 折半 + 长度分裂路径宇宙（上千行 GM-relay 代码 + 第二套 twiddle 表）是常见过度工程。推荐形态：放弃折半（承认 ~2× flop）直接纯复 FFT——非 2 幂零填充到 next_pow2(2L−1) 复用同一 radix-2 核（Bluestein 探针验证正确但因动态范围放弃时须留档），超长长度也只套一个流式首级。依据：向量机瓶颈实测通常是管线占用而非蝶形数——省 flop 不省瓶颈。
4. **分支合入门禁（流程）**：「大片元素系统性错误」（非零星舍入越界）通常指向未回归的分支/边界形状缺陷；「第二路径的 session 排在交付前最后几条轨迹」是典型临终形态。精度问题须分层归因（twiddle 表→单级蝶形→相位函数→边界），每个分支合入前跑固定形状最小回归。

## 性能问题模式（哪些 profiling 信号说明该用）

- 数学类算子（FFT/三角/超越函数）设计期对硬件原语可用性存疑，或已存在「禁用某原语」的口头/文档约束但无实测依据。
- kernel 中出现 SetValue/GetValue/Gather/Scatter 高密度画像（标量索引机形态），同步点数与代码行数异常增长。
- 同一数学结构存在多条并行代码路径（直路径/分裂路径/镜像路径），路径间核心代码共享 <80%。
- 精度失败呈「大片元素系统性错误」而非零星舍入越界——指向未回归的分支而非精度积累。
- 工时分布：开发期反复回退（同一阶段 ≥3 次返工）、性能迭代阶段从未进入。

## 正确性红线（什么情况下禁止用 / 必须回退）

1. **原语探针先行**：任何「禁用/启用硬件原语」的决策必须有目标 NPU 上的 20 行级 probe kernel 实测结论（可用性+精度+吞吐）；无实测不得设禁令，也不得假设可用。
2. **恒等式必须先符号验证**：零置换/免转置类代数恒等式先在 numpy 全形状（含奇数长、质数长、边界长）验证逐位等价，再写 kernel；kernel 侧保留 numpy 对照回归。
3. **动态范围类放弃要留证据**：Bluestein 类高动态范围算法被放弃时留探针数据；零填充法的 M=next_pow2(2L−1) 不得截断。
4. **新代码路径与既有路径核心共享 ≥80%**：低于该比例的第二条路径视为设计报警，必须先尝试合并到同一核（流式首级包裹优于另起宇宙）。
5. **合入门禁**：每条分支合入前跑固定形状清单最小回归（≥6 条 case 覆盖各分支边界）；禁止「最后一个 session 还在新路径上」就进评测交付。

## 泛化条件（dtype / shape / 流水线 / 算子类型）

- 流水线：aiv_vec 主导的复杂数学类算子（FFT/卷积/超越函数/大整数运算）；也适用于**任何开发期反复回退的任务**（流程部分通用）。
- shape：NPU 无硬件加速单元、需手写数学引擎的 level4/5 类算子全适用；性能部分（恒等式/反折半）对已收敛实现的优化同样适用。
- dtype：与 dtype 无关；精度部分换 dtype 须重做误差分层归因。
- 流程子项（探针/门禁）与载体无关，Vector/Cube/SIMT 全适用。

## 实施步骤

1. 设计期（2.1/2.2 之前）：列出候选硬件原语清单（SinCos/Gather/Scatter/专用指令），每个写 20 行级 probe kernel 实测可用性与精度，落档探针报告；据实测修订设计禁令。
2. 数学设计：在 numpy 中推导并验证「消除置换/消除转置/统一正逆变换」的代数恒等式，全形状逐位对照；产出恒等式证明文档作为 kernel 设计输入。
3. 算法选型：先实测瓶颈类型（管线占用 vs 蝶形数 vs 搬运），再决定是否做 flop 折半类优化；默认取「单一核 + 流式包裹」结构，非 2 幂用零填充复用。
4. 代码组织：为每条分支建立固定形状回归清单（≥6 case），接入合入门禁；仿真底座（如有）升级为门禁工具而非一次性救火。
5. 精度问题分层归因流程：twiddle 表 → 单级蝶形 → 相位函数 → 边界/分支，逐层二分定位，禁止整链盲目加倍精度。

## LLM 前置问题（应用前必须自问）

1. 设计约束里有哪些「禁令」？每条禁令有目标硬件实测证据吗？
2. 候选原语的 probe 实验做了吗？SinCos 类指令在目标 SoC 的精度（ulp）与吞吐实测多少？
3. 正逆变换是否用了互为精确逆的结构（DIF/DIT 镜像共轭类恒等式）？位逆序/转置在全链出现几次？能不能是零次？
4. flop 折半类优化的依据是「蝶形数是瓶颈」的实测还是直觉？管线占用实测多少？
5. 代码里几条并行路径？共享核心比例多少？每条路径的固定形状回归清单存在吗？
6. 当前任务工时分布：开发期返工次数 vs 性能迭代轮次——是否已经倒挂？

## 验收标准

- **构建**：编译通过；原语探针报告在档（每条设计禁令/启用决策有实测编号引用）。
- **精度**：全量用例一次通过；恒等式改动另附 numpy 全形状对照记录；无「大片系统性错误」类失败残留。
- **性能/交付**：开发期不出现同一阶段 ≥3 次返工；性能迭代阶段实际进入；代码规模与路径数受控（第二路径共享 ≥80% 核心）。
- **流程**：合入门禁清单在档，最后一轮 session 不得落在新路径实现上。
- **回退**：探针证伪原语假设、恒等式全形状验证失败、路径合并后分支语义无法保持时回退对应子项。
