# 【已撤回】~191 行这个数，以及它背后的机制

> **撤回日期 2026-10-24。** 原标题为「MMAD 不补算对齐行 ≠ MTE1 不搬补齐行：
> A 的有效搬运行高反解为 ~191 行而活跃仅 ~9 行」。
> **本卡此前是机制类查询的 rank-1 命中**，即它正在被当作答案投喂给 agent，
> 所以撤回优先于任何新结论。

## 撤回什么

```
⛔ 「A 的有效搬运行高 ≈ 191 行」              —— 数值撤回
⛔ 「MTE1 把 A 按接近整块的行高搬进来」        —— 机制撤回
⛔ 原标题断言的 MMAD/MTE1 在本例【确实不同】   —— 撤回（见下第 1 条）
```
⚠ **证伪一个模型 ⇒ 由它派生的量不是「不准」，是【无定义】。**
不要把 191 读成「大概在这个量级」再用下去。

## 三条独立理由

### 1. 源码不支持该机制（最强的一条）
在**本卡自己钉的那棵树** `3bc27021d`：
```
block_mmad_mx_fp8fp4.h:297  mSize = min(MX_FP8FP4_M_STRIP /*128*/, param.mL1Size - mOffset)
                      :303  CopyAAndScaleAL1ToL0(..., mSize, ...)  → copy_l1_to_l0a, shape (mSize, realL0K)
                      :319  params.m = static_cast<uint16_t>(mSize) → MMAD
                      :500  blockParam.mL1Size = <tensorC.layout() 的行范围>
mega_moe_gmm_common.h :313  config.m = Get<M_VALUE>(problemShape)   → 每专家实际行数
```
⇒ **`mL1Size` 是每专家的【实际】行数，不是 `tileM`**；
⇒ **同一个 `mSize` 相隔十六行同时喂给 L1→L0A 的拷贝和 MMAD 的 `m`。**
⇒ **21× 的分歧在这个站点【不可表达】。** `:374-375` 显示 GM→L1 的 A 拷贝同样用 `mL1Size`。
⚠️ **范围**：这只否定「源码在两处显式使用了两种不同的逻辑行数」这一解释，**不能证明底层物理事务没有对齐/补齐**——源码的逻辑行数与硬件实际搬运的粒度是两件事，本卡没有后者的证据。

### 2. 模型只拟合了它被标定的那一个点
`191` 在 **bs=32** 上标定。k-steps 与 token 数无关 ⇒ B 的字节数跨 bs 恒定
⇒ **把 191 固定下来，模型预测每个 bs 的 `aic_mte1` 都是 `399.8 + 297.9 = 697.7 µs`**。
```
实测   bs=1  450.4 µs     bs=32  697.7 µs     bs=512  1133.9 µs
模型   bs=1  697.7         bs=32  697.7        bs=512  697.7
```
⇒ 它**命中了被拟合的那个点，错过了另外两个**。
⇒ 外推到 bs=512 需要 A ≈ **470 行 > `tileM` = 256**。

🔴 **而「行高 > 256 ⇒ 不可能」正是本卡用来排除 `rate=512` 的那条判据。**
**我只在【淘汰对手】的方向上用了它，没在【约束自己的结论】的方向上用。**

### 3. 预算少记了两项（真实但不足以解释）
同一棵树上，**MTE1 在本路径有四个消费者**：
```
:236 copy_l1_to_l0a      :246 copy_l1_to_l0scalea
:262 copy_l1_to_l0b      :272 copy_l1_to_l0scaleb
```
原预算只有 A + B。
⛔ **我最初在此写了「scale 约占 1.5% ⇒ 191→188」。该量级主张【撤回】** —— 它犯的正是本卡的原罪：
**拿 A/B 通路的速率去算一条目的地不同的流。**
```
scale 的目的地是 **l0scalea / l0scaleb**，不是 l0a / l0b
而 [AICoreMemoryRates] 只有  l1_to_l0_a_rate / l1_to_l0_b_rate / l1_to_ub_rate
                             l0_c_to_ub_rate / ub_to_{l2,ddr,l1}_rate
⇒ **平台表没有 scale 通路的速率** ⇒ **字节占比 ≠ 时间占比**
```
**字节**可以算（e8m0，每 32 元素 1 字节 ⇒ scale-B ≈ B 的 3.1%，4.8 MB vs 154.1 MB/核）；
**时间占比 `UNKNOWN`，不猜。**
⇒ 能说的只有：**`aic_mte1` 至少聚合四条流，分母少了两条。**
⛔ 原先据此给出的「反解的 191 系统性偏大，且方向与 clamp 结论同向」**已删除**：该反解模型本身已在本卡下文撤回，而四条流各自的速率与交叠程度 `UNKNOWN`，聚合量少了分母并不能定出单一方向的偏差。

## 仍然成立的

```
✅ 实测值本身：aic_mte1 = 450.4 / 697.7 / 1133.9 µs（bs 1 / 32 / 512，每核）
✅ 缺口是真的：朴素 A+B 字节预测低于实测。
   ⚠ **但「随 m 增长」这个说法本身要收窄**（2026-10-24 当日再修正，见下「三条约束」）：
   bs=1 处 m = 0.286 行/专家，**不是一个连续量** ⇒ 该点不能支撑趋势。
   ⇒ 可说的只有：**bs=32→512 之间，`C.mte1` 增长 1.63×，而 m 增长 16×**。
     ⛔ 原先这里还写着「bs=32 这一点比两端连线高 42%」——**已删除**，因为那条弦用 bs=1 作端点，而 bs=1 不是 m 曲线上的点（见下文③）。该数字不得再被引用。
✅ 杠杆分析（与上述无关，独立成立）：`SelectBlockMmadTilingConfig` 的四个接受判据
   全在 K 方向，`blockM` 进了 config 但从不是接受判据
   ⇒ 重开 `if constexpr (IsA8W4) return baselineConfig` 改的是 K 方向 L1 窗口，
     **答不了 M 方向的问题**。（这一条仍然省掉一整轮实验。）
```

## 任何替代解释必须同时满足的三条约束

全部来自 V501 §5 全 pipe 表（`PROCESS_RETRO_20261018:139-141`，9584 实测），
**三条都是「预测后失败」，不是拟合**：

```
  bs   m/专家   C.mte1   C.mte2    C.mac
   1    0.286    450.4    830.7    317.2
  32    9.143    697.7    764.8    473.4
 512  146.286   1133.9   2063.7   2277.6
```

**① ⛔ 我原先在这里写的「中点比弦高 42%」【已自撤】 —— 它与下面的 ③ 自相矛盾。**
那条弦用 **bs=1 当端点**，而 ③ 正说明 bs=1 不是 m 曲线上的点。
⚠ **我把 ③ 写进来了，却没回头作废依赖它的 ①** —— 同一张卡里前后矛盾。
```
丢掉 bs=1 之后只剩【两个】可用点 ⇒ **任意两点必然共线** ⇒ **线性检验无从谈起**
```
✅ **两点仍能支撑的，只有一个无需第三点的陈述**：
`m ×16.00` 而 `C.mte1 ×1.625` ⇒ **强烈次线性**（详见 V677）。
⇒ ⛔ **原先写的「不是 m 的仿射函数」在数学上是错的，已撤回。**
两点 `(m=9.143, t=697.7)` 与 `(m=146.286, t=1133.9)` 被
`t(m) = 668.6195759171085 + 3.18062168685241 * m`
**逐点精确拟合（残差 0）**，所以带非零截距的仿射模型**没有**被否定。
两点只能否定**零截距的严格正比例模型** `t = c*m`（因为 m×16.00 而 t 仅 ×1.625）。
⇒ 可保留的陈述只有：**相对于零截距正比例模型是强烈次线性**；
「高出弦 42%」作废，「不是仿射函数」同样作废，两者都不要引用。

**② `C.mte2` 随 bs 非单调**：`830.7 → 764.8 → 2063.7`，**在 bs=32 处下凹 65.9 µs**。
⇒ **凡「流量只随 token 增长」的模型都产生不了这个凹陷。** 机制仍未知。

> **已排除一个候选（2026-10-24，零卡时，源码读于 `3bc27021d`）**
> 候选是「随 m 翻转的复用判定」`mega_moe_gmm_common.h:433`：
> ```cpp
> hasNoLaterWeightReuse = **coversWholeExpert** && config.m <= config.tileM;
> :440 bypassWeightL2 = hasNoLaterWeightReuse;   → gmB.set_l2_cache_hint(disable|normal)
> ```
> 它看起来是 m 的函数（bs=1 多数专家 m=0；bs=32 m≈9；bs=512 m≈146）。
> ⛔ **但它被【第一个操作数】短路掉了**：该参数由 `allowWeightL2Bypass` 传入，
> ```
> gmm1_activation.h:621/:665 · gmm2_combine.h:752/:790  →  **= false**（默认）
> 全树按名穷举（mc2/mega_moe 下全部 .h/.cpp）12 处命中：**全是声明/默认/具名转发，无一处传 true**
> A8W4 wave :208/:248 调的是 7 参包装，**够不到该形参**
> ```
> ⇒ `false && (…)` ⇒ **`config.m <= config.tileM` 从不被可观测地求值** ⇒ **不可能驱动 MTE2 随 m 变化。**
> ⚠ **未穷尽的残余**：非 A8W4 路径上经 10+ 参列表的**位置传参**我没有逐一排除
> （按名 grep 看不见位置传参 —— 本项目已有先例）。**A8W4 路径是干净的。**
>
> 📌 **并且即使它触发，同一次调查里该杠杆的单因素结果是负的**（A8W4 权重 L2 bypass；
> 该项未随本批提交，其主张已因自相矛盾撤出，此处仅作背景，不作本卡依据）
> 实测把 bypass 接进 A8W4 两个 GMM ⇒ 客户 bs=32 EP4 中位数 **1671.868 → 1733.978 µs
> （r=1.0372，慢 3.72%，两臂不重叠）**。
> ⇒ **仍然开着的候选**：L2 驻留本身（9584 的 112 MiB L2 对约 88 MB/rank 的 fp4 专家权重，正好在边缘）。

**③ bs=1 处 m < 1，不是连续量。** topk=16、local_E=56 ⇒ 最多 16/56 的专家拿到 token。
⇒ 「每专家行数」在该点是**稀疏占用**而非标量；
**任何跨这三点的趋势陈述实际只有两个可用点。**

## 方法教训（这张卡现在最有价值的部分）

1. **用 A 的速率去算 B，而没有先确认两者相等。**
   本次在 950 上**侥幸正确**：`l1_to_l0_a_rate = l1_to_l0_b_rate = 256`（全部 950DT/950PR SKU）。
   **但在 910B1 / 910_9362 / 910_9372 / 310P3 / 310P7 上 `a=512, b=256`**
   ⇒ 同样的代换会错 2×。**对的数，没挣来。**
2. **一条「不可能」判据必须朝两个方向用。** 它淘汰了 `rate=512`，
   也应当被拿去检验**幸存的那个假设**在别的 bs 上的外推 —— 那会当场否掉 191。
3. **一个在单点标定、又声称与该点无关的模型，必须拿去预测另外的点。**
   本例 k-steps 与 token 无关 ⇒ 模型自带一个跨 bs 的刚性预测，**三分钟就能证伪**。
4. **「X 不做 Y」类厂商注释的主语是哪条 pipe 要读准** —— 这条**作为一般告诫仍然成立**，
   但**本例不再是它的实例**：源码显示此处 MMAD 与 MTE1 用的是同一个 `mSize`。
