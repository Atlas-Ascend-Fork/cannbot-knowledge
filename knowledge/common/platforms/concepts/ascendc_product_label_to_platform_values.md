# API 文档产品标签到 platforms 枚举的映射

知识卡 Frontmatter 里的 `platforms` 只能填 `a2`、`a3`、`950`、`310p`、`910`、`kirin_x90`、
`kirin_9030`、`agnostic` 这八个枚举值；而 asc-devkit 的 API 内容页用另一套标识声明产品支持情况
——产品支持章节里的 `npu` 标签。两套标识的取值集合与粒度都不同，照抄标签会写出非法取值或
含义错误的平台声明。本卡给出这一层的对应关系、两个易错点和标签的形态。

## 定义：两层不同的"平台标识"

| 层次 | 形态 | 出现位置 | 取值 |
| --- | --- | --- | --- |
| API 内容页 `npu` 标签 | `950`、`A3`、`910b`、`310b`、`310p`、`910`、`x90`、`9030` | 产品支持章节的 HTML 注释属性 | 8 个（见主映射表） |
| 知识卡 `platforms` | `a2`、`a3`、`950`、`310p`、`910`、`kirin_x90`、`kirin_9030`、`agnostic` | 知识卡 Frontmatter | 8 个（注册表固定） |

两者不是同一套命名的两种写法。`npu` 一侧混用"芯片代号"式写法（`910b`、`310b`）与"产品家族"
式写法（`A3`、`x90`、`9030`），`platforms` 一侧统一按"产品系列"登记。中间必须做一次**按产品名称**
的翻译，不能按字面相似度对应。

## 主映射表

| API 文档 `npu` 标签 | 源文件登记的产品名称 | 知识卡 `platforms` 取值 |
| --- | --- | --- |
| `950` | Ascend 950PR&950DT系列产品 | `950` |
| `A3` | Atlas A3系列产品 | `a3` |
| `910b` | Atlas A2系列产品 | `a2` |
| `310b` | Atlas 200I/500 A2推理产品 | **无对应取值** |
| `310p` | Atlas推理系列产品AI Core；Atlas推理系列产品Vector Core | `310p` |
| `910` | Atlas训练系列产品 | `910` |
| `x90` | Kirin X90 | `kirin_x90` |
| `9030` | Kirin 9030 | `kirin_9030` |

左列与中列是源文件的原文口径，用于校验 `npu` 属性值与标签内产品名称是否对应；右列是本仓知识卡
的登记口径，取值集合由知识仓平台注册表固定。中列到右列的翻译是**本仓约定**，不是 asc-devkit
的事实——翻译依据是产品名称，而不是标签字面。

## 两个易错点

### 1. `910b` 对应 `a2`，不是 `910`

`910b` 在产品名称一侧登记的是 **Atlas A2系列产品**，因此映射到 `a2`。按字面把 `910b` 缩成 `910`
会落到表里另一行——`910` / Atlas训练系列产品，那是"早期 Ascend 910 系列"。这两个标签在同一张
表里同时存在，是本卡最需要人工确认的一处。

### 2. `310b` 没有对应的 `platforms` 取值

`310b` 对应 **Atlas 200I/500 A2推理产品**，而本仓 `platforms` 枚举中没有与它对应的取值。既不能
就近写成 `a2`（`a2` 已由 `910b` / Atlas A2系列产品占用），也不能写成 `310p`（那是 Atlas推理系列
产品）。**遇到 `310b` 标签时的正确处置是不声明该平台取值**，把"该产品系列未在本仓平台词表中
登记"作为范围缺口记录下来，而不是挑一个"最像"的枚举顶上。

## 标签的形态：`npu` 属性与 HTML 注释

产品支持情况不是用纯文本写的，而是用成对的 HTML 注释把一段支持声明包起来，属性里带 `npu` 值：

```text
<!-- npu="950" id1 -->
- Ascend 950PR&950DT系列产品：支持
<!-- end id1 -->
```

解析与撰写这类标签时有几条固定规则：

- `npu` 可以包含**逗号分隔的多个值**，例如 `npu="950,A3,910b"`，一条声明同时覆盖多个产品系列；
- 开始标签与结束标签必须**成对**出现；
- 同一个 Markdown 文件内 `idN` 必须唯一；
- `idN` 不要求从 `id1` 开始，也不要求连续递增；
- 标签可以包裹段落、列表、代码块和表格单元格；
- `docs/zh/api/README.md` 这类**索引文件**可以使用 `<cann-filter npu-type="...">`，**不要**把索引
  文件的规则套用到 API 内容页。

因此"某接口支持哪些平台"的原始证据是"`npu` 属性值 + 标签内产品名称"这一对，并且两者应当相互
对应；源文件的用途正是校验这对关系。标签属性值本身不是 `platforms` 的合法取值。

## 为什么卡里只写枚举值

- **可机器校验**：`platforms` 受注册表约束，写错即校验失败，不存在"近似写法"的余地。
- **稳定键**：产品名称随文档改版增删（如把"系列产品"改成别的写法），枚举值是仓内的稳定键。
- **可检索**：Query 按 `platforms` 过滤，保留文档原标签会让同一平台分裂成多个检索键。
- **口径分离**：需要在卡里表达"文档当时是怎么写的"时，写在正文并给出来源，而不是塞进 Frontmatter。

## 适用与不适用

**适用**：

- 把 API 内容页"产品支持情况"抄进知识卡 `platforms` 时做一次翻译；
- 校验 `npu` 属性值与标签内产品名称是否对应；
- 判断某个文档标签在本仓**该不该**声明平台范围（典型例子是 `310b`）。

**不适用**：

- 判断某接口在某平台上是否真的可用——本卡只做词表翻译，不承载能力结论；
- 芯片统一调用名、SocVersion 与 `__NPU_ARCH__` 数值的取值，那是另一层映射；
- 设备身份（Device ID / Chip ID）与编译命令行的现场核对。

## 与其他概念的边界

- 本卡是**文档词表层**的映射（支持声明标签 → 知识卡枚举）。
  [AscendC 芯片别名与 NpuArch 映射表](ascendc_chip_alias_and_npu_arch_map.md) 处理的是**构建与运行期
  命名层**（统一调用名 / SocVersion / `__NPU_ARCH__` 数值）的映射，两者不可互相替代：拿到 `npu`
  标签不能推出架构号，拿到架构号也不能推出标签；两张卡的平台范围也不同（该卡不含 Kirin 两值）。
- 文档标签是**支持面的声明口径**，芯片名称、产品别名或编译架构数值都不能替代它。"支持表没写"
  既不能读成支持，也不能读成不支持；而"表里没写、实测可用"这类偏差属于实测证据卡的职责，
  见 [TopK 高阶 API 在 DAV_3510 编译可用](../../../ops/ascendc/runbooks/compilation/topk_highlevel_api_dav3510_compile_verified.md)
  ——那类卡给出实测结论并标注其验证范围，本卡不据此改写标签映射。

## 失效边界

- 源文件是标签词表与校验规则，**不含任何芯片的实测支持结论**；本卡不据此断言某接口可用或不可用。
- `platforms` 的覆盖范围即主映射表右列出现的 7 个取值（源表覆盖到哪些产品系列，本卡就声明到哪里），
  不含 `agnostic`：本卡结论与具体硬件标签强相关，换一套词表即失效。
- `310b` 在本仓无对应取值，本卡不提供替代写法，也不把它并入 `a2` 或 `310p`。
- 标签取值会随文档改版变化（增删产品系列、改产品名）；判断某接口的支持面时以**目标版本的公开文档**
  为准，本卡的映射只是把文档口径翻译成仓内枚举的桥。
- 不覆盖 `<cann-filter npu-type>` 的完整语义：源文件只说明它用于索引文件、且不要把它的规则套用到
  API 内容页。
