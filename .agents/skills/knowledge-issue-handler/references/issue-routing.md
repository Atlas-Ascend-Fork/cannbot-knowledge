# 知识仓 Issue 路由

处理责任范围内的 Issue、准备分析或回复时读取。本文件只补充知识仓业务路由；首响、负责人、PR、跟进、授权和状态机仍以原 Handler 为准。

## 先识别实际诉求

综合标题前缀、表单字段、正文和最新评论判断，不因出现一个关键词就忽略其他诉求。一条 Issue 同时包含多类诉求时分别记录，回复逐项覆盖；无法判断且会影响处理方向时，提出最小澄清问题。

| 类型 | 常见入口 | 默认处理结果 |
|---|---|---|
| 知识问题反馈 | `Knowledge-Report` | 核对卡片与来源，确认错误、解释现有结论或请求必要证据 |
| 知识需求 | `Knowledge-Request` | 查重；已有覆盖则直接答复，未覆盖则说明缺口和入库所需条件 |
| 工具与 Skill 缺陷 | `Bug-Report` | 核对复现材料和当前实现，给出诊断；默认不修改代码 |
| 治理与能力建议 | `Requirement`、`[RFC]` | 默认 `list-only`，由维护者评审，不自动承诺方案或排期 |
| 角色任命申请 | `Requirement` 中的 Committer/Reviewer 提名 | 取证后给提名记录式首响，结论由维护者决定，见[角色任命申请](role-nomination.md) |

纯 Roadmap、规划汇总和工作记录按配置忽略。显式 single 也不能绕过 `list-only`、`ignore` 或 pending 范围门禁。

公开回复的结构按诉求选择：缺陷、知识问题与知识需求按[回复结构（六段式）](reply-structure.md)组织；治理建议与 RFC、角色任命申请不套该结构。

## 知识问题反馈

1. 从 `knowledge-location` 解析知识卡路径、Concept ID 或仓库链接；路径明确时先阅读全文，路径未知时通过 Query 定位。
2. 对照 `current-problem`、`expected-content` 和 `evidence`，逐项核对正文、Frontmatter、来源、平台、版本和失效边界。
3. 区分可验证错误、工程/治理选择和证据不足。只有当前来源或复核结果证明卡片违反事实或公开契约时，才确认问题成立。
4. 已确认错误时，回复指出具体位置、核实依据和可行修正方向；不声称卡片已修改，不自动执行 Ingest。
5. 现有卡片有充分依据时，直接解释结论和适用范围；双方来源冲突时列出冲突及待核验条件，不选择更方便的一方。
6. 缺少必要来源、平台、版本或问题原文时，只索要影响判断的最小材料。

## 知识需求

1. 先执行 Query `discover` 了解真实覆盖，再围绕使用场景、准确 API/错误信号和关键约束检索；搜索词与平台规则见知识证据参考。
2. 已有知识覆盖时，阅读全文后直接回答使用场景，并附实际读过的卡片链接；不要只回复“已有相关文档”。
3. 部分覆盖时，分别说明已覆盖和仍缺失的内容，不把相关卡片当成完整满足需求。
4. 有效零命中时，说明实际检索范围及当前知识缺口。零命中不证明相关技术或 API 不存在。
5. 候选来源不足时，可说明官方文档、固定版本源码、测试或可复现实验是后续入库依据；不得承诺一定收录或给出未经批准的排期。
6. 默认不创建知识卡、不更新索引或导航。用户另行要求贡献知识时，转入本仓正常贡献流程。

## 工具与 Skill 缺陷

1. 核对受影响组件、仓库 commit、环境、最小复现、期望/实际行为和日志。表单信息不完整时，参考 `knowledge-lint` 的 Issue 材料要求确定最小缺口。
2. 需要实现结论时读取当前或报告版本的实际源码/脚本，保留固定 revision 证据；不能只凭组件名称猜测根因。
3. 只有当前请求明确允许时，才运行复现命令。不得为处理问题自动执行具有外部写入、资源下载或设备副作用的操作。
4. 默认输出诊断和可行处理方向，不进入代码修改。用户明确要求修复后，才使用原 Handler 的复现、worktree、验证和交付门禁。
5. 回复区分已复现、源码推断和待验证假设；CI/Lint 未运行时不声称验证通过。

## 治理建议与 RFC

- 批量配置默认只列举仍需关注的项，不回复、不指派。
- 用户显式要求分析单个建议时，可基于当前规范说明问题、收益、成本、兼容性、迁移和替代方案，但仍不自动发布或修改治理规则。
- 不把提出者建议直接认定为缺陷，不承诺新增字段、修改默认流程或合入方案。
- 涉及公共组件新增、优化或主动行为调整时，保留 RFC、A/B 和 committer 检视要求。

## 角色任命申请

- 与治理建议分开：任命申请要首响，内容是提名记录而非方案评审，细则见[角色任命申请](role-nomination.md)。
- 先核对本仓可验证贡献（`merged_at`、文件数、卡/索引数）与本仓 Issue，再拟稿；未核验的跨仓数字标为申请人自述。
- 不承诺任命结论、时间或后续排期，不评价申请人水平；需要评审确认的边界交回维护者。
- 首响后保持 open；维护者给出结论后才关单。

## 新追问

提出者或责任人的最新评论可能改变原路由。先按原 Handler 确认 follow-up 和有效回复基线，再只针对新增诉求补充必要调查；旧结论仍适用时可以复用，但不能用旧回复掩盖新问题。

## 结果契约

沿用原 Handler 任务文件中的字段和允许值。把路由、已读证据、适用范围、未知项和拟采用的公开答复写入既有分析/审核字段；不修改 pipeline、不增加旁路状态文件，也不因知识检索失败伪造 prepared 结果。
