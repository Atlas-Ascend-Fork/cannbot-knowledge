# 角色任命申请（Committer 提名）

处理「申请成为 cannbot-knowledge 仓库 Committer / Reviewer」一类 Issue 时读取。这类 Issue 属治理事项，但**不是方案类 RFC**：它需要首响，回复内容是「提名记录 + 可核验贡献 + 治理归属」，不能套知识/缺陷的根因-复现结构，也不能替维护者给出任命结论。

## 识别

标题或正文命中任一特征即按本类处理：

- 标题含 `申请成为`、`Committer`、`Reviewer`、`提名`、`角色任命`；
- 正文含 `贡献方向（责任田）`、`申请角色`、`代表性贡献`、`代表性 PR` 等字段；
- 申请人已 `/assign` 自己，只说明其认领动作，不改变类型判断。

同一 Issue 顺带报告技术问题（例如申请材料里同时指出某卡错误）时分别记录：缺陷部分按 `Bug-Report` 处理，不因主体是任命申请而忽略。

## 与相邻类型的边界

| 类型 | 区别 | 路由 |
|---|---|---|
| 治理与能力建议 / RFC | 改规则、加字段、调流程 | `list-only`，不自动回复或承诺方案 |
| 角色任命申请 | 人事与评审权限归属 | 本类：提名记录式首响，结论由维护者决定 |
| 知识需求 | 缺知识或缺口径 | 按 `Knowledge-Request` 处理 |

判断依据是诉求本身，不是标题前缀：`[Requirement]` 里也常有真正的缺陷或知识需求，要按正文拆分。

## 事实核验

只写核得到的内容，默认用 `scripts/collect_nomination_evidence.py` 收集（只读，仅 GET）。输出目录默认按 Issue 编号隔离为 `data/nomination-<issue>`（无 `--issue` 时按登录名 `data/nomination-<login>`），两个申请人不会互相覆盖证据：

```bash
python3 .agents/skills/knowledge-issue-handler/scripts/collect_nomination_evidence.py \
  --issue 105 --draft
```

脚本产出 `nomination-evidence.json`、`nomination-evidence.md`；加 `--draft` 另生成 `reply-draft.md` 骨架，占位符用 `<!-- 待确认 -->` 标出，需人工确认后使用。

核验口径：

1. **本仓 PR**：按申请人账号拉全部 state，逐条记录 `state`、`merged_at`、文件数、增删行、是否落在责任田路径。
2. **「已合入」只认 `merged_at` 非空**：open 与 closed-without-merge 都不算合入，写「在途」或「已关闭未合入」。
3. **卡片数按实际文件计**：`index.md` 单列为索引，不并入卡片数；一处索引改写不要放大成「新增知识卡」。
4. **本仓 Issue**：申请人提起的知识 Issue 及状态，用于说明其认领与在途批次。
5. **责任田现状**：目标路径现有卡片数。存量作者与迁移历史需人工 `git log` 核对，脚本不推断归属。
6. **同类申请**：检索既有 Committer 申请，标注重叠方向与在途编号；责任田边界是否需要合并评审由维护者定。
7. **跨仓贡献**（cannbot-skills、asc-tools 等）不在本仓范围，只能写「申请人自述，未逐条核验」，不得用未核验数字为其背书。

自述与核查结果不一致时，以核查结果为准并说明差异；无法核验的项写「未核验」，不省略、不模糊处理。

## 回复模板

四段，长度控制在 150 字以内（不含事实列表）：

```markdown
已收到提名申请，本单作为提名记录保留。

已核验的贡献（截至 <核查日期>）

- 知识卡：<PR>《<标题>》于 <合入日期> 合入，<N> 张卡 + <M> 个索引共 <K> 个文件，+<A>/−<D>；<在途 PR> 在途。
- 路径治理：<PR> <做了什么>，<合入日期> 合入。
- 知识 Issue：<已关闭编号> 已关闭，<在途编号> 在途，均由本账号提起。
- <跨仓贡献> 为申请人自述，不在本仓范围，本次未逐条核验。

<责任田边界或需评审确认的口径，一句话；无内容则整段省略>

Committer 任命属治理事项，由本仓有合入权限的维护者决定，同步安排进入 SIG 例会陈述。
```

写作要求：

- 不加「根因 / 复现 / 影响 / 修复方向 / 验证建议」小节：任命申请没有失败复现路径，套用会写出「该能力当前缺位，用户需手工完成」这类错位表述。六段式的适用类型与排除项见[回复结构（六段式）](reply-structure.md)。
- 不列「还需补齐材料」清单要求申请人补交，除非申请人明确询问差距；评估口径由维护者提出。
- 不做承诺：不写「本周」「尽快」「例会前」，不写「通过后按知识生产流程排期」，不预告评审结论。
- 不评价申请人水平，只陈述事实、差异与归属；不用「仅」「不过」这类贬抑性限定词描述贡献。
- 可以点出需要评审确认的边界（如两个方向的责任田划分），把裁判权交回维护者。

## 状态与关单

- 首响后保持 open，作为提名记录；任命是否生效由维护者决定，Handler 不据此关单。
- 只有维护者已给出明确结论（任命或驳回）后，才由人工或单独授权关单；关单前按 PR–Issue 关联规则核对是否存在需关联的 PR。
- 已有有效首响不重复发送。申请人追加材料或维护者提问时按新追问处理，只补新增事实，复用已核验结论。
