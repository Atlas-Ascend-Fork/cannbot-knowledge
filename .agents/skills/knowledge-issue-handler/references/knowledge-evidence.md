# 知识证据与回复约束

知识问题、知识需求，以及包含 CANN 技术判断的其他 Issue 在拟稿前读取。工具自身的非领域缺陷不需要为了形式执行领域知识查询。

## 知识检索的唯一入口

- 原 Handler 上游的 `knowledge_query.py`（Issue 处理规则卡 + 目标仓历史案例的预检查询器）**不在本仓 vendored 保留集内**，仓内运行时全部知识检索由本仓 `knowledge-query`（及按需的 `ascendc-api-knowledge-query`、`runtime-api-knowledge-query`）承担；上游文档中的预检命令按 [issue-routing.md](../../gitcode-issue-handler/references/issue-routing.md) 与 [runtime-knowledge.md](../../gitcode-issue-handler/references/runtime-knowledge.md) 的裁剪副本注意替换为本仓 Query。
- 本仓 `knowledge-query` 提供经过治理的 CANN 技术知识卡。它只负责召回候选，Agent 负责选卡、阅读全文和核对证据。
- 本 Skill 的领域结论必须走本仓 Query 或直接读取唯一明确的知识卡；上游历史案例层（若经外部完整副本启用）不能冒充知识库卡片，本仓卡片也不能替代当前 Issue、当前源码或当前版本的核验。

## 检索顺序

1. 首次进入本知识仓时执行 `discover`，区分真实覆盖和注册/占位目录；同一任务且索引未变时可复用。
2. 已知唯一卡片路径且问题只依赖该卡时，直接阅读全文；需要查重、相关背景或新证据时继续 Query。
3. 已知准确 API、类型、错误码或连续日志短语时保留原文并使用 `literal`；只有能力、机制或现象时使用“实体 + 一个关键约束”的短词组和 `text`。
4. 只添加 Issue 已明确且有助于区分的 domain、technology、Profile、status 和 Scope 条件。不要从自然语言猜测硬过滤条件。
5. 初次只取少量候选，按标题和摘要选卡后阅读全文；未达到目标定义且结果达到 k 时可扩大窗口或按真实线索细化。

具体命令、参数和错误语义以 `../../knowledge-query/SKILL.md` 及其 CLI 参考为准，本文件不维护第二份接口。

## 平台、版本与技术边界

- 普通 Query 必须有目标平台或项目缺省平台。Issue 未提供且无法唯一识别时，不猜测平台；先询问会影响答案的最小信息。
- 项目缺省平台不能覆盖 Issue 中明确不同的目标平台。平台无关的工具缺陷不强制补平台。
- Ascend C API 契约/选型使用 `ascendc-api-knowledge-query`；Runtime API 选型/比较使用 `runtime-api-knowledge-query`。两者均复用 Query，不另建搜索。
- Query 不按 CANN 版本过滤。阅读全文时仍需核对 `cann_versions` 或 Runbook 正文中的版本边界。
- 不用其他平台、其他 DSL、未定位 draft 或 deprecated 卡片替代目标证据。专用 Skill 允许的补搜也必须单独标注其证据边界。
- 索引缺失、损坏或 stale 属于查询错误，不是有效零命中。保留错误并停止依赖该索引的结论，不自动重建。

## 从候选到证据

1. 选中的卡片必须读取完整 Frontmatter 和正文；分页或截断时继续读完。
2. 核对 `status`、平台、版本、适用条件、失效边界和来源。`stable` 是生命周期，`verified` 是复核事件，都不证明当前结论必然适用。
3. 结论依赖原始文档、固定源码或实验时，按需继续读取实际来源。来源链接存在不等于来源已读，搜索排名不等于技术正确。
4. 卡片之间或卡片与 Issue 证据冲突时保留冲突，补充必要核验；不得为形成完整回复而隐藏不确定性。
5. 有效零命中只能说明当前条件下未召回。补搜仍无结果时说明已查范围和知识缺口。

在 `analysis` 或既有审核字段记录：

- 实际执行的查询及关键过滤条件；
- 实际阅读全文的卡片路径/Concept ID；
- 实际核对的来源、固定 revision 或实验；
- 每个结论对应的证据、适用范围和未知项；
- 零命中、索引错误、来源冲突及补搜结果。

## 公开回复

- 先直接回答提出者的问题，再给实际读过的卡片或来源链接；不要倾倒搜索候选和内部运行路径。
- 区分 Issue 报告内容、知识卡事实、当前源码观察、工程推断和已执行实验。
- 已覆盖的知识需求给出可用答案；未覆盖时说明缺口，不用通用技术记忆补写未经治理的结论。
- 已确认的知识错误只能说明已核实的问题和可行修正方向；没有实际修改与验证证据时，不写“已修复”“已补充”或“已收录”。
- 不暴露 Token、内部凭据、本地绝对路径、Agent 分工、内部评分或运行故障细节。
- 不承诺未来修复、收录、版本支持、排期或性能收益。确需承接时，只表述当前已获授权且能够落实的动作。

发布前在原 `response_review` 中额外核对：诉求是否逐项覆盖、卡片是否阅读全文、平台/版本是否匹配、证据是否支持结论、未知项是否明确、是否含有未授权承诺。该检查不增加发布权限。
