# 回复结构（六段式）

缺陷、知识问题与知识需求三类 Issue 的公开回复主体按本文件组织。本文件只约束**回复骨架与证据措辞**，不放宽发布授权、证据边界或承诺限制。

## 先判断该不该用

| 路由 | 用六段式 | 实际走向 |
|---|---|---|
| 工具与 Skill 缺陷（`Bug-Report`） | 是 | 本文件，段名用原名 |
| 知识问题反馈（`Knowledge-Report`） | 是 | 本文件，段名按知识卡语境替换 |
| 知识需求（`Knowledge-Request`） | 是，但没有失败路径 | 用「缺口定位」代替「根因」，见下方变体 |
| 治理与能力建议 / `[RFC]` | **不用** | 默认 `list-only`；显式要求分析时按 [Issue 路由](issue-routing.md) 的问题、收益、成本、兼容、替代维度组织 |
| 角色任命申请（Committer/Reviewer 提名） | **不用** | 四段式，见[角色任命申请](role-nomination.md) |
| 纯答疑（用法、参数、返回码） | **不用** | 一条直接答案加证据链接，不先发受理通知 |

排除项是硬边界，不因“格式统一”破例：

- 任命申请没有失败复现路径，套六段会写出「根因：该能力当前缺位」「验证建议：请按新流程复测」这类把人事申请当缺陷的错位表述；
- 治理建议与 RFC 的结论由维护者评审，写「修复方向 + 验证建议」等于替维护者定方案。

一条 Issue 同时含多类诉求时拆开写：缺陷部分用六段，任命部分用四段。两者可以出现在同一条回复的不同小节里，但不要给任命小节补根因和复现。

## 六段定义

| 段 | 写什么 | 不写什么 |
|---|---|---|
| **根因** | 触发点落在哪个文件、函数、参数或卡片字段，为什么导致报告的现象 | 只凭组件名猜的“应该是……导致”；未读实现就下的结论 |
| **复现** | 已验证的复现步骤与结果，或按 Issue 描述归纳的触发条件 | 没跑过却写「本机已复现」 |
| **影响** | 受影响范围：平台、版本、算子或卡片数量、是否阻断主流程 | 没有实测支撑的「影响所有用户」 |
| **修复方向** | 可以改哪里、为什么可能有效、必须保留什么契约 | 承诺排期、承诺一定实施、写成已完成的修复 |
| **验证建议** | 提出者可以自己执行的核对动作与判定标准 | 把维护侧的修复和测试推给对方完成 |
| **当前进展与下一步** | 关联 PR 与合入状态、当前卡在谁或什么条件上 | 重复前五段结论；预告未获授权的时间点 |

段间不重复：PR 状态只出现一次，写全「覆盖范围 + 合入或分支状态」，后文不再复述。

## 三类段名变体

**缺陷类**用原名：根因 / 复现 / 影响 / 修复方向 / 验证建议 / 当前进展与下一步。

**知识问题类**按卡片语境替换，避免把文档错误写成运行故障：

> 问题定位 / 触发条件 / 影响范围 / 修正方向 / 核对方式 / 当前进展与下一步

**知识需求类**没有失败路径，不套根因与复现的段名：

> 缺口定位 / 当前表现 / 影响范围 / 入库方向 / 验收口径 / 当前进展与下一步

变体只换段名与侧重，不减少证据要求，也不改变排除项。

## 复现与影响的证据分级

这两段最容易越界，按实际做过的事选措辞：

| 实际状态 | 允许的写法 | 禁止的写法 |
|---|---|---|
| 实机跑过复现命令 | 「复现结果：<命令> → <输出>」，附平台与版本 | 省略环境，让读者以为通用 |
| 只按 Issue 正文归纳 | 「触发条件（据 Issue 描述整理，未实机复现）」 | 「已复现」「可稳定复现」 |
| 只读了源码或卡片 | 「源码推断：……，未运行验证」 | 「实测」「经确认」 |
| 无法判断 | 省略该段，把缺口写进分析材料 | 用通用技术记忆补「一般是因为……」 |

影响段同样分级：有检索或统计支撑时给数字和口径；没有时写推断范围与不确定项，不换算成“全部受影响”。

## 段落裁剪

- 某段无内容就整段删掉，不写「暂无」「不涉及」占位；
- 问题简单时先给结论，再按骨架补必要段落，不为了凑齐六段扩写；
- 六段是内容骨架而不是字数任务：每段要增加机制、证据或约束，不重复正文和泛化测试清单。

## 与其它规则的关系

- 六段式只替代 vendored `gitcode-issue-handler/references/response-writing.md` 里「不设固定标题」的建议，其余要求（证据自检、授权、承诺边界、发送前复核结尾）继续适用；
- 「已回复」不等于「已修复」：没有实际修改与验证证据时，修复方向段不得写成已完成；
- 发布、指派、关闭仍走原 Handler 的授权与回查，本文件不产生任何外部写权限。

## 发布前自检

1. 这条 Issue 属于适用类型吗？任命申请与 RFC 是否被误套？
2. 复现段和影响段的措辞，是否超过了实际做过的核实？
3. 是否有段落只是占位或复述前文？
4. 结论是否在第一段就给出，而不是留到最后？
5. PR 状态是否只出现一次，且带覆盖范围？
