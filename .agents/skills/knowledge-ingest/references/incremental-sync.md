# 增量同步

仅适用于已接入 Git 上游在同一 ref 上从旧 commit 推进到新 commit。首次接入走新来源流程，ref 或大版本切换走版本升级流程。文档归档不走本流程；需要刷新当前归档时按官方 Reference 流程核对新旧正文与平台范围。

## 流程

1. 从上一批日志、决策账本和现有卡的固定 sources 确认旧 commit；缺少可靠基线时停止并请求明确起点，不猜 `HEAD~N`。
2. 固定新 commit，盘点 `old..new` 的新增、修改、删除和重命名文件，并重新生成完整 inventory。
3. 把变更映射为 `create`、`update`、`merge`、`split`、`deprecate`、`skip` 或 `defer`。删除上游内容不自动物理删除知识卡。
4. 先读原卡，再增量融合新事实；来源冲突并存记录 revision 与适用边界，不静默覆盖。
5. 对每个改动卡做独立来源核验；按 [Ingest 收尾门禁](../SKILL.md#收尾门禁)集中更新导航与日志，完成 Lint、索引重建和目标查询；本地图谱仅在需要查看时另行构建。
6. 只有全部门禁完成后，才在日志/ledger 中把新 commit 标成已落地基线。

决策按语义实体分批。同一张卡涉及多个上游 commit 或文件时合并成一个实施单元，避免重复写入。

模型 Recipes 及其依赖仓采用每仓单一最新提交：先冻结默认分支最新 commit，再逐页对照旧卡与该提交的文档和代码；来源、正文链接和图片最终全部使用新 commit。旧故障、配置或测量必须重新判断当前是否成立，失效结论据实改写或撤回，并从新来源补充知识。不能仅把多个旧 commit 替换成同一字符串而保留旧版技术结论；旧版原文及版本差异保留在 Git 历史和 ignored 审计材料中。
