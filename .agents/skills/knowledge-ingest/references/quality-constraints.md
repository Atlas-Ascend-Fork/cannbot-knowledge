# 质量与证据约束

本文件汇总跨 producer 通用的质量与证据约束，适用于创建和更新所有知识卡。

## 元数据一致性

- `tags`、`platforms`、`sources` 不得重复。
- `platforms` 必须与正文和固定来源证明的实际范围完全一致；未知平台使用空列表并保持 `draft`，不得根据偶然平台词、架构演进描述、章节内局部能力限制或某工作模式限制猜测整卡平台。没有产品支持表或明确以本卡、本接口、本样例等为主语的整卡范围句时保持未知。
- 平台无关只在定义本身不会随硬件变化时使用 `agnostic`，不能与具体平台混用。
- 来源固定、lint 通过和单次成功都不自动生成 `verified` 事件。
- 改写标题或摘要时保留主题的稳定名称、英文名、缩写和关键实现标识。Profile 允许时可用 `aliases` 保存稳定检索名称；不允许时在标题、摘要或正文自然保留，不临时扩展字段。不要把含收益承诺的旧任务长句整段搬进别名；用原名称和实际短查询分别验证召回，避免迁移后规范入口难以查找。

可选 `scope` 只记录来源支持且对过滤有帮助的条件；缺少 Scope 或缺少维度不意味着普遍适用。不得按标题、移动目录或检索相关性扩大适用范围，也不为提升填写率补造条件。不同领域的约束使用各自注册的 Schema，不套用模型推理维度。

## 证据合同

- 官方 Git 证据优先记录固定 revision、仓库相对 path/symbol 和精确 blob，并能把正文 claim 映射回来源。
- 开发轨迹在没有远程 Git 时，按 [trace 证据准入](../../ops-knowledge-trace-ingest/references/runbooks-contract.md#81-证据准入来源模式--内部知识形态)保留原始来源与归一化产物的 SHA-256、记录位置、逐字机制材料和客观观测。证据要求随知识形态区分：修复配方需要失败、before/after 与修后验证；诊断规则需要触发、探针与观测；失败路线需要尝试、客观失败或回退与边界；已验证模式需要完整实现与验证。不得仅因非修复形态没有 before/after 而拒绝；缺少该形态的关键锚点时 defer。
- GitCode/GitHub Issue/PR 证据使用对应仓库的规范工作项 URL；能定位实现时同时保留固定 base/fixed revision、实际代码变化和验证结果，Issue prose 本身不是技术事实。
- 文档、声明、实现或实验冲突时保留双方、revision 和边界，不选择更宽说法静默覆盖。

## 内容边界

- 正文通常保存可复用结论、条件、失效边界和验证方法；Registry 文档归档的官方 API/Guide 只为含独立技术事实的来源页建卡，README、发布占位、纯链接目录和接口清单等导航页统一由 `index.md` 替代。保留页除 Registry 声明的冗余章节和失效链接目标外保持来源正文完整；当前“产品支持情况”先用于生成 `platforms`，再从正文删除。归档发布器已确认的正文损坏只能在获取阶段对已知文件和 token 做幂等修复，不固定次数或校验内容树 SHA-256，不能在知识卡生成阶段静默改写。批次、diff 范围、skip 理由与执行过程进入日志/ledger。
- 正文图片使用带 40 位 commit 和具体文件路径的 HTTPS Git raw URL，不复制本地图片资产。
- 不保留 Git 冲突标记或未收敛 TODO；文档归档 API/Guide 受控转换之外不保留大段上游原文。保留的来源正文尾随空格可能承载 Markdown 换行语义，必须随来源保留，不执行通用空白归一化。
- 一概念一 canonical 卡；交叉引用已有卡，不复制第二份同义内容。
- 按需生成的 API 到 Operator 引用建议只接受可复验的明确调用：优先来自卡片声明的固定版本源码；仅有正文证据时单独标注，不宣称已在源码调用。完整同名集合的唯一归属必须早于平台与参数数量过滤，泛化符号与已审核否决 pair 不得绕过。源码范围、词法排除、证据形状及展示上限统一遵循[本地图谱](local-graphs.md)；限额只影响建议展示，不限制正文链接或图谱边，不抹去完整审计。
- 完整样例工程、算子模板编译、轨迹进化等需要专用 producer；当前未迁移时明确 defer。

## 模型推理卡片组织

先检索同主题候选并读完整正文和来源，明确 create/update/merge/split/deprecate/defer。Concept 解释机制，Optimization 拥有优化决策，Guide 串联任务，Case 只补特定条件下的实施差异和证据；其他卡通过链接复用规则。反模式已有完整“症状—探针—修复—验证”链路时由 Runbook 承载。不要为了配齐类型复制正文；目录迁移和归并先形成逐卡清单，不能按标题自动合并。

正文按职责覆盖以下内容，可保留语义等价的小节，不能用标题齐全代替内容或补造缺失证据：

- Optimization：适用场景、问题信号、优化规则、机制、实施要点、收益、代价和风险、回退方式、验证方法、适用边界、相关经验、Evidence。
- Runbook：症状、快速检查、诊断路径、根因、修复、验证、回退和残留风险、Evidence；轨迹型知识继续遵守对应 producer 的形态与证据准入。
- Benchmark Observation：Workload、Hardware、Software、Baseline、Variant、Metric Definition、Repetition and Variance、Result、Limitations、Evidence。记录 batch、序列长度、并发、卡数/并行、软件版本、warmup/重复次数、指标定义、受控对比和独立复测情况；来源未提供时明确未知，不将单次或仓库自报数据泛化成性能保证。

稳定卡需要明确适用范围、失效边界、验证信号和相应证据；`scope` 只填来源支持的条件，`verified` 仍只记录真实复核事件。Scope 未标注不等于普遍适用，Case 和观测数据也不因关联规则有更宽范围而获得同等适用性。
