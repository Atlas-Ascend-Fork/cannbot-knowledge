# 使用知识库查询 API

## 目标

通过已安装的 Ascend C API 查询 Skill，找到与目标硬件匹配的接口说明，并依据完整正文和来源回答问题。

## 适用场景

- 开发AscendC算子（如 foreach_addcdiv_scalar、rms_norm）时需要确认 API 签名、参数含义或平台支持情况
- 问题涉及具体开发硬件平台（910B/910B2/950 等）
- 需要同时查看签名、参数、约束、示例和使用方法

## 不适用场景

- 知识库索引不可用；此时先恢复索引，不能把查询失败解释为 API 未收录。

## 前置条件与输入

- 已由安装器或维护者准备的有效索引；当前采用字段加权的确定性词法检索。
- 明确的 API 名称和关键约束（如 `Div count 对齐`）
- 目标平台标识（如 `a2`、`a3`、`950`）
- `knowledge-query` 与 `ascendc-api-knowledge-query` Skill 可用。
- Ascend C 专用流程使用与 Query 同装的 `ascendc-api-knowledge-query`；需要本机头文件证据时提供当前工程的 CANN 版本和包路径，详细定位流程以该 Skill 为准。

## 步骤

1. **明确问题。** 已知准确 API 名时先按该标识查询；只有能力需求时，用“实体 + 一个关键约束”描述问题。准备真实硬件型号和需要核对的条件。
2. **执行查询。** 使用 [`ascendc-api-knowledge-query`](../.agents/skills/ascendc-api-knowledge-query/SKILL.md)；它复用 Query 的平台过滤与匹配流程。参数和补搜规则由 Skill 维护。
3. **选择候选卡。** 根据标题、摘要、路径和状态选择要阅读的卡片。优先选择平台匹配、状态为 `stable` 的卡片。
4. **打开卡片正文。** 阅读完整保留的官方文档正文，包括签名、参数含义、约束条件、示例和平台范围；再沿正文中的普通链接查看相关算子设计卡，并核对目标卡中的调用证据。不要直接使用搜索摘要作答。
5. **核对来源。** 确认来源确实支持准备采用的结论。如果多张卡片冲突，先比较它们的平台、版本和来源。
6. **补搜未定位卡。** 精确 API 名在目标平台的 stable 查询零命中时，按 Skill 单独补搜平台未定位的 draft 卡。此类结果只能提供待核验线索，必须阅读正文或来源确认平台；不能并入主查询的结果或共用审计凭据。
7. **降级路径。** 未定位 draft 补搜仍未命中时，降级到官方来源核对原文。

## 预期产物

一个带结论、适用范围、依据和限制的回答，例如：

```text
结论：<API 签名和参数说明>
适用范围：<平台、版本和其他条件>
依据：<使用的知识卡和来源>
限制或冲突：<不适用情况或不同结论>
仍需验证：<源码、实验或性能分析>
```


## 效果对比

以下保留一组既有的内部对比记录：75 条来自算子开发的 API 查询，每个查询单独开会话，对比 docs-search 与 knowledge-query 的耗时、回合数、工具调用和 token 用量。当前仓库未附这批样本、逐条结果、运行配置和评判标准，因此这些汇总只作观察记录，不能作为可复现的效果保证。

### 第一轮：deepseek-v4-flash

| 指标 | docs-search（baseline） | knowledge-query（本仓库提供的 skill ） |
|---|---|---|
| 平均耗时 | 47.4s | **32.6s** |
| 回合数 | 7.8 | **6.3** |
| 工具调用 | 11.2 | **8.7** |
| token/条 | 33.5K | **27.6K** |

### 第二轮：glm-5.2

| 指标 | docs-search（baseline） | knowledge-query（本仓库提供的 skill ） |
|---|---|---|
| 平均耗时 | 58.3s | **44.9s** |
| 回合数 | 7.7 | **6.0** |
| 工具调用 | 11.2 | **8.1** |
| token/条 | 33.3K | **26.8K** |

### 第三轮：minimax-m2.7

| 指标 | docs-search（baseline） | knowledge-query（本仓库提供的 skill ） |
|---|---|---|
| 平均耗时 | 131.9s | **69.3s** |
| 回合数 | 9.2 | **5.8** |
| 工具调用 | 10.2 | **5.1** |
| token/条 | 56.1K | **46.8K** |

耗时可能受到测试时段、服务负载、工具版本和运行环境影响；缺少受控实验，不能据此比较模型能力或确定耗时变化的唯一原因。

### 重合度分析

原记录报告内容重合率超过 96%，但未提供计算方法和逐条对应关系。结果重合不能单独证明答案正确、召回完整或质量没有下降；需要公开样本、预期证据及逐条评判后才能评估这些指标。

### 实验总结

按表中已四舍五入的均值计算，三轮耗时分别降低约 31%、23%、47%；回合数分别减少 1.5、1.7、3.4；每条查询 token 分别减少 5.9K、6.5K、9.3K。若三轮样本等权，平均每条减少约 7.2K token。这些数字仅描述上表，实际任务的性能与答案质量仍需分别验证。

## 验证方式

- 命中卡的路径 Profile 是 `apis`，平台包含目标平台，生命周期满足当前查询条件。
- 正文中的签名、参数、约束和版本边界能分别回到 `sources` 核验。
- 使用仓库的检索回归验证代表性 API 查询。

## 失败或停止条件

- 索引缺失、损坏或 stale：停止查询，请维护者重建索引。
- 目标平台 stable 查询和未定位 draft 补搜都零命中：报告知识缺口，不把它解释为 API 不存在。
- 候选平台、版本或来源互相冲突：停止给出确定性结论，先核对固定来源或目标环境。
