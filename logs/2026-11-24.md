## [22:43] diagnose(mcp) | 远端网关 404 根因定位：Claude Code PRD 带尾缀 404 是代码 L3891 路径错位，非网关配置

### Summary

排查 Claude Code 对远端 `https://mcp.hicann.cn` 认证失败（"Dynamic Client Registration rejected (HTTP 404)"）。逐端点探测远端四条 PRD/AS 发现路径并对照本地源码与 SDK 路由注册，定位为**代码缺陷**（`server.py:3891` SDK 模式 PRD 转发路径错位），网关配置无责——重部署当前代码即可修复，网关不需要改。

### Details

- 症状链：`/mcp` 401 的 `resource_metadata` 指向 RFC 9728 插入式带尾缀 URL `/.well-known/oauth-protected-resource/mcp/gateway/mcp-server/mcp` → 404 → 客户端把 AS 误判为站点根 → 根级 DCR `/register` nginx HTML 404。
- 远端实测矩阵：PRD bare 200、PRD bare+/mcp 404、PRD 插入式无尾缀 200、PRD 插入式带尾缀 404（404 响应体为 Starlette 风格 `Not Found` 9 字节 text/plain，证明是后端返回而非网关拦截）；AS 四条全 200。
- 源码定位：SDK 模式下 `streamable_http_app()` 内 SDK 的 `create_protected_resource_routes` 将 PRD 路由注册在 `/.well-known/oauth-protected-resource` + `urlparse(PUBLIC_URL+"/mcp").path`（即带完整前缀+尾缀的插入式路径，本地 `.venv` 实例化验证）；而外层 dispatcher `server.py:3891` 只把 `/.well-known/oauth-protected-resource/mcp`（bare+/mcp）转发给 inner——网关把插入式带尾缀请求剥成 bare+/mcp 到达后端后，L3891 转进 inner，inner 只有带完整前缀的路由，Starlette 404。
- AS 为什么不受影响：`server.py:3698` 外层手写 handler 对 `_discovery_paths()` 全部四条路径直接回 200（含 device_authorization_endpoint 的权威文档），不经过 inner，网关剥成哪种形态都命中。
- 修复方向（待另行提交）：`server.py:3891` 的转发条件与 SDK 实际注册路径对齐——bare+/mcp 与插入式带前缀+尾缀两条都应被正确处理（后者外层 `server.py:3908` `_sdk_pr_metadata` 分支已能 200，问题是网关剥尾缀后变成了前者）。最小修法：L3891 分支不转发 inner、与 L3908 合并直接回 `_sdk_pr_metadata`（SDK 模式下 bare+/mcp 目前无正确响应者）。
- 关联：远端部署版本指纹 = SDK_AUTH=on + PUBLIC_URL 含 `/mcp/gateway/mcp-server`（PRD 响应体 `resource` 以 `/mcp` 结尾、`authorization_servers` 为前缀根、无 `scopes_supported`，与 `_sdk_pr_metadata` 形态一致）。
