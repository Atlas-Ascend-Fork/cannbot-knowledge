### Summary

## [18:53] test(docker) | 远端主机 Docker 实测：httpx 依赖缺口与 HOME 固定两处修复

### Summary

在远端测试机（独立目录 checkout，host port 18092→容器 8090，宿主 8090 已有现役部署不占用）对 compose 全栈做真实容器验证，发现并修复两处只在 Docker 形态下暴露的缺陷：①`httpx` 从未声明为运行依赖（本地开发被 httpx2 的 httpx 兼容命名空间掩盖，镜像内崩溃）；②`auth.key` 路径取 `Path.home()` 而 setpriv 只改 uid 不改 HOME，uid 1000 无权读写 /root，签名密钥静默回退为内存临时密钥——auth 卷的持久化被架空。

### Details

- 缺陷一（9c13256c）：GitCodeTokenVerifier/OAuth 回调自 dec6a21f 起 import httpx，但 pyproject.toml/Dockerfile 只声明 mcp/uvicorn/pyyaml。容器启动即 `ModuleNotFoundError: No module named 'httpx'` 崩溃循环。修复：pyproject/uv.lock/Dockerfile 三处显式声明 `httpx>=0.27,<1`；`uv lock`+`uv sync --frozen`+全量单测 233 passed（fakeredis/redis 为测试专用依赖经 `--with` 注入，不进运行依赖）。
- 缺陷二（e8c491e7）：entrypoint 新增 `RUN_HOME=${AUTH_DIR}/home`，mkdir+chown 后以 `env HOME=...` 启动服务器；auth.key 落在 `/data/auth/home/.local/state/cannbot-knowledge/mcp/auth.key`，随卷持久化。
- 实测通过的验证矩阵：`/health` 200；未认证 401 带 RFC 9728 `WWW-Authenticate resource_metadata` 挑战；AS metadata（8414）端点齐全；设备码流程完整走通（issue→pending→allow→token，无 OAuth client 配置时走手动输入+用户名路径）；设备令牌调 discover 10543 卡成功；自服务 API key 创建并调 /mcp 成功；`docker compose down`→`up` 全周期后 API key 与旧 JWT 均仍有效（auth.key 不再临时化）；refresh 轮换成功且旧 refresh 重放 `invalid_grant`（jti 台账跨重建存活）；连续认证失败触发 IP 冷却 429（retry-after 300，state.db 可见 `cd:block:*`），冷却期内好令牌同样被拒（fail-closed）；调用日志四类事件（call/auth_failed/api_key_created）落 /data/logs；`:ro` bind 拒写验证；服务器以 uid 1000 运行（docker top 确认）。
- 远端测试机侧环境适配（不改仓）：aliyun pip 镜像（官方源超时）、宿主 checkout 预建 `artifacts/indexes/`（Docker 29.4 嵌套卷挂载点问题）、compose 端口映射 18092:8090（8090 被现役部署占用）。这些是部署侧参数，仓库文档已有对应说明（FAQ 端口冲突、PIP_INDEX_URL）。
