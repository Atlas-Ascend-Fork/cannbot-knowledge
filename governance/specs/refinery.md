# 精炼规约(预案)

*这篇文档为一个目的服务:给 CANN 与算子开发攒一座 **AI 原生**的知识库——知识长成模型用得顺手的样子,可信不可信由可证伪的检查和独立的复跑说了算,不靠谁的一句话。*

*做法是:在本仓开一条长期分支 `refinery`(下称"精炼区"),上面跑一个去中心、**递归自我改进**(RSI)的知识精炼系统——粗料宽进,蒸馏严出,订单自己产生订单,每隔一个周期把确立的成品送进 master 上一个独立的成品目录。本文只管三件事:**这套系统怎么运转、东西怎么进出精炼区、精炼区里面的规矩**。*

*先把三件事说在前头。第一,这是一份**预览版**:以 PR 直接提交、边评审边修;其中的结构请求(独立成品目录及其配套改动)在仓库接受并通过部署验收(§10)之前一律不启用,在那之前本文不改变 master 的任何现行治理。第二,这里的参与者——人和代理——**是同一边的**:精炼区是代理的世界,没有人来刷提交数、攒声望。所有的门和复核,防的是**诚实的错误**——一次测量会说谎,一次誊写会不小心把"这个环境成立"写成"所有平台都成立"——不是防坏人。第三,本文只带理由和规矩;工具和设施是跑起来之后按需长出来的,除 §8 种子里的承重门外不预先设立,以防止过度干预。*

## 0. 为什么这么设计

- **第一读者是模型。**对模型有用的知识,不是更多的字,而是:结论自己说得清、环境钉得死、可信程度一眼看得出、出处机器查得到。"AI 原生"就是这个意思,下面几条都是它的展开。
- **核验的账该记在谁头上。**如果核验一条结论要花读者的注意力,读者只有两个选择:全信,或者全不信。精炼区把这笔账挪走——挪给会跑的检查,挪给两只独立的手;读者只需要看标签。
- **知识在用的那一刻应该几乎不花钱。**要先读半天才有用的知识,到了现场帮不上忙。所以成品卡自带结论、环境、读数、失效边界,不用翻别的东西就能判断。
- **纸上的规矩不会自己执行。**规矩迟早被自己的作者违反;承重的规矩不能只靠自觉——可机检的部分交给检查,技术判断仍靠证据、复跑和复核。所以本文里承重的规矩,都要落成一个会跑、而且被坏样例咬过的检查;没有检查撑腰的条文,只能算说明文字(§9)。
- **记一件事的成本必须是常数。**记录比干活还贵的系统,会被自己的台账拖死。所以一切记录定字段、定尺寸;写不下的细节放进可复跑的程序,记录指向程序。
- **系统递归地改进自己。**产出回头喂生产者:工位干活时消费成品库,包括干精炼这件事本身;失败和缺口变成新订单,订单再生订单(§5.6);检查器被坏样例喂着长大(§5.7),可调的数字凭证据修订(§10)。知识让工位更强,更强的工位产出更好的知识,出错的地方变成下一轮的活——库在长,长库的系统也在长。

## 1. 全局一张图

```
工位分支 ──PR──▶ refinery 分支(日常全在这里) ──每周期打受保护 tag,切过境分支──PR──▶ master 的成品目录
```

- **日常全在精炼区里。**工位从 `refinery` 切自己的分支,干活,PR 回 `refinery`;门在这里跑。持有当前阶段合并权限的**非作者**工位复核门绿的 PR 并合并(权限分阶段放大,§8);其他工位到场同样先复核,只是不执行。master 不看这些,也不用看。
- **出门按周期。**每两周(可调,§10)或一批攒够:在 `refinery` 上打受保护 tag(周期号唯一,§6),从 master 切过境分支,只带这个周期的成品 diff 和随行材料(§6),PR 进 master。
- **单向。**出了门的东西不回头改;要改,在精炼区改,下个周期自然带出去。精炼区内部的历史不出门。
- **成品目录独立于 `knowledge/`**:默认放顶层 `distilled/`,具体位置可以商量——不放进 `knowledge/`,不碰它的 Bundle 边界、Concept ID、索引和链接规矩。本文不自己改写"唯一知识正文根"那句话;这个结构扩展,连同所有要跟着动的地方——README 入口、需要知道新目录存在的治理 Spec/Schema/Profile/Contract、文档与回归测试——在本预案里明着提出来;原 knowledge Bundle 的身份和默认行为不变,新目录的身份、链接、消费范围另立明确约定;**扩展没获准、没验收,就不开始过境**。
- **时间口径。**master 上成品带的一切标签,意思都是"**截至那个周期的快照**是这样",清单绑着来源 commit;周期之间的变化,下个周期带出去,不承诺实时。

## 2. 四条底线

其余规矩都是这四条的推论;这一页长过注册的字数上限(§10),就是设计开始漏进散文的信号(§9)。

```
一 出处   没有证据的内容不被相信。一张卡承重的依赖必须全部有效,一路
         向下查到不引用任何东西的原始观测为止。链条断在哪里,哪张卡
         就立刻不能被消费、不能出门——这由会跑的检查当场算出,不等
         人想起来。
二 过境   出门的卡和它确立时的记录逐字节一致;标签原样出门,并说清自己
         是哪个快照的结论;没确立的内容,不许用实测的口吻出现在任何
         成品里。
三 记录   记录定字段、定尺寸,记一件事的成本不随库变大。可信程度、订单
         死活、缺口开闭、能不能出门,一律在被问到的时候对着快照当场
         算;标签和清单是绑定输入 commit 与检查器 commit 的快照产物,
         不是状态的老家。工具不许报它这次没算过的状态和统计;已记录
         的实验读数可以原样展示,但要和现算的值分开标。
四 见证   每条记录署名,署名就是账号,检查会核对。确立 = 两个不同账号
         在各自设备上独立做成这件事;一张卡的起草者,不能给自己的这
         一版作见证——作者不该是自己结论的唯一证人。
```

## 3. 知识卡长什么样

精炼区里承重的东西——主张和成品条目——是同一种卡的两个形态。一张合格的卡:

- **一条主张,一张卡。**工作形态按稳定 id 存放;成品的文件名用表达断言的 snake_case 名称。文件路径和稳定 id 的对应要明确,修订文字不悄悄改变条目身份。一张卡混了几条主张的,拆开。
- **出处先于知识。**没有出处的内容进不了卡;出处要么指向树里的观测和原料,要么是钉死版本的外部来源。原料和外部摘录可以当线索;哪些引用能承重、何时有效,按 §5.4 判断——不能只因"有出处"就算确立。
- **标签跟着证据走。**抄来的(有出处、没人验)→ 单手(一个账号验过)→ 确立(满足 §5.4 的全部条件,包括两个账号的复跑)。卡自己怎么宣称不算数;标签从验证事件里现算出来。
- **写明什么情况会推翻它。**每张卡带失效边界:出了哪个环境、哪个版本、哪种输入,这条就不保了。
- **环境钉死。**结论在哪个机型、哪套工具链版本上成立,写在卡里——机器住在卡里,不住在目录里;换一台新机器是加一行,不是加一个目录。
- **语态诚实。**没验证过的内容,不许写成亲手测过的样子。
- **写不下的细节放进可复跑的程序**,卡指向程序。卡是给读的,程序是给跑的。

## 4. 入门:宽,只有两种拒绝

- **什么能进**:任何"提出一个想法、附上粗料"的东西——会话轨迹、实验观察、设想、文献摘录。
- **什么形式**:一张原料卡 = 四个内容字段(来源:路径、链接或一句话;内容或引文;时间;内容哈希)+ 署名(账号、提交时间)。齐了就收,不经任何人判断。
- **只有两种拒绝**:字段不齐(补齐就收),和公开红线。投进来就是公开的,公开收不回,所以红线扫描在**推送之前**就地执行——这件装备必须在种子里(§8),不能等第一次出事再造。扫描按注册的模式集查密钥、令牌和登记过的不可公开模式;它不是能认出一切敏感信息的神器,**脱敏的责任始终在提交者**。
- **原料不承重,错了就错了;原料永不出门。**真正的门在确立(§5.4),不在门口。

## 5. 精炼区里面

### 5.1 谁在干活

| 角色 | 是什么 | 干什么 | 不干什么 |
|---|---|---|---|
| 工位 | 一个账号 + 自己的设备和工具链 | 投料、领活、加工、替别人复跑作见证、复核并合并门绿的 PR(需当前阶段权限)、发起过境 | 给自己起草的那版卡作见证;绕过 PR 直推 `refinery` |
| 收料器 | 机器 | 核原料卡字段、写前红线扫描、收料 | 对内容做任何判断 |
| 周期评审 | 每周期来一次的独立账号(人或代理,§5.8) | 只读评审;往活清单投订单;把外部信息做成原料投进来 | 领活;关自己立案的缺口 |
| 发起人 | 低频出现的人 | 写第一张订单;签可调数字的修订;裁决上诉;**阶段一期间复核确立与过境** | 阶段二起退出日常 |
| committer | master 侧,本仓现有角色 | 按 CONTRIBUTING 检视过境 PR、执行合入(§6) | 本文对其不加任何新要求 |

工位随来随去,谁都能克隆下来就干活;人来人走只发放或吊销账号与令牌,系统本身不动。

### 5.2 树上有什么

精炼区的树上只有**六类业务记录**,每类定字段、定尺寸(数值见 §10;装不下的细节进程序)。要出现第七类,先改本文,不是加目录:

| 记录 | 位置 | 内容 | 谁写 |
|---|---|---|---|
| 原料卡 | `rough/` | 四个内容字段 + 署名(§4) | 投料的工位 |
| 观测 | `book/obs/<sha256>.obs` | 命令 · 环境 · 日期 · 退出码 · 作者 + 原始输出,文件名是自身内容的哈希 | 只由跑器写;不引用任何东西,写完不改 |
| 主张 | `book/claims/<id>.c` | 卡的工作形态(§3):id(带账号前缀) · 主张原文(一条) · 机器 · 工具链 · 复跑程序的指针 · 日期 · 作者 · 引用(分承重/线索) · 所关缺口 · 失效边界 | 起草的工位 |
| 订单 | `orders/o-<账号>-<序号>.md` | 要什么(怎样算完,立单就冻结) · 用什么机器 · 预算 · 完成的定义(§5.6) | 结单的工位铸造;发起人与周期评审也可投 |
| 日志行 | `journal/<作者>-<utc>.j` | 日期 · 作者 · 订单 · 事件 · 目标 ID · 目标版本哈希 · 结果 · 缺口;一行一个文件 | 做这件事的人 |
| 成品条目 | 成品目录 | 卡的消费形态(§3、§5.5) | 誊写的工位 |

**事件是个关着门的清单**:领活、续租、释放、验证、反证、撤销、结单、拒绝、批准(阶段一)——每种事件规定必填字段(验证事件的字段见 §5.4);平台上的事实(PR 什么时候开的、什么时候合的)以只追加的记录进树;要扩这个清单,走 §10 的通道。

**一行一个文件**不是讲究,是机制:它减少文本冲突,两个工位的活多数情况下合并即取并集——去中心靠这个成立,不靠调度员。**共享的名字**(订单号、卡的 id、谁结的单)由检查在合并时对着最新的树裁决,文件系统防不了的,门来防。**缺口不是一个状态,是一个名字**:日志里有人点过它,它就存在;有确立的卡关了它,它才关;这些都是问到时现算的(§2·记录)。精炼区不设状态板——**PR 列表就是状态页**,谁在干什么,一眼看得见。

### 5.3 怎么领活

活清单 = 开着的订单。没有派活的人,各工位看自己的设备和版本自己挑。规矩都是为了协调,不是为了提防:

- **领活从 PR 可见那一刻起算数**——没开 PR 的领活别人看不见,看不见的占座不存在;时间以平台事件为准;
- **续租要附上这张订单的新进展**(新观测,或可核验的半成品),次数有上限(§10)——租约是让别人知道活还活着,不是用来占着的;
- 过了租期没进展,谁都可以释放。判断"过没过期"要三样输入:**仓库 commit、可信的当前时间、平台事件快照**——光看 Git 树算不出租约;
- 两个工位领了同一张订单不是事故:后来的那位正好站在第二只手的位置上(§5.4);单只结一次,按合并顺序定;
- 凡是影响确立、结单、出门的门,都对**真正要合并的那棵树**重跑,不是只查名字撞没撞;
- **尝试不受审,确立才受审**:失败的尝试只花一行日志,和它点名的缺口。

### 5.4 怎样才算确立

一句机器能核对的定义:

> 在某个快照下,一张卡算确立,当且仅当:它的形制合规;它承重的依赖全部有效、没有循环,一路到原始观测;有**至少两个不同账号**的成功验证事件,各自绑定同一组〈卡的内容哈希,程序及依赖哈希,环境指纹,判据〉;并且没有有效的反证或撤销。

展开说:

- **绑四样东西**是为了精确:见证见证的恰好是"这一版卡、这一套程序、这一个环境"。结论、程序、环境任何一个改了,旧验证自然对不上号,得重新见证——防的是张冠李戴,不是造假。
- **验证事件的字段是关死的**:作者和执行实例、那四样东西、自己那次观测的内容哈希、按判据对读数算出的结果——**成败由判据算出来,不由一句"成功了"说了算**。
- **依赖"有效"的意思**:引用的卡递归地已确立;引用的观测存在、哈希对得上、形制合规。线索类引用不参与确立。
- **两只手怎么数**:起草者自己的第一次实测可以算一只;第二只必须来自这版卡起草者以外的账号。
- **验证、反证、撤销都只添新事件,不回头改旧事件。**标签对快照现算;承重依赖一失效,消费和出门的门当场拦住,不等另开一个改标签的 PR。要改结论、程序或适用范围本身,才单独开 PR——这个"才"只是和改标签相比,不豁免其他提交本来该走的 PR 规矩。
- **环境指纹**按注册的 Profile 比(§10):同指纹的复跑,是同一行主张互相印证;**指纹不同,各记一行**——同一条主张在两个环境是两行记录,各有各的手。必填字段缺了,就是没有互证资格,不默认兼容。
- **给不出复跑程序的主张,确立不了**:别人没法照做重现的想法,留在原料层当线索,不以知识的身份出门。
- 测量上有分歧,回那个环境**重跑**,不开会讨论;同指纹下出现相反的主张,这叫**争议**,消费那头必须能看见并且被拦住(§7),不能两边都当成定论。对本文规矩的分歧,走 §10 的通道。

### 5.5 成品怎么誊

确立的卡由任一工位誊成消费形态(§3):正文自含结论、环境、读数、失效边界;头部沿用本仓 Frontmatter 公共字段的形制;引用指回它承载的主张。**誊写不是创作,是确定性生成**:承重的字段(结论、环境、标签、读数、边界)全部由冻结的主张和证据生成、逐字段核对——结论和主张原文**逐字节一致**(§2·过境说的就是这个);标题、摘要这类自由文字只能用固定模板或已确立的内容,不许带进任何新断言。模型誊写最常见的错,就是悄悄把范围写大——检查器的坏样例必须专门盖住"结论没变、头部把范围扩了"这种卡。

**证据怎么引**:成品用**固定 40 位 commit 的 HTTPS 引用**指回精炼区里的主张、观测和程序(和本仓来源钉 commit 的习惯一致),并给出取证和核验的入口;master 的克隆不需要精炼区的文件也能把条目读明白,要复核时按引用去取。这个方案要正常运转,有几件事列进部署验收(§10):受保护的周期 ref 保证那些 commit 一直取得到;引用盖住主张、两个验证事件、各自的观测、程序及依赖、用的检查器;取证入口按 commit 精确取,不跟着分支走;取回来校验哈希、能跑核验;取不到或校验不过,老老实实返回**"证据不可复核"**,不装成通过。

### 5.6 订单怎么自己产生订单

一张订单写四样:要什么(怎样算完,必须可检,**立单就冻结**)、用什么机器、预算、完成的定义;只说目的,不说做法。结单时按当初冻结的标准验收;结单的最后一个动作是铸造新订单:**b = max(0, ⌈r·(1−N/K)⌉) 是上限,不是任务**——N 从真正要合并的树里算:先扣掉这次结掉的订单,也不算这次新铸的订单,只数其余还活着的订单;r、K 见 §10;没有足够的真缺口就少铸、零铸,写明原因。新订单必须挂在**没解决、去过重**的可检缺口上(换个说法的同一个缺口不算新的);如果活着的订单全出自同一个血统,这次真要铸的时候,优先铸血统之外的缺口——**不许为了凑血统去编缺口**,开缺口不等于非得铸单,零铸和总量上限都不破。

缺口还有两个来源,保证清单不干涸、库不靠人想起来才保鲜:

- **巡检**(检查器的定时任务):链断了、来源失效了、环境漂了、确立太久没人复核——各自动开卡;
- **周期评审**(§5.8):外面的需求和使用反馈,写成订单进清单。

### 5.7 检查怎么管自己

种子带**整套承重门**(§8);检查可以说不,但每次说不都要可查、可申诉。检查器每次升级都过两面镜子:**已知的坏样例必须全拦住,已知的好样例必须全放行**——坏样例漏网那天,检查器自己亮红。**没拦过错东西的检查,它的"通过"不算数。**规矩和检查器自己的改动走**单独的受保护路径、单独的 PR**,不和被检查的东西混在一个变更里——这是干净的改法,也让"门是怎么变的"永远查得到;门跑的是已合并的可信版本,不是待检分支里的那份。其他顺手的工具(巡检、统计、索引重建)不预装:哪天规矩第一次要用它,它经由缺口和订单到来。

### 5.8 每周期的外部评审

每个周期 tag 之后必跑一次,相当于挂在 tag 上的 CI,由独立账号承接——资格窗口(§10)内提交过卡的账号不能接;没有合资格的人,这个周期照常出门,评审缺席自动开卡提醒发起人。干三件事:

- **评审**:冷克隆、只读,按固定清单走——抽样复跑卡的程序、核引用链、对着本文找漏项、验证检查器的坏样例还咬不咬人;发现走普通入口,一样的证据要求、一样的两只手;评审结果针对该周期的 source commit 另记一个 commit,不要求出现在被审的 tag 里;
- **投单**:把外部需求、下游反馈、master 那边的评审意见写成新订单,进活清单;
- **投料**:外部信息做成原料卡,从入门进(§4)。

评审报告写明承接者的账号、机器、是人还是哪个模型——独立性是一条可查的记录,不是一句话。

## 6. 出门:master 认门,不认人情

- **节拍**:每两周一个周期(可调),或一批攒够先到;周期号唯一(`cycle-<YYYYMMDD>-<序号>`),tag 受保护;清单记本周期的 source commit 和上一次成功出门的基线。**基线按条目算,不按批算**:清单逐条记下 master 实际收了哪一版、文件哈希、合并记录;只合了一部分时,没合上的条目明着进重试,不会因为基线整体前移而被漏掉;第一个周期从空集合起步;PR 挂着的时候 master 前进了,门对真正要合并的树重跑(§5.3)。
- **谁来发起**:任一工位(不能是本周期条目的唯一作者,§2·见证)从 master 切过境分支,对固定的 source 和 master 基线生成同一份补丁——新增、更新、弃用分开列,不碰 master 上不相干的东西;重试可以反复做而不出岔子。
- **出门的东西分两种**:**新增和替换**,必须已确立(§5.4);**撤销和弃用通知**,不要求"确立"——被推翻的卡恰恰不再确立——但必须附上指向旧成品和反证/撤销事件的依据。纠错的路不能被"没确立不许出门"堵死,被推翻的旧结论也不能换张脸当新事实发;消费那头按撤销事实拦住旧条目(§7),历史和快照口径保留。
- **随行材料**:一页清单(条目、作者与见证、环境指纹、标签及其快照时点、机检结果、来源 commit、输出文件哈希、检查器 commit 与命令、逐项证据引用),成品索引的同步,当天 `logs/` 一条;过境分支要过本仓的 `bash check.sh`。完整证据按 §5.5 的引用可达,一页清单只做导航。
- **门和检视**:门在精炼区跑完、结果逐项写进清单。**清单汇总的是本仓现有贡献流程本来就要的证据**,逐项关联本预案和相应 Issue(本次 PR 提交的是预案文本供评审;日后实际过境的贡献材料,按仓库届时适用的流程准备);committer 照 CONTRIBUTING 判断内容、效果、兼容性,可以要求复跑、拆分、延期——**门绿给的是可核对的事实,不是合入的权利**;合并由非作者之手执行,这正是本仓现行的合入规则本身。
- **自动化的边界**:本预案不引入任何自动提交、推送、合并或发布的仓库脚本与 Skill;代理贡献者的操作范围、它和 CONTRIBUTING §2/§7 的适用关系,经本预案的评审明确确认,确认之前不启用相关自动操作;master 的检视与合入完全照旧。
- **被拒**:被拒的条目退回精炼区,自动立案成缺口,进活清单;其他条目不陪绑。**下游发现出门的卡错了**:反证事件进树,精炼区这头立刻拦住它的消费和再出门,下个周期以修正或弃用的形式带出去;两个周期之间,master 上的标签始终是快照口径(§1)。

## 7. 成品怎么被使用

后来的使用者——人或模型——落地第一眼就该明白这是什么、怎么用:

- 成品目录顶层一页 `index.md`:这一层是什么、标签什么意思、怎么引用、怎么按引用取证;
- 目录结构照着 `knowledge/` 的领域划分来,文件名就是断言;
- **身份稳定**:条目 ID 不随文字修订偷偷变;卡的版本用内容哈希说话;适用条件、失效条件、判据和读数是**可解析的字段**,正文自含解释;
- **默认过滤**:没确立的、被撤销的、环境对不上的,不进默认消费;同指纹的相反主张以"争议"返回并拦住,不并排当事实;查无结果就是查无结果,不退化成猜;
- **不动本仓的信任词汇**:verified 事件的 machine-confirmed / human-reviewed 含义一个字不改——两个代理 actor 的事件仍然是 machine-confirmed;"确立"是这套机制自己的尺子,两把尺并存,谁也不冒充谁;
- **标签不说谎**:它如实报告截至周期快照的状态;机器担保的是形制、链条、见证记录,技术结论本身由证据和复跑担保;
- **第一批使用者就是精炼区自己的工位**:工位加工、复跑、誊写时都消费成品库——这是递归自我改进的那个环,成品的质量直接决定下一轮成品的质量;
- 检索入口(扩展本仓 Query,还是独立一套)另行提案,不在本文;**入口做出来之前,成品只按目录和索引用,不声称本仓 Query 已经覆盖了新目录**;启用前拿一组固定的真实问题实际验五件事——找得到、环境不对的被滤掉、争议被拦住、撤销被拦住、查无结果不瞎猜。

## 8. 怎么起步:三个阶段

| 阶段 | 有什么 | 人管什么 | 往下走的条件 |
|---|---|---|---|
| **〇 种子就位** | 本文;第一张订单(发起人写);**整套承重门**——形制检查、写前红线扫描、记录解析与事件计算(含 §5.4 的定义)、身份核验、过境门——连同它们的好坏样例 | 发起人写第一张订单 | 坏样例全拦住、好样例全放行;环境 Profile、判据、事件字段的 schema 冻结;部署验收(§10)逐项过 |
| **一 人在环试运行** | 首批登记的工位,其中**至少一对:同机型、同一套工具链、不同账号、不同设备**(异构工位扩大覆盖面,但同一行主张的互证只能来自同指纹的两只手);开始收公开投料 | 发起人复核**每一次**确立和**每一次**出门——复核是查得到的凭据:对〈卡的版本哈希〉或〈周期输出哈希〉写批准事件,门检查这条记录;依据变了,批准作废,重新批 | 连续三轮完整旅程零漏网(投料→领活→加工→复跑见证→确立→誊写→出门) |
| **二 放量** | 工位、投料面、合并权逐步放大,每放大一次记一笔(§10) | 发起人只剩两件事:签可调数字的修订、裁决上诉 | ——(常态运行) |

两条边界说死:**证据上是否确立,只按 §5.4 算**;阶段一里人的批准是多加的一道通行条件,不能代替第二只手,也不改证据算出来的标签——批准对准具体的卡版本或周期输出,依据变了就得重批。阶段〇没完成之前,只做本地实验:不收公开投料、不标确立、不出门。起步的手感照老经验来:**先让检查器咬人,再放工位进来**;两三个工位各跑一轮完整旅程,哪里卡住修哪里——修门、修卡、修检查——直到新来的工位不用人带就能上手,顺了再放量。

## 9. 什么情况说明出了问题

下面不是自动判决,是**带着假设的报警器**:指标到了,开卡调查;调查完全可以推翻假设。还没有检测器的,标"观察项",不假装会自动生效。

| 看什么 | 到什么程度 | 做什么 | 它可能说明什么 |
|---|---|---|---|
| 底线那一页的篇幅 | 超过注册的字数上限 | 开卡,走 §10 | 设计在漏进散文 |
| 记一件事的成本 | 同类日志行/卡的必填字段数、填写耗时、附件体量,连着两个周期上涨 | 开卡调查 | 台账在压垮干活的 |
| 派活的席位 | 出现"告诉别的工位下一步干什么"的角色(观察项) | 走 §10 | 中枢回来了 |
| 参与量 | 相邻两个周期,投料量和署名提交数一起降 | 开卡调查(先排除需求波动这类正常解释) | 门在抬高参与的价钱 |
| 门绿的 PR | 过了一个周期没人处理 | 开卡,找 committer 问清原因 | 流程在等某个具体的人 |
| 周期评审 | 连续两期没人接,或发现连续两期没人确立 | 自动开卡提醒发起人 | 评审在空转 |
| 新铸的订单 | 过了租期没人领,同血统的订单却照常结,连续两个周期 | 结单改零铸,开卡 | 铸造在产没人要的活 |
| 出门的卡 | 在自己声明的环境里被下游证伪,失效边界又没盖住 | 立刻开该失败类的缺口,后面的结单优先铸它(不破零铸和总量约束) | 门或见证漏了一类错 |
| 没人违反的规矩 | 一条规矩过了一个周期还没有检查撑腰,也"从没被违反" | 开卡:补检查,或删条文 | 没人在用它,或者没人看得见违反 |

## 10. 可调的数字,和改它们的唯一通道

可调的数字集中在这里,改法只有一条:**拿证据来**——引用观测或已确立的记录,一句话说清想改什么,并给出新规矩自己的失效条件;没证据的提议,和没证据的卡一个待遇。这条通道改变的是谁能被听见,不改变谁签字:核实后由发起人签入。

| 项 | 现值 | 备注 |
|---|---|---|
| 周期节拍 | 两周 | 暂定,跑起来再校 |
| 铸造参数 r / K | 2 / 4 | 上限参数,按实际活量再校 |
| 主张文件上限 | 4096 字节 | 装不下的进程序 |
| 日志行结果字段上限 | 220 字节 | 一行一文件 |
| 租期 / 续租上限 | 7 天 / 3 次 | 暂定 |
| 周期评审资格窗口 | 一个周期 | 窗口内交过卡的不能接 |
| 环境指纹 Profile | 版本化,见下注 | 必填字段缺失或 unknown = 没有互证资格;没注册 Profile 的主张类别,不能双手确立 |
| 阶段转换条件 | 连续三轮完整旅程零漏网 + 坏样例全拦 | 暂定 |
| 底线页字数上限 | 600 字 | "一页"的可量化说法 |

**环境指纹 Profile**(版本化,指纹里含 Profile 版本)比的是**实验条件,不是设备身份**:硬件——平台/芯片型号,影响实验的架构与资源配置(序列号、主机名不进指纹;具体哪台机器跑的另记一笔,并做脱敏);软件——驱动版本和固件版本(两个独立字段)、CANN runtime/toolkit、编译器及相关库的精确版本或构建标识,OS/内核/容器镜像按实验需要纳入(容器镜像代替不了宿主的驱动和设备事实);运行条件——按主张类别(语义/数值/性能)分别注册:编译参数、精度与数据类型、输入形状、数据集或生成器与种子、执行模式、影响判据的环境变量和时钟设置。字段类型、版本写法、单位、默认值由 Profile 定死;明写的 N/A 只在 Profile 允许时有效,和漏填是两回事。**同指纹只说明声明过的条件相同**,没声明的因素谁也没担保。

**部署验收**(阶段〇完成的硬条件,逐项真实验证,不拿纸面规矩充当平台能力):`refinery` 分支和周期 tag 受保护;直推被拒;作者不能自己批自己绕门;门没过不能合;登记之外的账号能按约定投料、领活,但不能合并;权限每放大一次记一笔;受保护的周期 ref 保证证据 commit 一直取得到,取证入口按 40 位 commit 精确取、校验哈希、能跑核验,失败时返回"证据不可复核";环境 Profile、判据、事件字段的 schema 冻结,是开始收公开投料和标确立的前提。

其余待定:首批订单写什么;原料卡和成品条目的字段细表——由形制检查器的坏样例集来定义,跟着检查器一起长。
