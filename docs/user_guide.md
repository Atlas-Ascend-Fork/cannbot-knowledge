# 知识库用户指南

这份指南介绍怎样使用 cannbot-knowledge 查询和贡献知识。安装方法见根 [README](../README.md#安装到项目)。

## 选择使用模式

| 你要做什么 | 使用模式 | 可用 Skill |
|---|---|---|
| 查询知识、回答技术问题 | `consumer` | `knowledge-query`、`ascendc-api-knowledge-query` |
| 新增或修改知识 | `contributor` | 三项基础 Skill、`ascendc-api-knowledge-query`，以及源码级算子使用的 `ops-knowledge-vv-ingest`、`ops-knowledge-cv-ingest`；仓内 trace 生产另用不安装到业务项目的 `ops-knowledge-trace-ingest` |

使用模式只决定安装哪些 Skill，不会改变知识卡的内容或可信程度。

## 查询前准备哪些信息

最好先明确下面几项：

- 要解决什么问题，例如查询 API、排查错误或优化性能；
- 使用哪种技术，例如 Ascend C 或 Triton；
- 目标平台是什么；
- 问题是否和 CANN 版本有关；
- 没有结果时，是报告知识缺口还是继续查找其他材料。

例如可以这样告诉 Agent：

> 使用 `knowledge-query` 查找 A2 平台上 Ascend C 的目标 API 约束。请打开知识卡并核对来源。如果没有结果，请说明当前知识缺口，不要使用其他 DSL 的结论代替。

如果平台或技术范围无法确认，应先补充信息。不要通过省略条件来扩大搜索范围。

## 怎样完成一次查询

1. **明确问题。** 一次先解决一个具体问题。复杂问题可以拆成多个小问题分别查询。
2. **查看覆盖情况。** 确认目标范围内是否真的有知识卡。只有目录不代表已经有知识。
3. **按真实条件搜索。** 保留需要的平台和技术条件。记录 CANN 版本供命中后核对正文，但当前不把它作为搜索过滤条件。
4. **打开知识卡。** 搜索摘要只用来选择卡片，不能直接当作答案。
5. **核对内容。** 阅读结论、适用条件、限制和完整来源。
6. **整理回答。** 说明结论适用于什么范围、依据是什么、还有哪些内容需要验证。

完整检查步骤见[形成可追溯回答](../recipes/answer_with_evidence.md)。具体查询方式见 [`knowledge-query`](../.agents/skills/knowledge-query/SKILL.md)。

Ascend C API 问题可直接使用 [`ascendc-api-knowledge-query`](../.agents/skills/ascendc-api-knowledge-query/SKILL.md)。它先识别目标硬件并按平台检索，阅读全文后根据当前问题选择相关卡片或头文件，不遍历全部链接。需要本机声明/实现时，提供工程使用的 CANN 版本和包路径；相对头文件线索必须结合正确的 AscendC 包布局解析，不能按知识仓目录打开。

## 怎样理解查询结果

| 看到的信息 | 它表示什么 | 它不表示什么 |
|---|---|---|
| 覆盖情况 | 当前有哪些真实知识卡 | 所有目录和已注册分类都有内容 |
| 候选卡 | 建议继续打开阅读的知识 | 可以直接使用的最终答案 |
| `status` | 卡片是草稿、稳定还是废弃 | 卡片一定正确或经过人工复核 |
| 信任层级 | 是否记录了机器或人工复核 | 卡片适用于所有平台和版本 |
| `sources` | 可以去哪里核对原始材料 | 来源一定能支持正文中的全部结论 |
| 零结果 | 当前条件下没有找到卡片 | 相关技术不存在 |

## 没有结果时怎么办

先检查索引是否正常。如果索引缺失、损坏或过期，本次查询无效，应先修复索引。

索引正常时，再检查：

1. 目标范围内是否真的有知识卡；
2. 平台、状态和技术条件是否正确，以及命中正文的版本边界是否适用；
3. API 名、错误码或关键词是否写对；
4. 是否确实存在尚未收录的知识。

精确 API 名在目标平台的 stable 查询零命中时，按对应查询 Skill 独立补搜平台未定位的 draft 卡。这些结果只提供待核验线索，不并入原平台结果；具体补搜入口见[API 查询实践](../recipes/api_search.md)。

不要用其他平台或其他 DSL 的卡片填补结果。如果补搜仍然没有结果，应说明查询范围、已经检查的条件和下一步建议，不能直接判断相关技术不存在。

## 怎样贡献知识

贡献知识前，先搜索同一主题并阅读已有卡片。然后选择一种处理方式：

- `create`：新增知识；
- `update`：更新已有卡片；
- `merge`：合并重复卡片；
- `split`：拆分职责过多的卡片；
- `deprecate`：废弃错误或过时结论；
- `defer`：信息不足，暂不落库。

确定处理方式后，再选择路径、准备来源和编写知识卡。最后更新导航与日志、运行全库 Lint，由知识仓维护者准备与改动后内容一致的检索索引，再确认新知识可以被目标查询找到。Query 本身不会重建索引；索引准备方式见其规范 Skill。

完整流程见[贡献知识](../recipes/contribute_knowledge.md)，正式要求以 [CONTRIBUTING.md](../CONTRIBUTING.md) 为准。

## 常见问题

| 问题 | 处理方式 |
|---|---|
| 索引不可用 | 停止查询，由安装器或仓库维护者重新准备索引 |
| 平台或技术不明确 | 请求补充信息，不扩大范围 |
| Lint 报错 | 根据错误找到对应规则或知识卡并修复 |
| 来源不足 | 缩小结论、保留为 draft，或选择 defer |
| 多张卡片结论冲突 | 比较平台、版本、来源和更新时间，暂时保留冲突 |
